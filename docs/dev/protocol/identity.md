# Identity and handshakes

Part of the [protocol reference](README.md): who a phone is, how two phones authenticate and encrypt a link, and the security boundaries.

## Security layers and participants

```text
Bluetooth transport: RFCOMM, LE CoC or bounded GATT byte stream
  BMH2 adjacent-link handshake: persistent signed identity + ephemeral P-256 ECDH
  BMS1 hop records: directional AES-256-GCM, ordered per Bluetooth connection
    BMH2 endpoint handshake: separate signature/KDF domain, opaque to a blind relay
    BME1 endpoint content: stream/media, lifecycle, timing and authenticated controls
    BFG1 forwarded-stream grant: source ID + stream ID + current media-open key
    BGK1 static group epoch key: independently wrapped for each final receiver
```

Direct streams use both handshakes. A direct stream or private call has one peer endpoint session. A normal viewer-forwarder is an admitted viewer and can decrypt for local playback. With forwarding enabled, it authenticates one child using fresh link and endpoint handshakes, wraps the current media-open key in `BFG1`, then copies unchanged upstream `BME1` ciphertext. The child checks the grant's source/stream IDs against its first authenticated mesh envelope and independently opens the shared media sequence. This is immediate-parent admission; the source does not maintain a graph-wide endpoint list, and forwarding adds no second codec or media decrypt/re-encrypt pass.

A forwarding chain has a separately authenticated endpoint session for each adjacent parent/child pair. Child keyframe requests and terminal acknowledgements are authenticated locally and regenerated toward the upstream parent, because adjacent sessions use different directional keys. Queue, decoder, thermal and bitrate telemetry is never forwarded graph-wide.

The hidden blind-relay harness has only adjacent-link keys and cannot open endpoint media. Its branched group mode creates one source `BGK1` epoch key and wraps it in an independent endpoint session for each final receiver. It can copy one shared encrypted media record to multiple children. This is distinct from the trusted normal viewer-forwarder; static key distribution does not implement live revocation or re-key.

## Identity and key agreement

- Android's persistent P-256 ECDSA signing key lives in Android Keystore. Windows uses a non-exportable named CNG user key.
- The node ID is the first 16 bytes of SHA-256 over the identity key's DER SubjectPublicKeyInfo.
- Each handshake creates fresh ephemeral P-256 ECDH keys and a 32-byte random nonce. The signed hello binds role, node ID, identity key, ephemeral key, nonce and transport/codec capabilities.
- Initiator/responder derive 64 bytes through HKDF-SHA-256, split into directional 32-byte AES keys.
- Link signatures and KDF use `BluetoothVideoMesh/LinkHandshake/1` and `BluetoothVideoMesh/LinkSession/1`.
- Endpoint signatures and KDF use `BluetoothVideoMesh/EndToEndHandshake/1` and `BluetoothVideoMesh/EndToEndSession/1`. A valid link hello is invalid in the endpoint domain.

`BMH2` is a clean cutover: `BMH1` peers cannot authenticate or downgrade the connection. Discovery-selected link identities must match the selected announcement prefix, including hybrid BLE-control/Classic-RFCOMM after operating-system pairing. Direct DEBUG connections still authenticate a persistent app identity but lack that discovery binding.

Classic link security is independent of the app's. Streams and forwarders have always used insecure RFCOMM; calls and relays use Android's secure RFCOMM, which requires a MITM-authenticated bond on both phones. The experimental Classic without pairing (the register in [architecture.md](../architecture.md), off by default) makes every role insecure: Android pairs Just Works without storing a bond, so the radio link has no authenticated link key, as on LE CoC and GATT. Nothing in BMH2, BMS1, BME1, BFG1 or BGK1 changes, and the link and endpoint handshakes still bind the announced node prefix. An active radio attacker can therefore sit between the phones at the link layer and see record sizes and timing (the metadata a passive observer of LE links already sees), but cannot open, forge, reorder or replay records, and cannot impersonate either identity. Remembered Classic addresses are hints bound to an authenticated identity only after BMH2 succeeds on them; a relayed handshake can point a hint at a relay, which costs a failed or relayed attempt, never trust. A first contact by Classic inquiry needs the target to be discoverable, which exposes its name and public address to nearby scanners for the visibility period.

## Identity verification

Added 2026-10-10 (API only; the UI binds it). Fingerprints, codes and checks are computed locally from keys the BMH2 endpoint handshake already authenticates; no record format changes.

- **Why.** Discovery binds a link to the 48-bit (12-hex) announcement prefix, and calls/streams check the endpoint identity against that prefix. The node ID itself is 128 bits and the signed hello proves possession of the key, but an attacker who grinds about 2^48 P-256 keys gets one whose node ID starts with a victim's prefix and passes the prefix check. Comparing the full key fingerprint closes that gap for contacts the user has verified.
- **Fingerprint.** `SHA-256(identity SubjectPublicKeyInfo DER)`, the exact bytes `NodeId.fromPublicKey` hashes, so the first 16 bytes are the node ID and the first 6 the announcement prefix. Shown as 64 hex digits (16 groups of four). Each authenticated endpoint session (`EndToEndVideoSession.peerFingerprint`) carries the peer's fingerprint.
- **Safety code (Signal style).** Each party has its own 30-digit half: `h1 = SHA-512("BluetoothVideoMesh/IdentityVerification/SafetyCode/2" || fingerprint)`, `h(i+1) = SHA-512(h(i) || fingerprint)` up to `h5200`; group `g` (0-5) is the big-endian 40-bit integer from bytes `5g..5g+4` modulo 100000, zero-padded. The pair code is the two halves sorted as strings: 60 digits in twelve groups of five. Both phones show the same code for the same pair, and it never changes for the pair. Each half depends on one key only, so a man in the middle must find a key whose half equals the victim's half: a second preimage of about 2^100 tries, each costing 5,200 hashes and a key generation. There is no birthday shortcut (the version 1 code hashed both keys together, which allowed one, and was replaced before release). The QR comparison of the full 256-bit fingerprint remains the stronger path.
- **QR payload.** `BVMID1.<64 hex fingerprint>.<base64url, no padding, UTF-8 NFC display name>`. Encoders write uppercase hex (QR alphanumeric mode); parsers accept all-uppercase or all-lowercase hex. The parser rejects any other magic/version, field count, length or alphabet, mixed-case hex, padding, non-canonical base64, invalid UTF-8 and names that are blank, longer than 64 bytes, or contain control, format (bidi embeddings, overrides and isolates U+202A-202E and U+2066-2069, directional marks, zero-width characters, BOM), private-use, surrogate, unassigned or separator code points. Names are NFC-normalized. The display name is an unauthenticated label; only the fingerprint is compared.
- **Verified contacts.** `noBackupFilesDir/identity-verification/verified-contacts.bin`, sealed with its own non-exportable Keystore AES-256-GCM key (`bluetooth-video-mesh-verification-v1`). The file and key exist only after the first contact is verified. A peer becomes verified only when the scanned (QR) or confirmed (safety code) fingerprint equals the full fingerprint of a handshake completed in this process with that node ID (an end-to-end handshake, or since 2026-10-27 the link handshake of a direct BMH3 connection, whose real-key answerer is checked there too); the last 1,024 authenticated real keys are remembered by node ID for this, in memory only (throwaway keys never are). A second key with a verified contact's prefix cannot be marked verified until the old contact is explicitly forgotten.
- **Session check.** Every end-to-end handshake (calls through any relay chain, direct and forwarded streams, group endpoints) records the peer fingerprint and compares it with the verified contacts right after the signature verifies and before any content key is used. A verified contact with the same 48-bit prefix but a different fingerprint is `MISMATCH`: it is logged as `SECURITY IDENTITY MISMATCH` (a release log names no peer since 2026-10-27; DEBUG adds the 12-hex prefix), the UI listener is notified, and by default (`MismatchPolicy.REFUSE`) the handshake fails with "possible impersonation". `WARN` continues and leaves the warning to the UI. With no verified contacts nothing changes.
- **Forwarded streams.** The forwarder's own fingerprint is checked in its handshake. The original source is known only by the 128-bit node ID that the authenticated forwarder states in its `BFG1` grant: the receiver compares it with verified contacts of the same prefix (equal node ID: verified; same prefix, different node ID: `MISMATCH` under the same policy). This trusts the forwarder, which is an admitted viewer holding the media key and could re-seal content anyway.
- **Group branches.** A group source that refuses one receiver drops only that receiver: it sends that receiver an empty `WRAPPED_KEY` control (the existing type, no new value). The receiver's endpoint cannot open it and fails closed, and the relay reports it gone. The other receivers keep their keys and the stream continues; the refused receiver is not counted, and its later controls are ignored.
- **Damaged store.** A store that exists but cannot be opened is `STORE_UNREADABLE`, with a cause: `CORRUPT_FILE` (AES-GCM authentication or structure fails: damaged, or sealed under a lost Keystore key) stays unreadable until the user resets the store (`resetVerifiedContacts()`); `KEYSTORE_ERROR` and `IO_ERROR` are retried on the next access. The cause is logged and UI listeners are told once per episode. The policy is fail-open (design decision): nobody is refused because of it, every peer counts as unverified meanwhile, and the store is never overwritten implicitly.
- **What it does not do.** It proves which key a phone holds, not who holds the phone. Unverified peers are still accepted exactly as before (prefix check only). The store has confidentiality and integrity against offline tampering (AES-GCM under a Keystore key) but no rollback or deletion protection: anyone who can delete or roll back app files on the phone can make a verified contact unverified (never falsely verified), which disables the mismatch refusal for that contact. Store-and-forward contact cards keep their own safety number (key plus mailbox key). A wipe or reinstall creates a new key, so the contact becomes unverified (new prefix), not a mismatch.

## Build tag in the link hello and update verification (updater, default on; wire change 2026-10-11)

Status: designed 2026-10-11 for the "Newer version nearby" notice (SWITCHES register "Check for updates" and "Tell me about newer versions nearby"). No record type, length or version number changes, so every BMH2 build keeps interoperating. Not yet tested on phones (PLAN).

**Why the hello, and why not a new field.** The link hello is the one authenticated artifact both phones already exchange on every connection, and its signature binds it into the session transcript. `HandshakeHelloCodec` is exact-length (a longer capability block or trailing bytes fail with "Unsupported capability version" or "Trailing handshake data"), so a new field would cut off every older build, including the published 0.1.0-beta. A new hop record type is also rejected as unknown by older readers. The hello does have two places an older build cannot object to: a transport-mask bit it never tests, and a 32-byte nonce it treats as opaque.

**Field.** Link-hello transport-mask bit 7 (`0x80`) means: the first two bytes of this hello's nonce are a build tag, and the other 30 are random.

| Link-hello transport-mask bit | Meaning |
| --- | --- |
| 0, 1, 2 | Transports: Classic, LE CoC, LE GATT |
| 3 | `BDO1` link opening (rotating discovery IDs) |
| 4 | `SETUP` (relayed calls) |
| 5 | Unused in link hellos (end-to-end hellos use it for `LABELS`). Reserved by the draft "Classic address exchange and media upgrade" (not implemented) |
| 6 | Call relay |
| 7 | **Build tag** (end-to-end hellos use bit 7 for call video fragments; a link hello and an end-to-end hello are different signature domains and never share a reader) |

```text
nonce[0..1] = tag, big-endian u16:  bit 15 = project release key,  bits 14..0 = release number R (1..32767)
nonce[2..31] = 30 random bytes
```

`R = installed longVersionCode / 10`: the base `versionCode` of `app/build.gradle.kts` with the ABI digit removed (ARCHITECTURE "Distribution and releases": code = base x 10 + 0/1/2), so the tag never says which CPU type a phone has. A debug or non-split build (code below 10) has no release number and sends no tag. Bit 15 is set when the installed APK's only signer is the published release certificate pinned in the app (`AppSharePolicy.PUBLISHED_RELEASE_CERT_SHA256`); an F-Droid build, a self-built APK and a debug build send 0. The tag is sent only in **link** hellos (never end-to-end hellos, which a relay copies, so only the adjacent phone learns it), never in an advertisement, and only while the user's switch "Tell me about newer versions nearby" is on. A DEBUG benchmark launch sends it only with `test_newer_versions_nearby=true`; otherwise the hello bytes are exactly as before.

**Receiver rules.**

1. Read the tag only after the BMH2 handshake succeeded (`MeshHandshake.finish` verified the peer's signature over its hello, which includes the bit and the nonce). A failed or unverified handshake yields nothing.
   The tag then reaches the notice (`LinkBuildTags.sink`) **only from a link this phone opened** (it called, joined or relayed with that phone): a stranger who connects to our listener could otherwise plant a note, and a note leads a user toward installing a file (independent review F2). The responder side still parses the tag and keeps it on the session; it just does not report it.
2. Take it only if bit 7 is set, `R` is 1..32767 and the local switch is on. An older build never sets bit 7, so it yields no tag.
3. Remove bit 7 from the capabilities the rest of the app sees (`SecureBluetoothSession.peerCapabilities`) and keep the tag in a separate field, so no transport test, relay check or negotiation can read it. Local capabilities never carry bit 7, so the existing `peer.transportMask and local.transportMask` overlap tests are unaffected.
4. The tag is a **claim by the peer's identity key about its own build**, not proof about its APK. The hello is signed by the identity key, never by the APK signing key, so a modified app can claim any value. It therefore only ever decides whether to *show a notice*; it never starts a download or an install.

**Notice rules** (`NewerVersionNearby`, JVM-tested). Show "Newer version nearby" only while all hold: the switch is on; the claim `R_peer` is greater than the installed release number and at most 20 above it (a bound so one forged number cannot suppress later notices for long); a phone with the project release key sees only claims with bit 15 set (a build signed by someone else cannot update it); and the user has not dismissed this claim (a dismissal hides claims up to that number for 7 days, then the number is forgotten). A claim that is not repeated for 14 days fades. The stored state is the best claim, when it was seen and the dismissal; no peer identifier is stored. The notice is a quiet row on the home screen, never a sound, a notification or a dialog, and it never appears during a call or stream.

**Compatibility.** An older build parses a tagged hello unchanged: it checks the nonce length (32) and reads `transportMask` only with `and` tests (`transportMask and transport.capabilityMask`, `and LINK_HELLO_BIT`, `and CALL_RELAY_CAPABILITY`, ...); no reader compares the whole mask or looks at nonce contents. The Windows receiver (`SecureBluetoothProtocol.cs`) checks only the nonce length and copies the mask. The iPhone app (`NearbyCore/MeshHandshake.swift`) also checks the nonce length only and reads the mask with `&` tests; its call-fragment test (bit 7) reads the end-to-end session's capabilities, never the link's, so a tagged Android link hello cannot switch fragments on. The HKDF salt `SHA-256(initiator nonce || responder nonce)` still has at least 240 random bits from each side, and the fresh ephemeral ECDH keys are what make the session keys unique, so a two-byte tag costs no cryptographic strength. The tag is part of the signed, transcript-hashed hello, so it cannot be added, removed or changed by anyone who does not hold the identity key without failing the handshake. Tested: a tagged and an untagged phone handshake in both roles; a tagged hello decodes with the unchanged codec; the tag is invisible in `peerCapabilities`.

**Privacy.** The hello is not encrypted: anyone who completes or captures a link handshake already sees the node ID, identity key and capability bits. The tag adds the release number (coarse) and one bit "project-signed build". It is never in an advertisement, so a passive scanner of adverts learns nothing, and with rotating discovery IDs a stranger still learns the identity only by connecting (stated residual there). Stated residual: a peer that connects to an updated phone can tell whether it is outdated, which could help it pick a known bug; the switch turns this off in both directions (a phone that does not send also does not show notices). Forcing the same disclosure on phones with the switch off is not possible, because an older build sends no tag at all.

**BMH3 links.** The tag does not travel in a BMH3 link's cleartext (no nonce field, no bit 7): it is the `BUILD_TAG` extension inside the sender's encrypted block (see "Experimental BMH3 identity-hiding link handshake"), with the same receiver rules.

**Update verification (not a wire format; used by the online check and by an APK received from a nearby phone).** No path installs automatically. An APK is installed only after Android's own confirmation, and only if all of these hold, checked on a private copy and bound to the bytes installed:

1. The package name equals this app's.
2. `versionCode` is strictly higher than the installed one (never a downgrade), and its ABI digit (`versionCode % 10`) is the installed one or 0 (universal), so a 32-bit-only file never replaces a 64-bit install.
3. `PackageManager.getPackageArchiveInfo(..., GET_SIGNING_CERTIFICATES)` reports exactly one current signer (no multi-signer APK). On Android 10 the call must also pass `GET_SIGNATURES`, or the platform collects no certificates and `signingInfo` is null (AOSP android10-release; fixed in Android 11).
4. That signer's certificate SHA-256 equals the installed app's signer, or the APK carries a signing lineage (`signingCertificateHistory`) whose last entry is that signer and which lists the installed certificate before it (a key rotation signed by the old key; Android enforces the lineage's capabilities at install). For the online check it must also equal the pinned release certificate, and the online check is offered only when the installed app already carries that certificate (a debug or F-Droid-signed copy cannot be updated from a GitHub release).
5. For an online download, the file's SHA-256 equals the release's published value (the asset `digest` of the GitHub API response, else the release's `SHA256SUMS`); with neither, nothing is installed.
6. The SHA-256 computed over the private copy while it is verified equals the SHA-256 of the bytes written into the `PackageInstaller` session (one pass, hashed in transit), so a file swapped between verification and installation is detected.

Android independently refuses an update whose signing certificate differs from the installed one and a lower `versionCode`; the checks above fail first with a readable reason and add the pin, the ABI rule and the hash bindings. The online source is a value (`UpdateSource`: `releases/latest` URL, the release-download prefix its assets must have, the redirect hosts); GitHub is the only one shipped, and a mirror is one more instance, no more trusted than GitHub because the checks above run on the file. A later certificate rotation needs the next certificate added to the pin set in a release signed by the old key (`ReleaseSigner.PINNED`); only then does a lineage APK signed by the new key pass the online check on installed copies.

## Experimental BMH3 identity-hiding link handshake (on by default for user sessions since 0.2.0-beta)

Settings > Privacy > Advanced privacy "Hide my ID from strangers" (feature id `bmh3`, DEBUG benchmark extra `test_bmh3`; default ON for user sessions since 0.2.0-beta, one constant `ConnectivityFeatureDefaults.BMH3`, a stored choice wins, a DEBUG benchmark launch reads only the extra; the BMH3 test steps 1, 3 and 6 passed on the S24 and ASUS, steps 4, 5, 7, 8, 10 and 11 not yet run). Sub-options, DEBUG extras only: `test_bmh3_only` (an initiator never speaks BMH2), `test_bmh3_contacts_only` (a responder reveals itself only to a holder of its lease key; `test_bmh3_test_lease=<64 hex>` supplies a fixed lease key for phone tests, standing in for real presence leases until Phase 2). Design 2026-10-11, built on an earlier SIGMA draft that a independent security review corrected (findings SR1-SR14) and then reviewed again in this form by a second independent reviewer (findings BR1-BR11); both are adopted below and recorded in DECISIONS "Design F". With the switch off every byte on air and on the link is unchanged, and a BMH3 message is rejected exactly as by an old build. Phase 1 covers **private calls and message exchanges** (the call endpoint's link and end-to-end handshakes, direct and through DEBUG call relays); streams, viewers, forwarders, the stream relay, the group harness and Design C reach-page routes keep BMH2 (PLAN "Discovery privacy" item 5). Not yet tested on phones.

**Why.** BMH2 hellos are signed but not encrypted. A sniffer that follows a connection reads both identity keys; anyone who connects learns the responder's key; a sniffed hello can be replayed to draw out the other side's hello (RV13); relays see both endpoint hellos. Rotating discovery IDs hide the advertisement only: bitchat's own design note (docs/PEER-ID-ROTATION.md section 1) says rotating IDs accomplish nothing while a handshake sends the static key in the clear. BMH3 is the handshake that closes this: each side first sends only a one-time key and a nonce, and identities, capabilities, signatures and key confirmation then travel encrypted under keys derived from the one-time exchange.

| Observer | BMH2 | BMH3 |
| --- | --- | --- |
| Passive sniffer on a hop | both identity keys and both capability sets | one-time keys (random), message sizes and timing, and which order was used (3 or 4 messages) |
| Active attacker who connects (stranger, prober) | the responder's identity key | Everyone mode: the responder's identity (once per connection, rate-limited by the signing budget). A Contacts-only responder (below): nothing, unless the attacker holds its lease key |
| Active attacker who answers (fake or replayed advert), **when the caller speaks BMH3** | the initiator's identity from its first hello, and a replayable signed hello | nothing at the end-to-end layer, and at the link layer toward a relay a throwaway key instead of the real one: the caller reveals only after the answerer's signature, key confirmation and the discovery-binding check passed |
| Same attacker, caller speaks BMH2 (version 2 advert without hint or pin, or a BMH2 phone) | the initiator's hello | the same: BMH3 changes nothing for a caller that does not speak it (see "Stripped hint") |
| Relay on a chain | both endpoints' hellos | its two neighbours' link identities only (and with the throwaway key, not even the caller's); a one-relay chain still sees both endpoints, because both are its neighbours |
| Later theft of an identity key | identities were public anyway; session keys were already forward secret | past session keys and past identities stay secret (the identity key only signs) |

**Primitives (all already in the app).** ECDH P-256 (`KeyAgreement("ECDH")`), HKDF-SHA-256 (Extract and Expand over the app's HMAC), AES-256-GCM (`MeshAead`), ECDSA-P256-SHA256 with the Keystore identity key (`SigningIdentity.sign`; same key, alias and purposes), HMAC-SHA-256. No library, key type or Keystore purpose is added.

### Negotiation and downgrade

The initiator chooses before it sends a byte and never retries with BMH2 after a BMH3 attempt failed (an attacker who drops BMH3 gets a failed connection, not a cleartext hello). With the switch on:

| Selected offer | The initiator speaks | Why |
| --- | --- | --- |
| Rotating (version 5) call offer | **BMH3, always** | A fake or replayed rotating advert could otherwise leave the hint out and collect the caller's BMH2 hello (BR1). Old builds cannot produce or decode version 5, so BMH2 would only ever be a downgrade. Cost: a phone with rotating IDs on and BMH3 off cannot be called by a phone with both on. |
| Version 2 call offer with the hint, or a pinned prefix, or `test_bmh3_only` | BMH3 | The callee said so (hint), this phone has seen it speak BMH3 (pin), or the user wants no BMH2. |
| Version 2 call offer, none of those | BMH2, exactly as today | Old phones stay reachable. This is today's exposure, not a new one. |

- **Hint.** `capabilitySummary` bit 5 (`0x20`, `Bmh3Hint.SUMMARY_BIT`) of a **version 2** private-call offer, set by the callee at route cost 0 (not on a relay-helper offer): "this identity accepts BMH3 handshakes". It is not set on version 5 offers (they imply BMH3 for BMH3 initiators; the bit would only be another stable quasi-identifier). Readers of call offers test only codec bits, bit 4 (relay consent) and bit 3 (dual); stream offers compare the whole byte and never carry it. A DEBUG call relay mirrors the child's summary one hop further, so a caller reads it at any route cost and assumes the relay runs the same build (call relays are DEBUG only). The iOS compact encoder cannot represent bit 5 and must mask it (open item, iOS repository).
- **Pin.** After a BMH3 handshake toward a **version 2** offer whose answerer proved itself (and only while pseudonym mode is off), the peer's 6-byte node prefix is remembered (at most 256, oldest dropped, each valid 30 days after its last success) in `noBackupFilesDir/hidden-identity-pins.bin`, sealed with the verified-contacts Keystore key: never part of a cloud backup or device transfer, deleted by the emergency wipe. A rotating (version 5) offer is always BMH3 and in pseudonym mode every stranger link is a throwaway, so a pin there would only list the contacts this phone called (review 2026-10-27; the plain `hidden-identity-pins.txt` of earlier builds is read once, rewritten sealed and deleted). The link and end-to-end handshakes of one outgoing attempt, and a Classic connector's link handshake, take the choice, the pin rule and the caller's throwaway from one per-attempt plan, so a callee always meets one stranger at both layers. A pin store that cannot be read at that moment (a passing Keystore or storage failure) counts as pinned for the attempt: BMH3, never a BMH2 first hello. Pins are written off the handshake, and an earlier build's plain file is sealed and deleted at each start after any pending emergency wipe was completed. A later version 2 offer with a pinned prefix is contacted with BMH3 even if the hint was stripped. The expiry bounds how long a peer that turned the feature off stays unreachable; a user-confirmed BMH2 retry that clears the pin is a follow-up (PLAN).
- **Responder.** With the switch on, a call listener reads the first frame and dispatches on its magic (`BMH2` or `BMH3`). An **Everyone-mode** listener accepts both: refusing BMH2 would protect nobody, because the initiator's hello is already sent and a prober can still obtain the identity through BMH3, and it would strand old builds and phones with rotating IDs but no BMH3 (a rotating-ID phone should therefore not refuse BMH2 with strangers; the protection is on the caller's side, above). A **Contacts-only** listener always refuses BMH2 (silent close), because a replayed BMH2 hello would draw out its own hello (RV13).
- **Stripped hint.** The hint is unauthenticated. An attacker that strips it from a version 2 advert, or that answers a forged legacy advert, makes an unpinned hint-driven initiator speak BMH2, which hands its signed hello to the attacker (SR3): the same exposure as today. Mitigations: pins after a first contact, `test_bmh3_only`, and rotating IDs (which are always BMH3). A signed "BMH3 capable" bit in the BMH2 capabilities was considered and rejected: it could be read only after the initiator's hello was sent, and an attacker simply omits it.
- **Link to a relay.** At route cost above 0 the link peer is a relay that cannot be bound to the selected advert, and route cost is an unauthenticated hint, so a fake relay could answer R_FIRST and collect the caller's link identity (BR2). The caller therefore presents a **throwaway software key** at the link layer toward a first hop at route cost above 0; relay admission uses node IDs of the neighbours (the caller is never the callee or the relay), so it is unaffected, and the end-to-end handshake still proves the real key to the callee after the callee proved itself. Not covered in Phase 1 (stated residuals): a Design C helper is called at route cost 0 on its own advert and learns the caller's link identity, and a route chosen from an unauthenticated reach page keeps the end-to-end handshake on BMH2 (reach pages carry no capability summary) unless `test_bmh3_only` or a pin says otherwise.
- **End to end.** The caller speaks BMH3 end to end when it spoke BMH3 on the link (the same choice), otherwise BMH2. The callee dispatches on the first end-to-end record's magic.

### Messages

All integers are big-endian. Link messages travel as `u32 length | message` on the raw RFCOMM, LE CoC or GATT byte stream (length 1..2048), like BMH2; end-to-end messages are the payloads of `BMS1` type-4 records, like BMH2 endpoint hellos. A message ends where its frame or record ends. Each message is built, signed and sealed once; a retransmission, if a carrier ever needed one, resends the identical bytes (re-signing with ECDSA's random k and re-sealing under the same key and zero nonce would reuse a GCM nonce).

```text
header (8)  "BMH3" | version 1 | purpose (1 link, 2 end to end) | message number | flags (unknown bits must be 0)

msg1  I -> R  header(1, flags) | offer 0x01 | e_I (65) | n_I (32) | tag (16)                      122 bytes
              flags bit 0 MAY_REVEAL_FIRST: the initiator would accept I_FIRST
              offer 0x01 = P-256 ECDH, HKDF-SHA-256, AES-256-GCM, ECDSA-P256-SHA256 (the only suite)
msg2  R -> I  header(2, flags) | e_R (65) | n_R (32) [ | AEAD(k_hs_r2i, B_R) ]                  105 if flag 0, 431 if flag 1
              flags bit 0 R_FIRST: 1 = the responder's block follows, 0 = nothing follows
msg3  I -> R  header(3, 0) | AEAD(k_hs_i2r, B_I)                                                 334
msg4  R -> I  header(4, 0) | AEAD(k_hs_r2i, B_R)           (I_FIRST only)                       334
```

`e` is an ephemeral P-256 public key in SEC1 uncompressed form `04 | x | y`; `n` is 32 random bytes; `tag` is the contact tag (below) or 16 random bytes, indistinguishable on the wire. A responder that would answer I_FIRST and sees `MAY_REVEAL_FIRST` clear closes without replying (normative, not a hint). AEAD is AES-256-GCM with a 12-byte all-zero nonce, a 16-byte tag and associated data = the message's cleartext part (msg2: its first 105 bytes; msg3 and msg4: the header). Each handshake key encrypts exactly one message, so the fixed nonce never repeats under one key. That holds only if `e_I`, `n_I`, `e_R` and `n_R` are fresh from the platform CSPRNG for every handshake: **a responder must never cache, precompute-and-reuse or resend a msg2** (SR5).

**Identity block `B`** (the plaintext inside the AEAD, always 310 bytes):

```text
SPKI length (2) = 91 | identity SPKI (91) | capabilities (7) | extension length (2) = 112 | extensions (112) | signature (64) | finished MAC (32)
```

The identity is the canonical 91-byte P-256 SubjectPublicKeyInfo (`3059301306072a8648ce3d020106082a8648ce3d030107034200 | 04 | x | y`, the point validated as above); the node ID is `SHA-256(SPKI)[0:16]`, computed by the receiver. A key whose platform export is not that exact form is re-encoded first, so one key has one node ID. Capabilities are the existing `NodeCapabilitiesCodec` version 1 bytes (the link or end-to-end hello contents, unchanged). The signature is raw `r | s` (IEEE P1363) with `0 < r, s < n`; Keystore's DER output is converted (strip the sign byte of each integer, left-pad to 32 bytes) and JCA verification re-encodes. The MAC comparison is constant time. Every block has the same size: the extension area is always exactly 112 bytes, filled by a `PAD` extension. This hides an `INTENT` and any later extension inside the handshake; it does not hide that rotating IDs are in use from a sniffer, because the `BDO1` and `BDX1` records that follow still have sizes that depend on the pinned IDs (BR7, stated residual; removing them when both sides speak BMH3 is a follow-up that touches the rotating-ID code).

**Extensions** (`type (1) | length (2) | value`, strictly ascending types, each at most once, the area parses to exactly 112 bytes; a type from `0x80` is critical and fails the handshake if unknown, a lower unknown type is skipped):

| Type | Name | Allowed in | Value |
| --- | --- | --- | --- |
| 0 | `PAD` | any block | zeros, first in the area |
| 1 | `OPENING` | responder blocks only (msg2, msg4) | the rotating-ID opening body of `BDO1` after its magic and version: `count (1, 0..2) \| count x entry (43)`. A rotating-ID listener includes the entries pinned when the connection was accepted whatever the initiator signed (it cannot see the initiator's hello bits); in msg2 the initiator checks it **before** it reveals itself, in msg4 (I_FIRST) after |
| 2 | `INTENT` | msg3 under I_FIRST only | 1 byte: 1 call, 2 stream, 3 store-and-forward exchange, 4 relay; reserved for an "ask first" mode, v1 senders omit it |
| 3 | `BUILD_TAG` | either block of a **link** handshake only | 2 bytes, the u16 of "Build tag in the link hello" (bit 15 = project release key, bits 14..0 = release number 1..32767); sent only while the "Tell me about newer versions nearby" switch is on; a value that is not a valid tag counts as none |
| 5 | `RELAY_SEEK` (draft, Design OR, DEBUG prototype only) | responder blocks (msg2, msg4) of a **link** handshake only | 1 byte, a feature bitmask: bit 0 `SEEK` version 1, bits 1-2 reserved (OR-T, OR-C), others zero; signed only by a listener that would admit a search now (PROTOCOL "Draft: on-demand route seek") |

A known type outside its allowed place fails the handshake (a `BUILD_TAG` in an end-to-end block included: bit 7 means call video fragments there). Everything the app can send together fits: two opening entries (`OPENING` 3 + 1 + 86), an `INTENT` (4) and a `BUILD_TAG` (5), behind a `PAD` of at least its own 3-byte header.

**Build tag (the updater's "newer version nearby" hint).** BMH2 carries it in two cleartext places of the link hello (transport-mask bit 7 and nonce bytes 0-1), so a sniffer reads the release number and the project-key bit. BMH3 has no such field to borrow: its nonces are fully random and bit 7 stays unused in its capabilities. A link handshake carries the tag as the `BUILD_TAG` extension inside the sender's own encrypted, signed block, so only the authenticated peer reads it and a sniffer learns nothing from it (the block size does not change). The receiver rules of "Build tag in the link hello" apply unchanged: the tag is the peer's claim about its own build, it is taken only from a verified block, it reaches the notice only from a link this phone opened (`SecureBluetoothSession.peerBuildTag` is set on both sides, `LinkBuildTags.report` runs on the initiating side only), and the capabilities the rest of the app sees never carry bit 7. The end-to-end handshake never carries a tag.

### Key schedule

`D` is the purpose domain `BluetoothVideoMesh/BMH3/Link` or `BluetoothVideoMesh/BMH3/EndToEnd`; every hash, key and signature depends on it, so a link message is invalid at the endpoint and vice versa. `TH(x) = SHA-256(D | 0x00 | x)`. `E(K, label) = HKDF-Expand(K, D | "/" | label, 32)`, labels ASCII.

```text
T (R_FIRST) = msg1 | msg2clear | B_R | hdr3 | B_I          T (I_FIRST) = msg1 | msg2clear | hdr3 | B_I | hdr4 | B_R
dh       = ECDH(e_I, e_R)                                    32-byte big-endian x coordinate
TH2      = TH(msg1 | msg2clear)                              the whole msg1 including tag and flags, and msg2's flags
HS       = HKDF-Extract(salt = TH2, IKM = dh)
k_hs_i2r = E(HS, "hs i2r")      k_hs_r2i = E(HS, "hs r2i")   one message each
fk_I     = E(HS, "finished i")  fk_R     = E(HS, "finished r")
dHS      = E(HS, "derived")
MS       = HKDF-Extract(salt = TH(T_final), IKM = dHS)       T_final = the whole transcript
k_i2r    = E(MS, "app i2r")     k_r2i    = E(MS, "app r2i")  the initiator sends under k_i2r, the responder under k_r2i
EXP      = E(MS, "exporter")                                 reserved for channel binding
```

For a block sent by role `X` (`Initiator` or `Responder`), let `P` be the transcript up to and including the cleartext part of the carrying message, and `prefix_X` the block up to the end of the extensions:

```text
sig_X = ECDSA-P256-SHA256(sk_X, D | "/" | X | " signature" | 0x00 | TH(P | prefix_X))
mac_X = HMAC-SHA-256(fk_X, TH(P | prefix_X | sig_X))
B_X   = prefix_X | sig_X | mac_X
```

The session keys depend on the whole transcript, so both identities, both capability sets, the tag, every flag and every extension are bound into them. After the session keys are installed each phone zeroes `dh`, `HS`, `dHS`, `MS`, the handshake keys and its ephemeral private key. The first `BMS1` (or `BME1`) record in each direction uses sequence 0 under its own direction key; a unit test pins both first records, so a swapped direction mapping (one key, repeated nonces) cannot pass.

### Order, contact tag and local checks

The responder picks the order from its **global mode** only (SR4), because it cannot know why a peer connected:

| Responder mode | Order | Who is protected from an active attacker |
| --- | --- | --- |
| Everyone (default) | R_FIRST (SIGMA-I, three messages) | the **initiator**: it verifies the answerer before it reveals anything. The responder reveals to whoever sent a msg1, which is what Everyone means |
| Contacts-only (`test_bmh3_contacts_only`, DEBUG in Phase 1) | R_FIRST if msg1's tag matches, otherwise I_FIRST (SIGMA-R, four messages): the stranger must reveal first, is silently closed unless admitted, and never learns the responder's identity | **both**, between lease holders; the responder against strangers |

**Contact tag (SR2, BR3).** A rotating-ID phone's contacts hold its daily lease keys `L_d` (this document, "Recognition and presence leases"; since the hardening these are independent random 32-byte keys, deleted when their day leaves the window, not derivations of one master key). `K_tag` needs only a pseudorandom key, so nothing about the tag changes: revocation (a new generation draws new keys) and forward secrecy (a day's key is gone after its window) come from the key lifecycle, and Phase 2 reads the responder's keys from `PresenceVault.dayKey(idEpoch, currentEpoch)` and a contact's from its stored lease record. `K_tag = HKDF-Expand(L_d, "BluetoothVideoMesh/BMH3/ContactTag/1", 32)` and `tag = HMAC-SHA-256(K_tag, TH(msg1 with the tag field zeroed) | binding)[0:16]`, with the 11-byte **binding** `selected (6) | role (1) | epoch (4)`: the 6 advertised bytes of the offer the initiator selected, the role (0, call), and for a version 2 advert the initiator's wall epoch (0 for version 5, whose RDI already changes every epoch). The binding makes a recorded tag worthless against the responder's next advert: without it an attacker who sniffed one tagged msg1 (a relay sees it in the clear) could replay it in later epochs to any Contacts-only phone and see which one answers R_FIRST, which would link the target's RDIs across a day. The initiator sends the tag when it recognised the selected ID as a contact and holds the lease for that day, otherwise 16 random bytes. The responder checks, in constant time and without early exit, each of its **own** lease keys (days of epochs `E-1 .. E+1`) against each advert it has on air or left less than 60 s ago: the RDIs of its pinned opening entries for version 5, its fixed prefix at wall epochs -1, 0, +1 for version 2 (a handful of HMACs, independent of the number of contacts). This is the idea of WireGuard's `mac1` and Briar's per-period transport tag, applied to the existing lease keys: prior shared knowledge is the only way both identities can be hidden from an active attacker, because otherwise whoever authenticates first must reveal to an unauthenticated peer (Krawczyk, SIGMA, identity-protection discussion). Replaying a recorded msg1 inside the same epoch draws a msg2 whose block is sealed under keys only the true `e_I` holder can derive, so it reveals nothing; the replay cache bounds the cost, and what remains is the timing of a signature (listed below). When a tag matched, the responder still requires after msg3 that the initiator is a current lease recipient (`admitInitiator(peer, tagMatched)`); otherwise it closes, logs and, in Phase 2, starts a new presence generation, because a lease has leaked (BR9).

**Initiator rules (SR1, BR4).** A default initiator **refuses I_FIRST**: an attacker who answers picks its own `e_R` and could otherwise demand it, collecting the identity of every user who taps Call on a forged or replayed advert. An initiator that sent a real tag also requires R_FIRST. `MAY_REVEAL_FIRST` is set, and I_FIRST accepted, only after an explicit user confirmation, which Phase 1 does not offer. When the selected row is a recognised or verified contact, the answerer's **full 128-bit node ID** must equal that contact's before the initiator reveals (an attacker who grinds a 48-bit RDI or prefix is a different key); verified contacts also keep the full-fingerprint check below.

**Checks that run before a phone reveals itself.** The existing identity checks move to just after the peer's block verified and before the phone's own block is built:

1. Not a self-connection: the peer's identity differs from the phone's own and `e_I != e_R` (SR6).
2. Discovery binding on the selected advert, never on the peer's flags (RV15). Version 2, route cost 0: the peer's node prefix equals the announced prefix. Version 5: the peer's `OPENING` opens the selected 6 bytes for the peer's node ID within the epoch window (`DiscoverySelectionCheck`). At the link layer this applies only at route cost 0 (above 0 the link peer is a relay and the caller presents a throwaway key); at the end-to-end layer it always applies to the callee. In I_FIRST the same check runs on the responder's block after msg4 and aborts the session before keys are installed (the initiator has already revealed).
3. Verified contacts: the peer's full fingerprint is compared with the verified-contact store; a `MISMATCH` under `REFUSE` closes **before the initiator has revealed anything**, which BMH2 could not do. This protects a prefix collision with a verified contact; for a rotating advert it is the expected-contact rule above that protects against a ground RDI.
4. Relay admission and store-and-forward neighbour rules stay where they are, on the authenticated peer after the handshake returns (a responder learns the initiator in msg3).
5. I_FIRST responder only: the reveal decision; anything but an admitted contact gets a silent close.

**Responder cost guards (SR11, BR5).** A stranger-facing R_FIRST responder signs for every msg1, and one fixed msg1 can be replayed at no cryptographic cost. It therefore (a) keeps a per-process cache of the last 4,096 `SHA-256(e_I)` values (a repeat is a silent close), (b) spends a token from a **signing budget** before it draws a key for a msg1 whose tag did not match: a bucket of 8 signatures refilled one per 4 s of elapsed (monotonic) time, so a wall-clock change neither refills nor stalls it, a caller that finds it empty waits for its token for at most 4 s and otherwise the connection closes silently; the Meet screen's code attempts spend from their own bucket of 3 refilled one per 10 s, so strangers cannot delay a scan and a held code cannot drain the shared bucket (the escalating RV8 tarpit is not used on this path: it would delay every unrecognised caller, contacts without a lease included, by up to 30 s after about eleven attempts per epoch), and (c) stays under the existing pending-connection and admission guards. A matching tag spends no token. In I_FIRST the responder signs only after the initiator authenticated. Keystore signing time on the six phones is measured in T14.

Any failure closes the connection with no error message: there are no alert codes to fingerprint. Local policy is enforced locally whatever the flags say; a flipped flag also changes `TH2`, so the keys differ and the AEAD fails.

### Composition with BMS1, BME1 and relays

- **Link.** The last message yields the session keys exactly where `MeshSessionKeys` are installed today; `BMS1` is unchanged (17-byte header as AAD, sequence nonce, exact-next ordering). The first record still carries what it carries today (hop type 11, 12 or 13, or the end-to-end handshake). The link `BDO1` exchange stays as it is and runs after the handshake; with BMH3 the `OPENING` extension adds the same check before the reveal.
- **Endpoint.** The end-to-end keys become the `BME1` keys of `EndToEndVideoSession` unchanged; `BFG1`, `BGK1`, `BMC2`, labels and fragments are unchanged. The callee's `BDX1` OPENING record and its checks also stay; the extension adds the pre-reveal check.
- **Pipelining.** The phone that sends the last handshake message may write `BMS1`/`BME1` records right behind it in the same write; the other phone reads them only after the final message verified. A responder never sends data after msg2 before the initiator authenticated.
- **Cost.** The responder now learns the initiator one message later than the first hello of BMH2: in R_FIRST the callee rings at the same moment as today, in I_FIRST about two hop round trips later. Bytes: R_FIRST 122 + 431 + 334 = 887 against about 638; I_FIRST 122 + 105 + 334 + 334. Compute per side: one key pair, one ECDH, one signature and one verification (as BMH2), about ten HMACs and one AES-GCM pass over 310 bytes.
- **Call relay.** `BluetoothPrivateCallRelay` copies type-4 and type-5 records in both directions without parsing, so three- or four-message end-to-end handshakes pass through it unchanged. A relay runs BMH3 with each neighbour: as an R_FIRST responder toward its parent and as an initiator toward its child. A middle relay learns neither endpoint. The stream relay harness parses BMH2 endpoint hellos and the blind group harness passes the source hello through group control; both stay BMH2.
- **Contacts-only through stranger relays.** A relay is the callee's link initiator; a Contacts-only callee answers a relay without the tag with I_FIRST and closes on a stranger relay. In v1 a Contacts-only phone is reachable directly or through relays that hold its lease.

### Platform notes

Android: identity signing is the existing Keystore `Signature("SHA256withECDSA")` over the label plus a 32-byte hash (the key authorises only `DIGEST_SHA256` and needs no user authentication); ephemeral keys are software `KeyPairGenerator("EC")`, decoded after an explicit on-curve and `0 <= x, y < p` check. iPhone (CryptoKit): `SecureEnclave.P256.Signing.PrivateKey.signature(for:)` returns the raw 64-byte form, `derRepresentation` is the 91-byte SPKI, `P256.KeyAgreement` rejects off-curve points, `HKDF<SHA256>.extract/expand` and `AES.GCM` match, and the key must be usable after first unlock without a biometric prompt. Windows (CNG): `NCryptSignHash` returns raw `r | s`; `BCryptDeriveKey` with `BCRYPT_KDF_RAW_SECRET` returns the secret little-endian and must be reversed. The Windows receiver and the iOS app stay BMH2 until updated; the iOS repository carries the vectors.

### Security argument and what it does not do

The construction is SIGMA (Krawczyk, CRYPTO 2003; proven in the Canetti-Krawczyk model, EUROCRYPT 2001 and 2002) in both reveal orders, with a TLS 1.3 shaped schedule (RFC 8446: transcript hashes, separate handshake and application secrets, Finished MACs, a role-labelled signature over the transcript hash). Its identity hiding matches Noise XX (Noise specification section 7.8: the initiator's static key "encrypted with forward secrecy to an authenticated party", the responder's to an unauthenticated one) while the Keystore key stays signing-only; Noise's static Diffie-Hellman would need a second static key per identity, and IK additionally needs the responder's key in advance and loses initiator forward secrecy. Properties: mutual authentication and session-key secrecy; no unknown-key-share (the MAC and AEAD keys come from `g^xy`, so an attacker cannot re-sign someone else's block); forward secrecy including of identities; no key-compromise impersonation; no replay across sessions; downgrade resistance inside BMH3 (the offer, flags, tag and purpose are in `TH2`); cross-protocol separation (every signed context starts with a distinct `BluetoothVideoMesh/...` domain that diverges within 19 bytes: BMH2 link and end-to-end hellos, BMH3 per purpose and role, `BNL1` labels, `BCC1` cards). Reflection fails on the AEAD keys and again on the role labels. There is no machine-checked proof; a Tamarin model of both orders is recommended before promotion.

**Not hidden or not solved** (stated, not hedged):

- **Everyone-mode responders reveal their identity to any active attacker that sends a msg1**, once per connection (the signing budget bounds the rate; it does not stop one probe). Hiding it needs prior shared knowledge (Contacts-only, above) or a pseudonymous per-epoch identity for strangers ("Phase 2: pseudonymous stranger identities", experimental, off by default). Until that switch ships on, the public tracking warning stays true for "a stranger can connect". Contacts-only is DEBUG-only in Phase 1; Phase 2 reads real presence leases.
- A sniffer sees message sizes, timing and the order (3 or 4 messages, which for a Contacts-only phone also says per connection whether the caller was a lease holder), the app's service UUID, the hint bit and the `MAY_REVEAL_FIRST` flag (stable bits), and the advertisement itself (the 48-bit prefix, or the RDI). The GAP Device Name and PSM (RV1), bonded devices' resolvable addresses (RV2) and the Classic address are separate leaks. The `BDO1`/`BDX1` record sizes show that rotating IDs are on.
- An adjacent relay learns its neighbours' identities (it authenticates them), except the caller's when the caller presents its throwaway key. A tag-free connection to a Contacts-only phone costs that phone one ECDH, and Keystore signing latency can fingerprint a phone model; a tag match skipping the budget is visible in timing under flood.
- A replayed tagged msg1 inside the same epoch still draws one signature from the true target.
- With BMH2 a sniffer reads the updater's build tag in the clear; with BMH3 it does not.
- Grinding a key with a victim's 48-bit prefix (about 2^48) passes the discovery binding toward a stranger and then receives the initiator's identity; a recognised or verified contact is protected by the expected-contact and fingerprint checks (SR13, BR4).
- A stripped hint downgrades an unpinned initiator to BMH2 for a version 2 advert (SR3, above). Design C helpers and reach-page routes, stream hops, the stream relay and the group harness stay on BMH2 in Phase 1.
- Signature coverage of the first revealer's block makes the exchange non-deniable between the two parties (as TLS 1.3 client authentication); BMH2 hellos were non-deniable and replayable.
- Post-quantum: a recorded handshake could be opened by a future quantum computer; offer bit 1 is reserved for a P-256 + ML-KEM-768 hybrid.

### Phase 2: pseudonymous stranger identities (on by default for user sessions since 0.2.0-beta, `test_bmh3_pseudonyms`)

Settings > Privacy > Advanced privacy "New identity for each stranger" under the BMH3 row (feature id `bmh3_pseudonyms`, a child of `bmh3`, DEBUG extra `test_bmh3_pseudonyms` next to `test_bmh3`; default ON for user sessions since 0.2.0-beta, one constant `ConnectivityFeatureDefaults.BMH3_PSEUDONYMS`; pseudonym phone test: the stranger, decline, restart and contact cases and the snoop check passed, steps 5, 6 and 8 not yet run). Design decision (2026-10-11): a stranger who connects meets a **pseudonym**, never the long-term identity; the long-term identity goes only to a verified contact (recognised through the presence leases and the contact tag) or to the other party of a call the user accepted. Design 2026-10-11, reviewed by an independent reviewer (findings PR1-PR15, adopted and rejected in DECISIONS "Design F"; the text below already contains the adopted changes). It needs BMH3 and rotating discovery IDs on; with the switch off not one byte differs from BMH3 Phase 1. Phase 1 of this feature covers **direct private calls**; **message exchanges and relayed calls with a stranger are refused** (they need a stable identity, below); streams are specified and not built.

**What the engine needed.** BMH3 already signs with whatever `SigningIdentity` it is given and already hides the key from a sniffer. What was missing: (1) a rule for which key a phone presents to whom, (2) a way to prove the real identity later, bound to the session, (3) keeping the salt of a rotating ID (it lets anyone who knows a node ID confirm that the phone owns the ID) from a stranger until the user decided, and (4) closing every other way a stranger could still obtain the real key (review PR1-PR4).

**Which key is presented (rule P).**

| Role | Presents the real key when | Otherwise |
| --- | --- | --- |
| Responder (callee), in msg2 | msg1's contact tag matched one of its own lease keys (the initiator recognised the advert as a contact and holds a lease for that day) | a **connection pseudonym**: a fresh throwaway key for this connection |
| Initiator (caller), in msg3 | it sent a contact tag **and** the responder's verified block was the expected contact's full node ID (the existing check) | a fresh **attempt pseudonym**, the same one at the link and the end-to-end handshake of the attempt |

The initiator decides after it verified msg2, the property of R_FIRST that makes the rule possible: it reveals the real key only to the contact it was looking for. A tag was sent but another key answered (a throwaway, a stranger, a forgery): the existing "not the expected contact" failure, so a user who tapped a contact never silently becomes a stranger call; and an initiator holding a real key refuses a responder that declared a pseudonym. A session is therefore **real-real** (contacts; BMH3 Phase 1 exactly) or **pseudonym-pseudonym**. I_FIRST (Contacts-only responders) is unchanged: the responder answers only an admitted initiator.

**The rule fails closed (PR4).** In pseudonym mode every untagged connection meets a throwaway, whatever else is true: an empty list of pinned adverts (an advert set that stopped while the listener stayed up), a Classic listener, a Visible-by-handle window. Nothing in the rule depends on rotating adverts being on air. Version 2 offers are bound by the reveal as well (the revealed node ID must carry the announced prefix).

**A refused caller fails fast (2026-10-12).** The refusal closes the link without a reply, so the caller sees the link end and its hop handshake fail. An outgoing call attempt that is not covered by the first-attempt stall guard (the 1M retry, an attempt without the guard, Classic) now also has a hop-handshake deadline of 10 s after the link opened (`CallSetupDeadlines.HOP_AUTH_MS`; measured authentication takes 71-269 ms): an answerer that keeps the link open and never answers is closed by the caller, and a link that ends early is reported as "closed the connection before the secure handshake finished"; both messages say the other phone may run an older version or accepts calls only from phones it knows (`call_setup: event=hop_auth_deadline`). The answering phone logs `incoming_handshake: result=failed | reason=<fixed reason>` (for example `bmh2_refused`) next to `bmh3: event=refused_bmh2`. The earlier prober call that waited 170 s in OUTGOING lacked this bound.

**BMH2 is refused (PR1).** An Everyone-mode listener accepts BMH2 in BMH3 Phase 1 because "a prober can obtain the identity through BMH3 anyway". With pseudonyms that reason is gone, and a BMH2 hello is answered with the real key. A phone in pseudonym mode therefore closes silently on a BMH2 first message at both layers (as a Contacts-only phone already does) and never speaks BMH2 itself (a caller's BMH2 hello would hand its real key to whoever answers, before any ring), and it cannot be reached by or reach phones that speak only BMH2 (BMH3 switched off, older builds, Design C helpers, the DEBUG relay). This is the price of the claim; the switch says so.

**Pseudonym keys.** A pseudonym is a software ECDSA-P256 key (`KeyPairSigningIdentity`), never in the Keystore, never persisted, never exported, dropped with its connection. The responder uses a new key **per connection** and the caller one **per attempt** (PR7). An epoch-wide key was considered for continuity (a redial reaches the same endpoint) and rejected: the advertised RDI already shows that, an epoch key would make one accepted reveal attribute every session of the epoch (a reveal is a transferable signature that the real key owns the throwaway) and would tie the call roles together. Nothing derives a pseudonym from the node ID, a lease key or another pseudonym (fresh CSPRNG output). The node ID of a pseudonym is `SHA-256(SPKI)[0:16]` like any other, which no code path can tell apart except through the extension below.

**Extension 4 `PSEUDONYM`.** Value empty (length 0), allowed in either block of either purpose, at most once, below `0x80` (an older BMH3 build skips it and treats the key as an identity). Meaning: *the key in this block is a throwaway; the sender expects the peer never to store it as an identity, and the sender speaks the `REVEAL` record below.* It sits inside the encrypted and signed block, so a sniffer cannot see it and nobody can add or strip it. The receiver of a block with `PSEUDONYM` does not run `PeerIdentityGate.admit` on that key (a pseudonym is not an authenticated *person*; admitting it would only fill the 1,024-entry memory of authenticated peers with throwaways), does not pin its prefix, does not look it up in the verified-contact store and shows no node ID or fingerprint. A block that carries both `OPENING` and `PSEUDONYM` fails the handshake. The area has room for it beside two opening entries, an `INTENT` and a `BUILD_TAG` (99 + 3 bytes, a PAD of at least 3).

**What the pseudonymous responder withholds (the confirmation oracle).** A rotating ID `RDI = H(nodeId, e, r, salt)[0:6]` plus its `salt` lets anyone who guesses the node ID (a public key shown on a poster or in a QR) confirm that this phone owns the ID. BMH3 Phase 1 hands the salt to every connecting stranger in the `OPENING` extension, in `BDO1` and in the first `BDX1` record, harmless there because the handshake has just revealed the node ID anyway. A pseudonymous responder therefore (a) puts **no `OPENING`** in its block, (b) clears **link-hello capability bit 3** in its link block (so neither side expects a `BDO1`; the endpoint block keeps bit 3, because the reveal uses the `BDX1` content type), and (c) sends **no `BDX1` OPENING** when the `INVITE` arrives. The salt leaves the phone only inside its `REVEAL`. A pseudonymous *initiator* keeps link bit 3, so a responder that answered it with its real key (pseudonyms off) exchanges `BDO1` as usual; a responder skips the link opening only when it presented a throwaway itself (2026-10-27; it used to skip for a throwaway initiator too, while the initiator waited for the opening, which broke a direct call from a pseudonym caller to a phone with pseudonyms off). **Classic:** a Classic caller accepts a throwaway link peer only from a candidate address that is the advertiser itself (learned from an earlier real-key link, bonded, or a DEBUG override) and then does not compare it with the announced prefix (the reveal binds it, as for a version 2 offer on LE); a throwaway answer from a guessed address (a bonded fallback, the discovered or an inquiry address) fails that candidate, because nothing would show which phone rang. Bond-free Classic calls to a pseudonymous stranger are therefore not supported. No address is learned for a throwaway, and a learned address is forgotten only when a real key proved it belongs to someone else.

**`REVEAL` (BDX1 kind 4, end-to-end content type 11, only after both endpoint blocks carried bit 3).**

```text
"BDX1" | kind 4 | role (1: caller, 2: callee) | SPKI length (2) = 91 | SPKI (91) | opening count (1, 0..2; 0 for the caller)
       | count x entry (43) | signature (64)
K    = HKDF-Expand(EXP, "BluetoothVideoMesh/BMH3/Reveal/1 key", 32)
TH_R = SHA-256(D_R | 0x00 | role | K | SHA-256(own pseudonym SPKI) | SHA-256(peer pseudonym SPKI) | SPKI | prior | count | entries)
sig  = ECDSA-P256-SHA256(real key, D_R "/" Role " signature" 0x00 TH_R)           D_R = "BluetoothVideoMesh/BMH3/Reveal/1"
prior = empty in the callee's reveal, SHA-256(the callee's reveal record) in the caller's
```

`EXP` is the end-to-end handshake's 32-byte exporter (a secret both ends derive from the whole transcript, which contains both pseudonym keys); the exporter itself is never signed, only a key derived from it (PR13). Both pseudonym hashes state which two throwaways the real key claims to speak for, `role` and the role label stop a reveal being replayed in the other direction, and `prior` makes the caller's reveal commit to the exact callee record it verified. A reveal recorded from another session, or forwarded by a man in the middle that terminated both sessions, fails on `K`; only the holder of the real key can sign one. At most one reveal is accepted per direction per session; a reveal from a peer that did not declare `PSEUDONYM`, a second one, a wrong role, a wrong length, more than two opening entries, an `OPENING` entry on a caller reveal or a non-canonical SPKI is a protocol error that ends the call (the rest of BDX1 is lenient because it never fails a call; a reveal decides whether the call continues).

**When the reveal happens (calls).**

1. Handshake: both ends are pseudonyms (rule P). The callee's phone rings as an **unverified stranger**: no node ID, no fingerprint, no name (the caller's name label is held until step 3, PR6, so a fake or copied advert collects nothing). Nothing about the callee's real identity has left its phone; declining reveals nothing except that a phone answered the advert.
2. The callee's user accepts: the callee queues its `REVEAL` (role 2, with its pinned opening entries) **before** the `ACCEPT` signal in the same ordered control queue, then its name label. The signature is made on the writer thread, not on the Accept tap.
3. The caller checks, in this order: signature and key binding; `PeerIdentityGate.admit(realNode, realSpki)` (a verified contact's prefix with a different key is `MISMATCH` and ends the call before the caller reveals anything); the discovery binding of the **selected** offer against the revealed node ID and the revealed entries (`DiscoverySelectionCheck`, the check BMH3 Phase 1 ran before the caller revealed; a version 2 offer is checked against the announced prefix); a direct call must also have reached the same throwaway at the link and the end-to-end handshake. Any failure ends the call with "Call peer identity changed between discovery and connection", and so does an `ACCEPT` that arrives before a verified reveal. Only then does the caller queue its own `REVEAL` (role 1, no entries) and its name.
4. The callee, on `REVEAL` role 1, checks signature, binding and `admit`; a role 1 reveal before its own role 2 was sent is an error. A `MISMATCH` ends the call. **The caller's reveal is required (2026-10-27):** a callee that sent its own reveal to a caller that declared `PSEUDONYM` refuses the caller's media (a stream header or media record before the verified reveal ends the call), **holds its own stream header, camera and microphone** until that reveal verified, and hangs up when the reveal has not verified 10 s after Accept. A relayed call gets 10 s more per relay hop the Invite states (at least one, at most three, so at most 40 s); a direct call (the authenticated link peer is the call peer) gets no extra time whatever the Invite claims, and a caller that overstates its hops gains only time in which it receives nothing. A reveal the writer had not flushed when a link renewal replaced the link is sent again as the same bytes, and a receiver ignores a byte-identical repeat of the reveal it already verified (any other second reveal is still an error). An honest caller sends its reveal right after it verified the callee's, ahead of its stream header in the same ordered queue, so it never meets this rule; before, a caller could stay a throwaway for the whole call.
   **Blocked people (2026-10-27).** Both phones check the revealed fingerprint against their own block list before anything else goes to that person. From then on nothing more goes to that person (no media, no label, no presence session, and for a caller no reveal of its own), and after the same human-like delay as a blocked call's decline (3 to 7 s) the phone ends the call with the ordinary hang-up (a caller: the ordinary cancel). A callee records a "Blocked call" that names nobody. A blocked callee never learns the caller's real identity, but a name the caller set may already have reached it before the ring (names before answer). No presence lease is offered to a blocked person, blocking a contact that holds a lease of the current generation starts a new generation (also for a block made while rotating IDs were off, at the next start with them on), and a blocked person gets no relay service, no stream (as a viewer or through a forwarding phone) and no message exchange.
5. Both phones now replace the throwaway by the real identity for everything about the person: the displayed label, the verified-contact lookup, the safety code and QR verification (the fingerprint recorded by `admit` is what `IdentityVerification` compares), the recent-calls entry, and the presence-lease session, which is created now instead of at the handshake. The **link** stays on the throwaway; labels stay bound to the endpoint key they were signed with.

**Accepting a call from an unverified stranger tells the caller who you are; declining, or letting it ring out, tells nothing. Calling a stranger shows whoever answers who you are.** The binding in step 3 protects the caller (a fake or copied advert cannot produce a reveal that opens the selected ID), not the callee: the callee reveals to whoever holds the session and whatever name that caller claims (a claimed name is unauthenticated and can be a social-engineering lure, PR9). There is no "answer without revealing": the caller cannot tell the owner of the advert from an impostor without the reveal, so such a mode would have to let the caller accept an unbound callee (a later, explicit user choice).

**Message exchanges and relays (refused with a stranger, PR2, PR8).** A store-and-forward exchange needs a stable identity on both ends: its hello sends the phone's contact card (the real SPKI and mailbox key) to anyone who opens a link, offers are keyed on the link identity, bundle IDs and tags stay the same for up to 14 days (they would link epochs), and per-neighbour limits would be keyed on throwaways. In pseudonym mode a link with a stranger therefore carries **no exchange and no relay request**: the listener closes on a first record of those types from a pseudonymous link (either side), and an exchange initiator that meets or presents a throwaway stops. Contacts (real-real through the lease tag path) still exchange as in BMH3 Phase 1. Relayed calls to a phone in pseudonym mode fail closed: a DEBUG call relay presents its real key as the initiator toward the callee's link and meets a throwaway, which an initiator holding a real key refuses; the end-to-end layer through a relay would work, the link layer toward the callee does not in Phase 1 (a later version can let a relay present a throwaway of its own and skip the link opening). Design C helpers and reach-page routes were on BMH2 and therefore unreachable until Amendment CP (relay edges below "Experimental relayed calls"), which lets a pseudonymous link carry one `SETUP`; message exchanges with a stranger stay refused.

**Presence lease eligibility and its log (2026-10-12).** The OFFER of a call is sent only when the vault is loaded (a load that failed once is retried, not judged from its first miss), the peer's real identity is a verified contact, and the per-contact switch is on; the identity is the revealed one after a pseudonym call's reveal, never the throwaway. Otherwise nothing is sent and the phone logs `rotid_presence: event=ineligible | reason=` at session creation or `event=offer_withheld | reason=` at send time, with the fixed reasons `no_vault`, `vault_not_persistent`, `no_contact_store`, `peer_unverified`, `peer_mismatch`, `peer_store_unreadable`, `contact_switch_off`. The exchange needs the verification on **both** phones: each phone checks only its own store, so a one-sided verification makes the unverified side withhold and no lease moves.

**Real lease keys (replaces the DEBUG fixed lease for the app's own phones).** The initiator's tag: `RotatingDiscovery.recognize(selected)` returns exactly one hit and the vault holds that contact's lease for `dayOf(hit.epoch)`; `K_tag = contactTagKey(lease)`, binding = RDI, role 0; `expectedPeer = hit.contact`; no tag where the answerer is not the advert's owner (the link toward a relay). Zero or several hits: no tag. The responder's checks: for each call-offer entry pinned at accept, `PresenceVault.dayKey(entry.epoch, E)` gives that entry's `L_d`; the check is (`contactTagKey(L_d)`, `advertBinding(entry.rdi, 0, null)`) and the key copy is zeroed after use. `test_bmh3_test_lease` still overrides both for phone tests. With a tag that matched, `admitInitiator` requires the initiator to be a contact the vault **delivered a lease to** in the current generation; a tagged connection from anyone else means a lease reached someone unintended: the connection is closed and `bmh3: event=lease_misuse` is logged. This is best-effort detection (PR11): a holder of a leaked lease reads the real key from msg2 and may disconnect before msg3, and no automatic new generation is started (a false positive after a lost record would break every contact's recognition), so revocation stays the user's "Reset presence key".

**Streams (specified, not built).** A stream source is public by nature, but its owner is not: once streams run on BMH3, a source presents a **per-stream pseudonym** to every viewer that is not a contact (not the call keys, which would tie the roles together, and not an epoch key, which would break the forwarders' source-node grant when it changed mid-stream, PR7), with no reveal at all (a stream has no accept moment, and a viewer count is not consent). A source may attach a *stream title* label signed by the pseudonym; that is the only thing that identifies it. Becoming a contact needs a *mutual* verification (a one-sided QR scan gives no lease), after which the tag path returns the real key. Until streams move to BMH3, a stream source answers BMH2 and reveals its real key to every viewer; the tracking warning therefore stays true for **stream sources**.

**Verification, mismatch and pinning.** A verified contact that calls with an expired lease arrives as a stranger and is recognised by the reveal (`admit` marks it; the next presence-lease exchange repairs recognition). A pseudonymous peer cannot be verified before it revealed; the in-call Verify button says so, and after the reveal the existing QR and safety-code flows work unchanged. Verification pins the real key (the verified-contact store); nothing pins a pseudonym. The prefix `MISMATCH` rule runs on the real key at the reveal and for contacts at the handshake (the expected-contact full node ID, before the caller reveals); since 2026-10-27 also on a real-key answerer of a direct **link** handshake, in the initiator's check before its msg3, so a mismatching link peer is closed before this phone presents its real key at the link. The BMH3 prefix pins (30 days) store a prefix only for an answerer that proved a real identity.

**Abuse and limits.** Pseudonyms are free to mint, so nothing may be limited per pseudonym. The limits are global and per connection, and the state a stranger can observe is scoped so that it cannot bridge a boundary (PR3): the replay cache (4,096 entries) and the signing budget (8 tokens, one per 4 s) of stranger-facing responders belong to the discovery epoch and are dropped two epochs later. With one process-wide cache a prober could replay one msg1 to every candidate RDI after a boundary and read "same phone" from the silent close, and a budget drained just before the boundary would carry over the same way. The pending-connection and admission guards and the ring limits stay as they are; a stranger who rings repeatedly is handled by declining (there is no per-pseudonym block list; the next connection is a new pseudonym by design). A `REVEAL` costs one ECDSA verification per direction per session, only after a user accepted or a verified callee answered.

**Downgrade and active attackers.** A fake or replayed advert gets the caller's per-attempt pseudonym and nothing else: the caller reveals only after a reveal whose signature binds the session and whose key opens the selected RDI, which needs the owner's key (forging the 48-bit RDI binding for an attacker-owned key costs about 2^48 hashes per epoch, the RV9 bound). A prober that connects to a stranger-mode phone gets a throwaway and a ring; it cannot obtain the salt, the node ID or any signature of the real key, on BMH3 or (because it is refused) BMH2. The attacker cannot make a phone present its real key (the tag is an HMAC under lease keys bound to the advert and msg1), cannot strip `PSEUDONYM` (inside the signed block) and cannot replay a reveal. A man in the middle that terminates both sessions can ring the callee and, if the user accepts, learns the real identity (consent), but cannot make the real caller accept it as the callee: the reveal it forwards fails on the other session. Interoperability: a BMH3-on, pseudonyms-unaware caller cannot call a phone in pseudonym mode (its real key is refused by the engine and its own pre-reveal check cannot pass); a pseudonymous caller to an older BMH3 responder gets a real key and a normal opening, stays pseudonymous and sends no `REVEAL` (an older peer did not declare `PSEUDONYM`, so it cannot parse one); a phone without BMH3 cannot connect at all while pseudonym mode is on.

**What a stranger can still link or learn (the honest list, PR15).**

1. Accepting a call from a stranger shows them who you are; calling a stranger shows whoever answers who you are.
2. Someone who can see you can ring nearby phones and watch whose reacts. Holding a connection across the 15-minute change (a connection stops the advert) lets a prober choose when your next ID appears, which can link the old and the new ID in a small crowd; a random reopen delay and a "silent for strangers" mode are future work.
3. Within one epoch, your advert (RDI, and the address when it does not change) and every connection are the same phone.
4. Anyone who connects learns the phone class (capability bytes: codec masks, bitrate ceiling, transport mask and feature bits such as labels, fragments, voice, dual, relay), the app build (the build tag, while the updater switch is on) and the BMH3 timing; these repeat across epochs.
5. Bluetooth leaks outside this protocol: the GAP device name on Android 13 and older and on some chips (unless the neutral name is on), the Database Hash, link-layer features, the fixed PSM on Android 10, Classic Bluetooth (fixed prefix, permanent address), OS beacons, bonded devices' resolvable addresses.
6. Streams you broadcast (until streams move to BMH3) and a Visible-by-handle window are identifiable or linkable.
7. Contacts who hold your leases, or anyone who takes their phone, recognise you for up to four weeks; a display name you set goes to every caller you call.
8. Keystore signing latency separates a real-key answer from a throwaway answer (a lease holder sees it; so can a sniffer who evicts the replay cache of the current epoch and replays a sniffed tagged msg1, PR14, which also shows that a sniffed caller is a contact of the target).

**Debug lines (no identifiers in release builds):** `bmh3: event=present | layer=link|endpoint | role | key=real|pseudonym | reason=stranger|contact|tag`, `bmh3: event=reveal | role=caller|callee | result=sent|verified|<failure class>`, `bmh3: event=lease_misuse`, `bmh3: event=peer | layer=endpoint | pseudonymous=` (DEBUG builds add `peer4=`, the first four bytes of the node ID the peer presented, so the phone test can compare throwaways across connections; release builds never log it).

## Emergency wipe

`EmergencyWipe.panic(context)` (no confirmation, bound by the UI to an in-app gesture such as a triple-tap) and `EmergencyWipe.wipeConfirmed(context, "DELETE")` (the word the user types, `EmergencyWipe.CONFIRMATION_TEXT`) run one synchronous, single-flight sequence on a worker thread; a concurrent or re-entrant call returns `alreadyRunning`.

1. **Stop admission.** No new end-to-end session is admitted and no Keystore key is created (identity, store-and-forward, verification) for the rest of the process.
2. **Pending marker.** `noBackupFilesDir/emergency-wipe-pending` is written and synced.
3. **Keys first.** Every Android Keystore alias of the app is deleted, so data sealed under them (store-and-forward messages and metadata, the software mailbox key, verified contacts) becomes unreadable even if the wipe is interrupted.
4. **Sessions.** The registered owner ends every call, stream, relay and discovery on the main thread (best-effort hang-up first). The wipe waits for it at most 2.5 s and never runs it unbounded on its own thread.
5. **Data.** Every SharedPreferences file (settings and learned link, rate, PHY, encoder and group-epoch memories) is cleared and deleted. The contents of the app data directory (files, `no_backup` with store-and-forward outbox/inbox/courier data, verified contacts and learned Classic addresses, cache, databases) are deleted, except the native library link, ART code cache and the marker. So are the app's external files and cache (benchmark traces and media).
6. **Second sweep.** In-memory caches are dropped, then the Keystore, preferences and files are swept again for late writers. The report is `complete` only when that final sweep leaves nothing.
7. **Finish.** Every app notification is cancelled (call alerts carry the caller's label; also once right after the sessions end). The marker is removed only when complete. One line is logged (`EMERGENCY_WIPE reason=... | complete=... | alreadyRunning=... | durationMs=...`, no identifiers or secrets), and the process ends.

On the next launch, a remaining marker makes MainActivity resume the wipe before any transport, key or store opens. If it still cannot complete (for example the Keystore keeps failing or storage is read-only), a minimal "Wipe incomplete" screen replaces the app. It has Retry and an App info link (clearing storage there finishes the wipe), and starts nothing; the app never closes silently. After a complete wipe, the next launch creates a new identity, so peers see a new node ID.

No intent reaches the panic or confirmed wipe. DEBUG builds alone accept `--es test_emergency_wipe <token>` on launch or new intent, and only when `<token>` (32-128 lowercase hex) equals the one-shot file `files/debug-emergency-wipe-token`. Write it with `adb shell run-as <package>` (debuggable builds only; internal storage, because on Android 10 legacy storage another app with the storage permission could write external app files). The debug wipe also deletes benchmark inputs in the app's external files.

A wipe cannot guarantee:

- **Flash remanence.** File deletion on flash storage does not overwrite cells; wear levelling and TRIM timing decide when blocks are erased. Files sealed under Keystore keys rely on key deletion instead, which is as strong as the device's Keystore deletion (strongest with StrongBox or rollback-resistant keys). Learned memories, settings, traces and media are plain files and may be recoverable forensically until the blocks are reused.
- **Copies outside the app.** adb backups or device-to-device transfers made earlier, screenshots, the system logcat buffer (which an app cannot clear), recordings saved to shared storage, the system's Bluetooth bond list and cached device names, and anything a peer stored (their verified-contact entry, received messages, carried bundles) are untouched.
- **A running attacker.** Malware or a debugger already on the phone can copy keys or data before the wipe. A phone that is powered off or seized before the wipe is triggered is not wiped.
- **Interruption.** Power loss mid-wipe leaves later steps undone until the next launch resumes them; keys go first to limit that window.

## Confidentiality and failure boundaries

A relay sees adjacent identities/capabilities, signed public endpoint hellos, record direction/size/timing, endpoint type/sequence/flags and its own local queue/drop information. Record timing and size remain traffic metadata.

A blind relay cannot open video geometry/FPS/rotation/audio headers, compressed VP9/AV1/Opus data, media timestamps, keyframe-request payload, wrapped group keys or group-sealed media. A normal viewer-forwarder can decrypt because it is an admitted local viewer; its forwarding branch still copies ciphertext unchanged.

Modified ciphertext/header metadata, replay, reordering, invalid signatures, wrong handshake domains and wrong recipient keys fail closed. Cryptographic identity does not establish human ownership. Full-fingerprint verification (above) is local and opt-in per contact; TOFU pinning of unverified peers, dynamic audience revocation/re-key, larger alternate-path proof and independent security audit remain open. Open/approval/verified audience modes would change admission, not remove hop/content encryption. Current primitives do not constitute independent protocol certification.
