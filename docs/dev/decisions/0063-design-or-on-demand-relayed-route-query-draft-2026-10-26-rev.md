# Design OR: on-demand relayed route query (draft 2026-10-26, revision 3 after reviews 1 and 2, DEBUG prototype only)

**Status.** Revision 3. Review 1 (independent, static, on the first draft) asked for a redesign before implementation while keeping the authenticated, bounded, on-demand depth-first search; two independent reviews of revision 2 approved it with changes for a default-off DEBUG prototype, with no P1 finding. Revision 3 adopts those changes (the tables "Review 1" and "Review 2" at the end). It adds a hop-record message and a BMH3 handshake extension and changes when helpers scan, so it exists only behind DEBUG launch extras that are off by default; with them off every byte on air and on the link is unchanged. A release or user-facing setting needs OR-T, a further review and a design decision. Wire draft: PROTOCOL "Experimental relayed calls and multi-hop discovery", subsection "Draft: on-demand route seek (Design OR)".

**Question.** Design C finds relayed routes proactively: every helper scans all the time, keeps a reach table and advertises reach pages (a distance vector: cost + 1, two entries per page, one page per second, entries dropped after 30 s without a refresh), so a caller already knows a route when the user taps Call. Could routes instead be found only when the user taps Call on a contact, with no background tables or pages, and what would that cost in time, battery, privacy and safety?

**What the proactive arm costs today.**

- *Battery.* Each idle helper runs a continuous scan (AOSP default windows: balanced 183 ms every 730 ms, 25 % receiver duty, while the screen is on or the phone charges; low power 140/1400 ms, 10 %, or 512/10240 ms, 5 %, with the screen off; the stack may change the effective mode with app state and connections), a second advertising set at 250 ms, and a host wake-up for every neighbour page and offer it hears. A plain call-ready phone does none of this. The per-hour cost is an unmeasured gate (Design C, C5).
- *Time.* Measured: 3-8 s from tap to ringing when helpers already know a route; about 12-20 s (one relay) and 25-35 s (two relays) from cold. Cold is common: an entry needs two sightings 2 s apart, a learned entry is advertised only after 5 s, pages rotate at one per second, and with rotating IDs every table flushes at each 15-minute boundary, leaving relayed reach empty for up to about 30 s per hop. In one room two helpers never formed a route by themselves (topology masks were needed).
- *Exposure.* Reach pages put a bounded subset of consenting targets' current IDs (at most four per helper) on air all day, whether or not anyone calls.

**How other systems discover routes (sources).**

| System | Discovery | What MeshLive takes from it |
| --- | --- | --- |
| AODV (IETF RFC 3561) | Reactive: a route request (RREQ) is flooded with a TTL and an expanding-ring search (section 6.4); the destination or a node with a fresh route unicasts a route reply (RREP) back; routes are cached with a lifetime; requests are rate limited (`RREQ_RATELIMIT`, 10 per second). | Search only when asked; keep only a short-lived route memory; rate-limit requests. |
| DSR (IETF RFC 4728) | Reactive: the request accumulates the path; the source caches complete routes and chooses among them. | The caller, not the network, chooses which first hop to try next. |
| Bluetooth Mesh Protocol 1.1, directed forwarding (Bluetooth SIG) | Path discovery on demand (Path Request flooded among directed-forwarding relays, Path Reply returned along the path), added on top of the managed flooding of Mesh 1.0 to cut its interference and energy cost; every node shares a network key. | On-demand paths save radio time; per-hop authentication by a shared network key does not exist here (MeshLive authenticates each link by identity). |
| Meshtastic 2.6 (managed flooding, next-hop routing for direct messages) | Floods first, learns the next hop from the reply, falls back to flooding per hop; backward compatible, so a mesh can be updated in part. | Per-hop fallback and mixed-version tolerance. |
| Bitchat (whitepaper) | TTL 7 flooding with a seen-set; signed announcements carrying up to 10 neighbour IDs give each node a 60 s topology map; source routing when a confirmed path exists, flooding otherwise; stable peer IDs (rotation is listed as future work). | A topology map is proactive state on air; flooding exposes every request. Not adopted. |
| Briar (Bramble protocols) | No multi-hop discovery: a device syncs only with its own contacts over Bluetooth, Wi-Fi or Tor. | The privacy floor: nothing about a contact is broadcast to strangers. |

The reactive protocols all **flood** the request. That conflicts with the hop-local rule (a phone acts on a broadcast it did not receive from a neighbour it authenticated), cannot be authenticated per hop without a shared network key, and makes every query visible to passive scanners. This design keeps the reactive idea (search only on a tap, remember briefly) and replaces the flood with a **depth-first search over authenticated hop links**, hard-capped at two relays.

**Options considered.**

**Scope of the first experiment (OR-1).** DEBUG launch extras only: no release or Advanced setting exists until OR-T (below) is designed, reviewed and the user has decided whether holding a current ID is enough authority to search.

- Every participant runs relayed calls, rotating IDs and BMH3. Targets are **version 5 (rotating) call offers only** (fixed-prefix targets would make the search an oracle forever, see Privacy); compact (iPhone) offers are excluded until they can carry consent.
- **Link identities follow Design C's Amendment CP.** With `test_relayed_pseudonymous_edges` on, every relay edge runs BMH3 with a fresh per-link throwaway that declares `PSEUDONYM` on the initiator side and the connection pseudonym on the responder side, a pseudonymous link may carry exactly one relay request, and the target is authenticated only end to end; OR adds nothing to those rules and works with pseudonyms on. With it off, the rev 2 table below applies, and helpers and targets must have pseudonyms off (a phone with pseudonyms on then neither helps, pause reason "pseudonymous toward strangers", nor is sought). The **caller's** own pseudonym setting is never restricted: its link edge is always a throwaway and its end-to-end handshake uses the contact tag.
- A Contacts-only phone answers an untagged initiator with I_FIRST and closes; helpers send no contact tag, so a Contacts-only phone neither helps nor can be reached through a helper.
- The helper's onward links (to the next helper or the target) run BMH3, never BMH2. This is the same change CP makes for SETUP routes; OR uses CP's implementation when it lands rather than a second one.

**Handshake and admission on each link with CP off.**

| Link | Initiator presents | Responder presents | Binding checked | Admission |
| --- | --- | --- | --- | --- |
| Caller to first helper | a fresh throwaway, random tag | the helper's real key, `OPENING`, `RELAY_SEEK` | the `OPENING` opens the helper offer the caller selected (Design C CR2) | the helper's phone-wide budgets; no per-identity limit (a throwaway is free) |
| Helper to next helper | the helper's real key, random tag | as above | the `OPENING` opens the helper offer selected from the scan | as above |
| Last helper to target | the helper's real key, random tag | the target's real key and `OPENING` | the `OPENING` opens the sought ID | the target's relayed-call admission and its current consent |
| Caller to target, end to end | the caller's real key, contact tag bound to the sought ID | the target's real key | the expected contact's full node ID, then the `BDX1` opening of the sought ID | ring rules |

With CP on, the three link rows become CP's throwaway-to-pseudonym edges (no hop binding); the end-to-end row is unchanged. The caller dials a helper's **own** cost-0 offer, which `Bmh3Policy`'s relay rule (route cost above 0) would not treat as a relay; the implementation therefore passes an explicit "toward a helper" flag, so the caller presents a throwaway and never the contact tag on that link.

What a helper learns about identities: with BMH3 a middle helper learns neither endpoint (the caller shows it a throwaway and the end-to-end handshake is sealed). The **last** helper learns the target's real key at its own link when CP is off (an Everyone-mode responder reveals it to any initiator), and only a connection pseudonym when CP is on.

**Capability.** A helper that would accept a search now signs the BMH3 extension type 5 `RELAY_SEEK` (non-critical; value one byte, a feature bitmask: bit 0 = `SEEK` version 1; bit 1 reserved for OR-T; bit 2 reserved for OR-C) in its responder link block, pseudonymous or not; it is registered as a draft row in PROTOCOL's BMH3 extension table. The caller and every helper send `SEEK` only to a peer whose authenticated block has bit 0; an older BMH3 build skips the extension and is never asked; a BMH2 link never carries it. A helper whose budgets are exhausted stops signing it on new handshakes at once, and if exhaustion lasts more than 60 s its next offer restart omits `FLAG_RELAY_CAPABLE` until the budgets recover.

**The search (OR-B within OR-1).**

1. **Helpers in on-demand mode** run no table scan and no reach pages; their own cost-0 call offer keeps the consent bit and `FLAG_RELAY_CAPABLE`, and the helper pause rules (`RelayHelperPolicy`) are unchanged. An idle helper costs what any call-ready phone costs.
2. **Selectors.** A request names exactly one target ID, blinded as one 6-byte token with a fresh 8-byte nonce, so the caller knows which ID a `READY` reached and binds its end-to-end contact tag to it (`READY` is unchanged). The **primary** selector is the contact's role-0 RDI for the epoch of a direct recognition in the current epoch, else for the centre `myE + skew` of the existing recognition policy (`RecognitionTable`: only days whose key the lease holds, nothing after revocation or pruning). The **neighbour** selector (the adjacent epoch on the side of the nearer boundary) is used only inside the boundary window: within 120 s of the target's predicted boundary. A contact whose lease is older than 14 days (recognition widens to `[-8, +8]` epochs for it) gets the primary selector only; a contact whose skew drifted further is not found by search until a fresh lease (stated limit).
3. **One give-up time.** The caller's attempt ends 45 s after the tap, the same `RELAYED_CONTACT_WAIT_MS` the proactive arm uses for a contact call, so both arms answer "Can't find" at the same moment.
4. **The caller's own duty.** From the tap until its attempt ends, the caller holds its own phone-wide relay-duty reservation: it refuses every request (`FAIL` busy), stops signing `RELAY_SEEK`, and its helper flags are withdrawn at its next offer restart. No path can therefore loop through the caller, even when CP's fresh throwaways make node-ID loop checks impossible.
5. **Direct check in parallel.** If the contact's own offer is heard, the caller calls directly as today. Otherwise it keeps a low-latency scan running while it searches; the moment the contact's offer appears before a `READY`, it closes the search link and calls directly.
6. **First hops.** Version 5 helper offers from the caller's own scan (`FLAG_RELAY_CAPABLE`, the call's bearer), ordered by the helper that last reached this contact in the epoch, then by signal (knob below); at most `N` = 3. Every candidate is revalidated at dial time: an offer older than 10 s is refreshed by a scan of at most 1 s charged to the attempt, or skipped.
7. **Expanding rings.** The caller walks the same ordered list of first hops in rings and stops at the first `READY`:
   - ring 1: budget 1, primary selector, to each first hop;
   - ring 1b (only inside the boundary window): budget 1, neighbour selector, to each first hop;
   - ring 2 (only when the relay cap is 2): budget 2, primary selector, to each first hop, carrying a skip list of the first two bytes of the RDIs of the first hops that answered "no route" in ring 1, so a first hop does not choose a sibling the caller already asked.
   A first hop that answered busy or refused, failed its identity binding, lacked `RELAY_SEEK` or closed without an answer is not asked again in this attempt. A request is sent only if its allowance after the expected connection time (DEBUG tunable, default 4 s) is at least the minimum for its budget: 9 s for budget 1 (1 s of scan, 6 s for the onward link, 2 s of grace) and 14 s for budget 2 (adding 1 s of scan and 4 s to reach a child). `remaining = min(20 s, attempt end - now - 2 s)`.
8. **Helper on `SEEK`.** It takes the phone-wide relay-duty reservation atomically (covering searching, connecting, waiting, relaying and teardown; released only after both links close), checks the budgets (resource envelope below), and fixes one monotonic deadline `D` from the request's remaining time, shortened to what its duty budget has left (if that is below the minimum for the budget it answers refused). Every later step uses what is left of `D`; a parent that closes cancels everything below at once; reply grace never starts new work.
   - *Opportunistic cache.* Offers it heard in the last 5 s from any scan it ran anyway count; a fresh match skips the on-demand scan.
   - *Scan.* Otherwise one low-latency scan of at most 3 s, shortened so that the onward minimum still fits. It does not stop at the first match: it keeps collecting for at most 1 s after the first matching address, up to 3 distinct advertiser addresses with the matching ID (heard twice first, then strongest), and records up to `F` = 2 version 5 helper offers on the same bearer that are not itself and not on the skip list. If its own current or previous ID matches, it treats that as no match (`FAIL` no route; it never reveals that it is the target, and its previous ID is never confirmed).
   - *Target.* It dials the collected addresses in order; with CP off the `OPENING` must open the sought ID, and an identity failure moves to the next address. With CP on there is no hop binding: the first address that completes the handshake is used, and a copied offer can make the search fail end to end (liveness, not safety).
   - *Children (budget 2, no target reached).* For each recorded helper, revalidated at dial time like the caller's first hops, and only if `D - now - expected connection` is at least the budget 1 minimum: a regenerated `SEEK` with budget 1, a new setup ID, the same nonce and token, the same skip list and `D - now - 1 s`. Any child failure (no route, busy, refused, timeout, identity failure, no `RELAY_SEEK`, a close) moves to the next child. When none is left the helper answers `FAIL` no route if no child was reached or any child answered no route, timeout if its deadline ran out, otherwise the last child's reason.
   - Every physical attempt (a dial, a PHY or transport retry, an alternate address) counts against a per-request cap of 3 dials and against the phone-wide budgets.
9. **Short memory, never on air.** The caller remembers "helper X reached contact C" until the epoch ends and "helper X found no route for selector S" for 60 s; after "Can't find C" it backs off its automatic retries for C (30 s, doubling to 120 s, reset when C is heard directly or a new helper appears); a user's tap is never blocked by the backoff ("Who carries the risk"). A helper keeps its scan result for 10 s (so a ring 2 request can reuse its ring 1 helper list) and nothing else. Nothing is persisted, advertised or logged in release builds.
10. **After `READY` nothing changes:** opaque relay, the caller's end-to-end check, the 10 s / 20 s chain deadlines, the 60 s ringing cap, one relayed call per helper, the relayed video cap.
11. **Target-side consent (also proposed for Design C's SETUP routes).** The consent bit is an unauthenticated advert field; an opening proves the ID, not the bit. A target therefore closes, unanswered, a first end-to-end handshake record that arrives over a link whose peer signed the call-relay mark unless relayed calls are on and its current "Let phones nearby relay calls to me" setting is on, whatever its last advert said, so no identity leaves it; as a second check it declines before ringing any call that turns out to be relayed (its authenticated link peer differs from its authenticated call peer) under the same condition. "Help calls nearby" stays a separate switch.

**Why this is hop-local.** Each phone acts only on a record from its authenticated parent and on its own scan; each request is regenerated per hop with a new setup ID, a smaller budget and a shorter deadline, as SETUP is; nothing is broadcast. The blinded token, nonce and skip list travel unchanged, the same stretch Design C accepts for the target ID in SETUP. Termination follows from the strictly decreasing budget; no phone appears twice on a path because the relay-duty reservation is phone-wide on every helper and on the caller (a phone on duty refuses a second request), which also covers CP's throwaway links where node IDs cannot be compared.

**Work bound.** Hard cap: two relays (`SEEK` budget 1..2; the wire rejects more, whatever `test_relayed_calls_max_relays` says). With `N` first hops, fan-out `F`, `S` budget-1 rings (1, or 2 inside the boundary window), up to 2 caller dials per request and 3 dials per helper request, an **honestly executed** attempt makes at most `N(S + 1)` requests to first hops and `N F` to second hops, touches at most `N(1 + F)` distinct helpers, and makes at most `2N(S + 1) + 3N(S + 1) + 3NF` physical dials. With the defaults (`N` = 3, `F` = 2, `S` = 2): 9 first-hop requests, 6 second-hop requests, 9 helpers and 63 dials, before the 45 s deadline and the minimum-allowance rule prune it (a realistic attempt makes far fewer). The caller enforces its own share as hard counters (requests and dials per attempt). This is not a guarantee against dishonest helpers: a modified helper can fan out more widely, and per-hop authentication cannot enforce a global budget; each phone's own budgets bound what it spends.

**Resource envelope (every helper, phone-wide; applies to `SEEK`, to a plain `SETUP` handled as a search, to table fallbacks and to every retry).**

- One relay duty at a time (the reservation above).
- Rolling 10-minute budgets: search duty at most 60 s, on-demand scanning at most 30 s, at most 12 outgoing dials and 12 outgoing handshakes; at least 10 s between the end of one search and the acceptance of the next. *Search duty* runs from accepting the request to sending `READY` or `FAIL` (relaying after `READY` never counts; teardown after `FAIL` counts up to 2 s); *scanning* is the wall time of on-demand scans (the opportunistic cache costs nothing); a *dial* is each connection attempt including PHY and transport retries and alternate addresses; a *handshake* is each outgoing link handshake started. Only work actually done is charged, and the duty and scan time of a search that ends in `READY` are credited back (it served a real call). All budgets are DEBUG tunable.
- A request that cannot fit gets `FAIL` refused at once, before any radio work, except that a request whose allowance exceeds the remaining duty budget is accepted with its deadline shortened to that budget when the minimum still fits.
- The owner first: a search reserves a scan start from the app's quota only while at least two starts remain in the 30 s window for the owner's own actions, never pre-empts the owner's scans, and is cancelled (`FAIL` busy upstream) when the owner starts a call, a stream, an exchange or opens a scan screen.
- Replays: only `FAIL` answers are cached (64 entries, 60 s, keyed on nonce, token, budget and skip list), and a cached answer is sent with the new request's setup ID; a `READY` is never replayed, because the chain behind it may be gone. "No route" never counts as misbehaviour. A parent is refused for 5 minutes only after a protocol violation (malformed record, a second type-12 record, a deadline overrun); with CP's throwaways that filter is keyed on the link's remote address and is a nuisance filter, not the bound.
- Under a sustained attack the budgets cap a helper at about 10 % search duty and 5 % scanning, plus 72 dials and handshakes an hour; handshakes from strangers are also paced by the BMH3 signing budget (8 tokens, one per 4 s). The attacker also shuts honest callers out of that helper for the budget window: the price of a bounded battery, measured by the availability-under-attack cell of the A/B.
- *A scan-start gate measurement comes first*: before the A/B cells, each required phone runs the prototype's on-demand scan with its timing lines (start to first result, quota refusals, behaviour while a link to the caller is open). If a phone cannot start a scan quickly or within the quota while it holds the caller's link, it is excluded as a helper (pause reason) rather than the minimums being stretched.

**Privacy.**

- *Passive scanners* see nothing new: no reach pages, and the request is inside the encrypted link. They see the caller connect to a helper, a short scan, and the helper connect onward, the connection pattern of any relayed call (timing correlation by an observer near several hops remains, as today).
- *Helpers asked* learn that someone is seeking a target. A helper resolves the token only against IDs it knows: those it hears during the search, those its own leases give it, or any it has recorded. With one ID per request it cannot link two epochs of the target from one request. A request reaches up to 9 helpers per attempt, against only the chosen path for SETUP. The skip list shows the first two bytes of current helper IDs that are on air anyway. The narrow claims: on-demand mode removes reach pages from the air, and a helper that does not know the target's current ID does not learn it.
- *A presence oracle, stated plainly.* `SEEK` answers "is the phone with this ID within two relays of here?" to anyone who holds a current ID: a lease holder (for the whole lease window, about four weeks), or anyone who saw the ID on air in the current epoch (at most 15 minutes). The wire does not prove that the asker holds a lease, tapped Call, or is asking about one person: a modified client can ask about every ID it knows, one request at a time, at the helpers' budget rates. It cannot derive an unknown rotating ID from a name, and it learns nothing about a helper's contacts. Compared with the proactive arm the exposure is **different, not smaller**: pages show a bounded subset to every passive scanner without asking; searches answer targeted questions about any known ID, need an authenticated connection and are rate-limited. **In OR-1 (DEBUG only), possession of the current ID is the authority to search.** OR-T is the stronger rule and must be decided before any user-facing build.
- *No stable identifiers:* the token is over an epoch ID; nonces and setup IDs are random.

**OR-T (sketch, separate review): a target-verified search proof.** The caller adds to `SEEK` a 16-byte proof `HMAC-SHA-256(K_seek, nonce || RDI || u32 epoch)[0:16]` with `K_seek = HKDF-Expand(L_d, "BluetoothVideoMesh/RelaySeek/Proof/1", 32)`, which only holders of that day's lease can compute. The last helper hands it to the target as the first record on its link; the target verifies it with its own day key, keeps a per-epoch replay cache of nonces, and closes the link when it does not verify, which the helper reports as "no route", indistinguishable from absence. A non-holder who only saw the ID could then no longer learn whether the target is within reach, unless the asked helper itself hears the target (which it knows anyway). It adds a hop record on the target's link and touches BMH3/lease rules, hence the separate review; `RELAY_SEEK` bit 1 is reserved for it.

**Who carries the risk (design rule, 2026-10-27).** Where a tradeoff cannot be avoided, the extra exposure or cost must fall on the forger, spammer or prober, never on the genuine user. Applied to every part of the search:

| Threat | Who would carry it under revision 3 | Rule now | Residual |
| --- | --- | --- | --- |
| A spammer exhausts a helper's budgets, so genuine callers lose that helper for up to 10 minutes | Genuine callers (lost reachability) | Searches that end in `READY` are credited back, so genuine successful use costs nothing; refusals happen before radio work. **OR-PZ (proposed, not built; needed before any user-facing build):** once a helper has used half of any budget in the window, it answers a new request with a client puzzle bound to the link (a hash puzzle whose difficulty doubles with each further quarter of the budget used) and admits the request only with the solution; a genuine caller pays a few hundred milliseconds of CPU only while the helper is under load, a spammer pays for every request. | Until OR-PZ is built, a spammer who can open authenticated links can still exhaust one helper's budgets for a window (DEBUG prototype only). An attacker with much more computing power than a phone can still buy requests; the puzzle makes the price per request, not zero. |
| A forger copies a target's ID so helpers waste dials on the copy | The helper (dials, battery) and the caller (time) | Bounded collection keeps the genuine address available; an advertiser address that failed the opening for the sought ID is not dialled again for that epoch on this phone, so a copy costs the helper one dial per epoch, not one per search. | With Amendment CP's unbound edges a copy that completes a pseudonymous handshake still makes one search fail end to end. |
| A prober who saw an ID asks whether that phone is within two relays | The target (presence leak) | In OR-1 (DEBUG) the possession of the current ID is the authority, stated as a residual. **A user-facing build requires OR-T**, so only a lease holder can make a target answer; to a non-holder an absent and a present target look alike ("no route"). | A helper that itself hears the target learns its presence, as it would from the advert anyway. |
| A stranger connects to a helper to learn its long-term identity | The helper | OR-1 (pseudonyms off) is a lab scope only: **a user-facing build requires CP's pseudonymous edges**, so a helper and a target show only connection pseudonyms on relay links. | In the DEBUG scope helpers reveal their real key to any initiator, as every Everyone-mode listener does. |
| A relay rings a target whose consent is off, using a replayed consenting advert, to learn its identity | The target | The target refuses before any identity leaves it: a first end-to-end handshake record that arrives over a link whose peer signed the call-relay mark is closed unanswered while the target's current consent is off (the decline after the handshake stays as the second check). | None for identity. The relay learns that some listener at that address refused. |
| Malicious helpers answer false "no route" so the caller backs off | The genuine caller (locked out of its own search) | A user's tap is never blocked by a backoff: the per-contact backoff applies only to automatic retries; a tap always runs a search (the budgets of the helpers, not the caller's patience, bound the cost). A helper that answered "no route" is skipped for that selector for 60 s, which hurts only that helper's own usefulness. | A search through only malicious helpers fails; the caller's next tap tries again. |
| A forged or replayed request makes a helper relay for someone else, or a cached answer is poisoned | The helper or the caller | Every request is regenerated per hop on an authenticated link; the replay cache keys on the caller's random nonce, so nobody can pre-answer a genuine request; `READY` is never cached. | None found. |
| A caller's own search is used to link it | The caller | The caller shows helpers a fresh throwaway per link and binds its real key only end to end to the contact it sought (contact tag, full fingerprint). | Timing correlation by an observer near several hops, as for any relayed call. |

Unavoidable residuals, in one place: a helper that hears the target learns its presence; until OR-PZ, a spammer can exhaust one helper for a budget window; with CP a copied target ID can fail a search end to end; an observer near several hops can correlate timing. None of them lets a forger or spammer make a genuine user reveal an identity.

**Security (beyond the resource envelope).**

- A copied target offer (someone replaying the target's ID) can match the token. With CP off it fails the `OPENING`, and bounded collection keeps the genuine address available; an identity failure is a failed candidate, not the end of the search. With CP on it can only make the search fail end to end.
- A malicious helper can drop, delay, refuse or answer a false `FAIL`; the caller moves on. It cannot read, alter or impersonate (end-to-end keys and checks unchanged). The 6-byte token is a lookup hint only: one token against 64 unrelated IDs matches by accident with probability about `2.3 x 10^-13` per search, and a collision still fails the end-to-end full-fingerprint check.

**Latency hypotheses (to be measured; not results).** The component times come from the measured warm path; the scan times assume a low-latency scan really runs at full duty, which the stack does not guarantee (it changes effective modes with app state and active connections). Each hop also pays up to 1 s of candidate collection and BMH3 signing on every handshake (Keystore ECDSA, unmeasured per phone).

| Case | Proactive warm | Proactive cold or after a boundary | On-demand (hypothesis) |
| --- | --- | --- | --- |
| One relay, the first helper reaches | 3-8 s (measured) | 12-20 s (measured) | about 5-14 s: the warm path plus the helper's scan (about 0.3-3 s), collection (up to 1 s) and signing |
| Two relays | not seen in one room without masks | 25-35 s (measured) | about 15-30 s: ring 1 misses at every first hop first (about 5-8 s each), then ring 2 |
| First helper cannot reach (one relay) | not applicable | not applicable | each wrong first hop adds about 5-8 s |
| Contact absent | the table already shows no route | as warm | 45 s, the same give-up time as the proactive arm |
| Within about 10 s after the target's boundary | tables flushed | as cold | the target's 1-8 s advertising silence can outlast a 3 s scan; ring 1b (the neighbour selector) recovers |

Two relays are slower than in revision 2 because the rings prefer short routes: a two-relay search starts only after every first hop has been asked for one relay.

**Battery hypotheses (to be measured).** An idle on-demand helper runs no scan, against 5-25 % nominal receiver duty plus a page set and neighbour wake-ups for a proactive helper. A search adds a scan of at most 3 s, connections, handshakes and CPU work, none of which scan-window arithmetic captures; at a few searches an hour the idle saving is expected to dominate. Under attack the budgets cap scanning at 5 % (180 s an hour), equal to the proactive arm's lowest duty, plus up to 72 dials and handshakes an hour. Idle drain, attack drain at the budget cap and screen-off behaviour are A/B gates (the battery measurement adapter is still missing). The caller's parallel direct check runs only during its own attempt.

**Interaction with SETUP, READY and candidate iteration.** `SEEK` is another opening message of hop type 12 with the same `READY`/`FAIL` replies and the same post-`READY` rules; it uses SETUP's remaining-time range (2,000..20,000 ms). Candidate iteration (deferred in Design C) is the ring loop. The benchmark rule is unchanged: `test_relayed_calls_require=<n>` accepts only `READY` with exactly n relays (n at most 2; with n = 2 the caller skips rings 1 and 1b), and a direct call is a failed requested chain. A helper in on-demand mode that receives a plain `SETUP` (message 4, from a proactive caller) handles it as a search for that one ID under the same reservation and budgets, with its budget clamped to 2. A helper running both arms tests the token against its table first and uses only a fresh entry within the request's budget that is not on its failure skip list (the existing `setupRoute` semantics), forwarding a regenerated message 4 `SETUP` whose remaining time is at most 20 s by construction; any other entry is ignored and the search proceeds.

**Mixed meshes.** Capability is the authenticated `RELAY_SEEK` extension, so an older or BMH2 helper is never sent a `SEEK`; a link that closes during a search is an ambiguous failure, remembered for 60 s per helper offer and retried after that, never treated as "unsupported". A helper applies the same rule to its own children: a child without the extension costs one dial (counted) and is skipped. Mixed meshes give partial connectivity: a proactive caller cannot find routes through on-demand helpers (they advertise no pages), and an on-demand caller reaches a proactive-only helper only through its pages (keep-tables arm) with a plain `SETUP`. Relayed calls are a default-off experiment, so the installed base of older helpers is the test phones.

**What the user sees.** The Nearby list shows routed contacts only when a reach table knows a route (the 2026-10-26 Nearby list decision). Arm O has no table, so a contact beyond direct range is not listed as routed; it is found only by tapping Call on it in Contacts. That difference is part of the decision rule, not a defect of the arm.

**iPhone and Windows (feasibility, not device validation).**

- *iPhone caller:* plausible once OR-1's handshake rules are implemented on iOS. It sends `SEEK` over a link it opens as central, advertises nothing, and computes tokens from the leases it holds.
- *iPhone helper:* plausible in the foreground only (an iPhone advertises in a form Android reads only then; compact offer bit 58 already means "relay capable"); a foreground scan and simultaneous central and peripheral roles are supported by Core Bluetooth. It is the only way an iPhone can ever help, because reach pages are manufacturer data, which iOS cannot advertise.
- *iPhone target:* excluded until the compact amendment can carry consent (call-offer bits 49..0 must be zero, and an older Android decoder rejects a UUID with one set).
- *Windows:* a caller is plausible (central role). A helper needs an adapter that reports and actually performs the peripheral role, its single announcing provider carrying a relay-capable offer, an on-demand advertisement watcher and simultaneous roles verified on that adapter. Deferred.

**Failure modes.**

| Failure | Behaviour |
| --- | --- |
| Contact not within two relays | Every request answers `FAIL` no route; the call screen shows "Searching nearby phones", then "Can't find <name> nearby" at 45 s or when the rings run out; then the per-contact backoff. |
| Wrong first helper | `FAIL` no route in about 5-8 s; next first hop in the ring. |
| Helper busy, paused, out of budget or out of scan starts | `FAIL` busy or refused at once, before radio work; not asked again in this attempt. |
| Epoch boundary during the search | One ID per request; ring 1b tries the neighbour selector inside the boundary window; the 60 s opening pin applies as for SETUP. |
| Target in a call | Its call offer is off air, so the search ends in no route (a busy-marker selector is an open question). |
| Copied target ID nearby | CP off: collected alongside the genuine address, its opening fails, the next address is tried. CP on: the search may fail end to end. |
| Target's consent off, or relayed calls off on the target | The target declines the relayed call before ringing. |
| Two callers at once | The second gets `FAIL` busy from a helper already on duty. |
| Link drops during a search | Ambiguous failure, remembered 60 s, next first hop. |
| Owner starts something | The search is cancelled, `FAIL` busy upstream. |
| The contact appears directly mid-search | The caller closes the search link and calls directly. |

**A/B test plan (on one frozen APK of the OR-1 prototype).**

- *Arms:* P = proactive (today), O = on-demand (`test_relayed_on_demand=true` on every participant), B = both (`test_relayed_on_demand_keep_tables=true`). Every participant has relayed calls, rotating IDs and BMH3 on; pseudonyms off unless the CP switch is on for the whole run. All participants of a run use the same arm, except one dedicated mixed-mesh case. Isolated runs (no concurrent lanes); arms alternated in blocks, the order randomised per block.
- *Step 0:* the scan-start gate measurement on every required phone (above).
- *Cells:* one relay (caller masked from the target), two relays (masks on the caller and the first helpers, extended to the on-demand scan), a room of three helpers of which only one reaches the target (wrong first guess), taps 0-30 s after an epoch boundary (`test_rotid_epoch_s=60`), the contact absent, a copied target ID (a test sender replaying it), screen-off helpers, and **availability under attack** (a second DEBUG caller searching for an absent ID as fast as the helpers' budgets allow, `test_relayed_seek_no_backoff=true`, while an honest caller places calls). P runs warm (helpers idle at least 60 s) and cold (helpers started less than 5 s before the tap). GATT and LE CoC; both setup roles.
- *Pacing:* the success and latency cells run with the helper budgets scaled up (`test_relayed_seek_budget_scale`) so one trial cannot exhaust the next one's budget, and each trial starts only after the previous one's links have closed; the availability, attack-energy and idle-battery cells run with the default budgets. Any budget refusal is logged and stays in the results.
- *Metrics:* tap-to-ringing on the caller's monotonic clock (tap to the callee's end-to-end Ringing record, so no cross-phone clock), median and 90th percentile; success (ringing within 45 s with exactly the required relay count); requests, helpers touched and physical dials per attempt; scan-start refusals and budget refusals; helper energy per idle hour and per hour at the attack budget cap (screen off, unplugged; UNMEASURED until the battery adapter exists); on-air exposure per hour from a passive observer phone running the DEBUG raw observer.
- *Statistics, fixed before the run:* the primary comparison is one-relay success, O against warm P, as a non-inferiority test with a margin of 10 percentage points on a one-sided 95 % Newcombe-Wilson interval; at an expected 90 % success, 120 attempts per arm give about 81 % power (review 2's enumeration; 110 give about 78 %), so the primary cell gets 120 per arm. A 5-point margin would need about 440 per arm, or a group-sequential design; not planned. Other cells get 20-30 attempts each, reported with their intervals and never pooled into the primary claim. Uncertainty is computed with a stratified block bootstrap (blocks = the alternation blocks, strata = cells), for success and for the median and 90th percentile of latency. Battery: at least three one-hour windows per arm per required phone, alternated.
- *Decision rule:* O can be considered for a default only if it is non-inferior on the primary success comparison, its one-relay median tap-to-ringing is within 3 s of warm P (interval included) and below cold P, no cell shows a new failure class, the attack cell leaves honest callers a measured, stated success rate, the idle energy saving is measured on every required phone, the user accepts that routed contacts are not listed in Nearby under O, and the presence-oracle question (OR-T, or accepting ID possession as authority) has been decided. Otherwise O stays an experiment. B (proactive while charging, on-demand on battery) is the likely compromise to test.

**Recommendation.** Build the OR-1 DEBUG prototype now (review 2: approve with changes for a default-off DEBUG prototype); no release setting and no default before the A/B, OR-T and the user's decision. Expected, as hypotheses: equal one-relay success, a few seconds slower than a warm table for one relay, faster from cold, slower for two relays than revision 2 promised, much lower idle helper drain, no reachability information on air, and a path to iPhone callers and helpers.

**Switches (DEBUG launch extras only; registered in SWITCHES when coded; all off by default, all effective only with `test_relayed_calls`).** `test_relayed_on_demand`, `test_relayed_on_demand_keep_tables` (arm B), `test_relayed_seek_scan_ms` (3000; 1000..6000), `test_relayed_seek_first_hops` (3; 1..3), `test_relayed_seek_fanout` (2; 1..2, 1 = the simpler fan-out the reviewers offered), `test_relayed_seek_order=strong|far` (strong: strongest first-hop signal first; far: the weakest usable one, more likely to reach beyond the caller's range), `test_relayed_seek_connect_ms` (the expected connection time of the minimum-allowance rule, 4000), `test_relayed_seek_budget_scale` (1; 1..20, multiplies every helper budget), `test_relayed_seek_no_backoff` (the attack cell's caller). The plain-ID sub-arm of revision 2 is dropped (it had no wire discriminator). Later: `test_relayed_seek_proof` (OR-T), `test_relayed_seek_probe` (OR-C).

**Phases.** OR-1a: codec, vectors, the `RELAY_SEEK` extension, token, budgets and reservation, the ring loop and the helper search state machine with JVM tests (matching, collection, budgets, reservation, regeneration, one deadline, the minimum-allowance rule, the work bound, `FAIL` handling, the replay cache, byte identity with the switches off). OR-1b: Android wiring (BMH3 onward links shared with CP, the on-demand scan through the scan-start gate, the caller loop with the parallel direct check, target consent). OR-1c: the phone plan above. Then OR-T and OR-P (pseudonymous relaying beyond CP, if CP leaves gaps), iPhone caller and helper, OR-C.

**Open questions for later reviews.**

1. Is the 6-byte token worth its bytes over the plain ID, now that its only property is "a helper that does not know the ID does not learn it"? (A plain-ID arm would need a selector-mode field.)
2. Are the budget numbers right for one helper serving a household or a crowd, given that an attacker can shut honest callers out of a helper for a budget window?
3. Should OR-T be part of the first user-facing build, so that no such build ever answers a non-holder?
4. Should the caller add a busy-marker selector so a helper can answer "in a call" (more information to helpers that hear the target)?
5. Do the required phones start a low-latency scan and report the first result fast enough for a 3 s window while holding the caller's link (step 0)?
6. Can a helper scan at full duty while it is a peripheral of the caller without starving that link (the Exynos dual-role scheduling seen in "Relay dual-role scheduling")?
