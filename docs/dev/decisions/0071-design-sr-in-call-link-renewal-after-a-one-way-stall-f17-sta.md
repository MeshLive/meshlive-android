# Design SR: in-call link renewal after a one-way stall (F17 Stage B; draft 2026-10-20, review 1 and revision 2 2026-10-21, review 2 fixed; on by default since 2026-10-21)

**Status: revision 2 implemented on Android behind `test_call_link_renewal`; on by default since 2026-10-21 (design decision Q-SR-DEFAULT A; control arm `test_call_link_renewal=false`, both phones). Phone A/B: stalled direct GATT calls survived 13 of 16 with renewal against 0 of 16 without, with 0 false renewals in 8 controls; open: the A15s-as-peripheral connect failure behind the 3 losses.** Wire rule: PROTOCOL "Experimental in-call link renewal (Design SR, on by default)". Stage A (`test_call_stall_tolerance`, Experimental, off for plain calls) and the liveness hang-up (on) are built; this record is the step after them.

**Problem.** A call ends although both phones are still connected and one direction still works. The hop link's sending stalls in one direction (host queue full, no controller credits), the peer hears nothing for 8 s and ends the call (CF-CALL-10). Three instances on 2026-10-20, all with the S24 as callee while a laptop paired with it connected to it about once a second (Phone Link; design decision: the app must tolerate it):

In both stalls the link layer stayed up (no disconnect, supervision timeout 5 s never fired), the other direction kept working, and the stall ended at the next **new LL connection** on that controller. That points at the stalled phone's controller or stack, not at the radio path; a fresh connection is the one thing seen to clear it.

**Conflict (resolved by amending the rule).** CF-CALL-21 said: "a call is never automatically reconnected or redialled". This design keeps the call ID and the end-to-end session and replaces only the hop link, which is not a redial. CF-CALL-21 is amended (2026-10-27): a call is never redialled and never moves to another phone; the only automatic recovery is the renewal of the hop link of a direct GATT call, with the same call ID, the same end-to-end keys and the same peer (USER_GUIDE says what the user sees).

**Options.**

| Option | What happens | Cost and risk |
| --- | --- | --- |
| A. Break-before-make renewal (recommended for the first experiment) | The phone that stopped hearing its peer (its own writes still complete, Stage A's "soft" state for 3 s) sends `RENEW_OFFER(ticket)` on the old link. The peer, which still reads, arms a connectable, non-discoverable renewal advert for at most 6 s. The offerer closes the old link, connects to that advert (a new LL connection), runs a pinned hop handshake, proves the ticket, and attaches the new link to the same end-to-end session and call ID. | 1-3 s of silence during the renewal, about what the stall already costs. One scan start (quota). A peer that cannot read the offer (both directions stalled) never arms the advert, so the call ends as today. |
| B. Make-before-break second carrier | As A, but the old link stays up until the new one is ready, with Design CX's two-carrier cutover (`SWITCH`/`RESUME`) on two LE carriers. | No gap when it works. But it needs a second LE connection between the same two controllers while the first lives (unproven: stacks may refuse or merge it onto the same ACL, which would not clear the stall), and it depends on the CX state machine, which has not been reviewed. Second stage. |
| C. Stage A only | Keep the call up to 14 s while our own writes complete. | Already built (off). Saves stalls that clear by themselves within 14 s (the first stall: 10.06 s), not those that end only with a new connection (the second: 9 s without a laptop link, then a failed notification). |
| D. Avoid the trigger | Nothing in the app; ask users to unpair PCs. | Rejected by the user: the app must tolerate it. |

**Rules for option A (all hop-local, direct calls only; relayed calls end as today).**
1. *Trigger.* Stage A's soft state for 3 s, the call `ACTIVE` for at least 10 s, at most one renewal per 60 s and two per call, never while ringing or during setup (setup has its own retry, CF-CALL-07).
2. *Capability.* Only when both end-to-end hellos carry the renewal bit (an end-to-end capability, so a relay never needs it; older builds never see a renewal record and end the call as today).
3. *Offer.* `RENEW_OFFER` is end-to-end content (BME1), so only the real peer reads it: ticket (8 random bytes), the offerer's role. The answer `RENEW_ARMED` (or `RENEW_REFUSED`) goes back on the old link if it can; the offerer does not wait for it (its direction is the one that may be stuck) and starts scanning at once.
4. *Advert.* Non-discoverable where the platform allows (API 34+), legacy, connectable, a fresh RPA, **no announcement**, and a 128-bit service UUID derived from the end-to-end session: `HMAC-SHA-256(K_renew, "srv" | callId | ticket)[0:16]` with the version and variant bits set; `K_renew` from the BME1 key schedule with a new label. Only the peer can compute it, and it is new for every attempt, so it neither links to the phone nor to earlier calls. Stopped when the renewal completes, after 6 s, or at call end.
5. *Admission.* The new link's first bytes are a pre-proof as in Design CX (`HMAC(K_renew, "pre" | ticket | challenge | hash of the first handshake message | both node IDs)`), checked before any handshake byte; the ticket is consumed only on a valid proof. Then the hop handshake with the **old link's pinned peer** (same node ID and static key; a pseudonymous call keeps its pseudonym keys, nothing new is revealed), the same protocol version, no build tag, no `BDO1`.
6. *Attach.* After the handshake the offerer sends `RENEW_BIND(ticket, next send sequences)` end to end; the peer moves the call to the new link, drops records below the floor (stale, never fatal), requests a key frame, re-asserts mute, camera and labels once. Audio is not discarded (user direction 2026-10-07); a backlog older than the playout budget is a separate bounded-age question for the user.
7. *Failure.* Any failure ends the call as link lost with the liveness hang-up, within a hard 12 s from the start of the soft state. Logged as `call_renewal: phase=offer|armed|connected|bound|failed | reason= | ms=`.

**Security review items.** Ticket single use and bound to the call ID and both identities; the renewal advert reveals nothing a passive observer can link (no fixed UUID, no announcement, fresh RPA); a third phone cannot attach (pre-proof plus pinned identity); a peer cannot use renewal to switch identity or reveal state (pinned keys, no reveal); no new path for a relay (end-to-end records only, direct calls only); bounded retries (DoS by a hostile peer costs at most two 6 s adverts per call).

**Gate before promotion.** Reproduce F17 with the laptop condition on the S24 (5-minute calls, both directions, btsnoop on the S24); A/B renewal on/off on the same pair and build; zero renewals on calls without a stall; a stranger call and a contact call; old build x new build ends exactly as today.

## Review 1 (2026-10-21): approve with changes, for a gated implementation (Experimental, default off)

**Why it matters (new evidence).** A second trigger fits option A exactly. In edgecases-20261020 a15s-redmi-m31-1 (A15s calling the Redmi, GATT, Redmi peripheral at 7.5 ms), Google Play services on the Redmi started its own advertising set mid-call. Within 0.5 s the link was renegotiated twice (7.5 then 15 ms). From then on the Redmi's stack kept completing about 70 notifications per second, but the A15s app received nothing more. The A15s -> Redmi direction kept working (about 65 writes per second received). After 8 s the A15s's liveness hang-up ended the call. MeshLive did no radio work in that window, so the trigger is outside the app, and only a new link can clear it. GR1 cannot help: nothing arrives, so there is no gap to request, and HIGH is not sent while the sender is busy.

**Verdict.** Approve option A as an Experimental, default-off implementation for direct GATT calls, with the changes below. Option B stays a later stage; options C and D as decided. The record's direction is sound: renewal keeps the end-to-end session (keys, call ID, sequences) and replaces only the hop link, which is authenticated again from scratch with the same pinned identity.

**Wire rules (against PROTOCOL).**
1. *Assign the numbers in the record and PROTOCOL before code.*
   - Content types: BME1 types `1`, `2`, `4`-`11` are in use (`9` call video fragments, `10` LABELS, `11` store-and-forward/opening), so use one new end-to-end content type `12` (`RENEW`) with a one-byte op (`1` OFFER, `2` ARMED, `3` REFUSED, `4` BIND) rather than four types.
   - Capability bit: end-to-end hello transport-mask bits `3`, `5` and `7` are taken. `4` and `6` are used only in link hellos; confirm in the hello codec that they are free in end-to-end hellos, then take one and record it next to the bit-5 and bit-7 rows.
   - Layouts: write them out. OFFER = ticket 8, role 1. ARMED = ticket 8. REFUSED = ticket 8, reason 1. BIND = ticket 8, then the next BME1 send sequence (8) of the sender. Exact lengths; anything else is rejected as a malformed record (fail closed, like every BME1 record).
2. *Transport of the new link.* Name it. The old link's transport is what failed; the evidence is GATT, and a CoC renewal would also need the listener's PSM in the advert (Design CD, not built). So the first experiment renews **GATT calls only, over GATT**; a CoC call ends as today.
3. *Roles.* The offerer connects as central to the armed peer's advert, so the peer is peripheral on the new link even if it was central on the old one. The armed peer needs a GATT server registration. On a phone whose 32-slot table is full (the Redmi Android 11 case, Nearby restart hint) this can fail; that must end the renewal as `failed reason=server_registration` within the 12 s bound, not hang.
4. *Challenge origin.* Rule 5's pre-proof includes a challenge but does not say who sends it. Specify: the armed peer sends a fresh 16-byte random challenge as the first value on each new connection; the offerer answers with the pre-proof. Otherwise a pre-proof seen on the air could be replayed into a second connection (the ticket is single use, but the order of acceptance would decide).

**Interaction with GR1 and the liveness hang-up.**
5. *Liveness on both sides.*
   - Offerer: renewal needs more than the 8 s liveness window (3 s soft state, up to 6 s advert, connect and handshake), so the SR switch must imply the Stage A tolerance on the offerer (the hard 12 s from the soft state replaces the 8 s check).
   - Armed peer: it stops hearing the offerer as soon as the old link closes (break-before-make), so it must suspend its own liveness hang-up from sending ARMED until the renewal deadline. It also must not send its HANG_UP before close during that window.
   - Both sides log the suspension.
6. *GR1 and the hop layer.*
   - The new link has its own chunk sequences (from 0), its own GR1 HELLO and history, and its own BMS1 keys and record sequences from the new hop handshake. Nothing of the old link's GR1 history or BMS1 state carries over.
   - A BMS1 record cut off at the old link's end is lost with that link. The end-to-end layer already accepts increasing sequence gaps after drops (PROTOCOL "Hop and endpoint records"), so BIND's next-sequence floor plus that rule are enough. State in PROTOCOL that a lost control signal (mute, camera, Hang-up) is re-asserted once after BIND (rule 6 does this for mute, camera and labels; add the call phase).
7. *Old link after BIND.* Once BIND is accepted, the old link must be closed, and any record that still arrives on it must be dropped (not processed), so an old-link record cannot reorder after the new link's records.

**Security (no hijack).**
8. *Same call keys, new hop keys.*
   - The renewed link is authenticated by a full hop handshake pinned to the old link's peer identity and static key, so a third phone cannot complete it.
   - The end-to-end BME1 session is unchanged: same keys, continuing sequences. So a hijacker would need both the hop identity and the end-to-end keys. Good.
   - Add the explicit rule that BIND is accepted only on the link that completed the pre-proof and the pinned handshake **for that ticket**, and only once. BIND arriving on the old link, or on another link, is ignored.
9. *Squatting on the renewal advert.*
   - The advert's 128-bit UUID is unpredictable before it is on the air, but anyone can read it from the air and connect first. The armed peer must not accept only the first connection.
   - It must drop a connection that has not presented a valid pre-proof within 1 s of its challenge, and keep advertising until the 6 s window ends. Then a squatter costs at most a failed renewal (the call ends as today), never a wrong peer.
10. *Downgrade.* An attacker who strips nothing can only force the call to end as today (no renewal), because the capability bit sits in the signed end-to-end hello. No downgrade to weaker keys exists, since the new hop handshake uses the old link's protocol version (rule 5).
11. *Privacy.* Per-attempt UUID, fresh RPA and no announcement are fine. On API 29-33 the advert cannot be non-discoverable: state it, and log `nonDiscoverable=false` for those attempts. The advert's timing reveals that a call is in progress near this phone, but so do the call's own link and traffic; accepted.

**Hop-local.**
12. *Direct calls only, and checked.* "Direct calls only" must be checked, not assumed: the renewal is allowed only when the call has no relay (the hop peer is the end-to-end peer, same node ID). A relayed call ends as today. Every renewal record is end-to-end (BME1), so a relay never acts on one; no new relay behaviour.

**Gate additions.**
13. Two more gate items:
    - Add the Redmi case to the gate: an Android 11 peripheral at 7.5 ms with another app's advertising set started mid-call, scripted where possible.
    - Measure the silence a renewal costs (soft state to first media on the new link), next to the 8 s the liveness hang-up costs today.
14. Before shipping, amend CF-CALL-21 and USER_GUIDE in the same change: a renewed link is not a redial; the call ID and keys continue. (Done 2026-10-27, when renewal was already on by default.)

**Not required now.** Option B (make-before-break), relayed calls and CoC renewal stay later stages.

## Revision 2 (2026-10-21): review 1 addressed; implementation, on by default since 2026-10-21

The wire rules are now normative in PROTOCOL "Experimental in-call link renewal (Design SR, on by default)"; these points record the decisions behind them and replace the matching parts of option A above. Switch: `test_call_link_renewal` (default on since 2026-10-21; `false` is the control arm, both sides).

1. **Numbers assigned (review 1 item 1).** One `BME1` content type `12` (`RENEW`) with op `1` OFFER (ticket 8, role 1), `2` ARMED (ticket 8), `3` REFUSED (ticket 8, reason 1) and `4` BIND (ticket 8, next send sequence 8), exact lengths 10, 9, 10 and 17 including the op; anything else fails closed. Capability: end-to-end hello bit 4 (`0x10`). Checked in this repository on 2026-10-21: end-to-end hellos are built from the endpoint's own capabilities (AndroidPrivateVideoCall `establish`, `CallEndpointOpening.advertise(PeerLabelFeature.advertise(CallVideoFragments.advertise(...)))`) and carry bits 3, 5 and 7 only; bits 4 and 6 are added only to link hellos (`RelayedCalls.linkCapabilities`, `PrivateCallRelayChain.relayCapabilities`), and the Windows hello sets transport bits only. The iOS hello codec is not in this repository; iOS readers test only their own bits, and an iOS build must not set bit 4 until it implements renewal.
2. **Transport (item 2).** GATT calls renewed over GATT only; CoC, Classic and dual-listening links on another transport end as today.
3. **Roles and the full registration table (item 3).** The offerer is central on the new link, the armed phone peripheral with a dedicated GATT server. Registration and the advert start run on a worker bounded to 3 s; past that the armed phone answers REFUSED (server registration or advertising) and closes the late server when it arrives. All bounds include it (item 7 below).
4. **Challenge origin (item 4).** The armed phone sends a fresh 16-byte challenge on every new connection; the offerer's proof covers it and its own fresh nonce.
5. **Liveness (item 5).** The offerer's liveness close moves to the renewal bound (12 s after OFFER). The armed phone suspends its liveness hang-up and sends no liveness HANG_UP from OFFER until BIND or its own bound, and logs both.
6. **Per-link state (item 6).** The new GATT connection has its own chunk sequences, its own GR1 HELLO and history and its own BMS1 keys and sequences; nothing carries over except the end-to-end session and the call state.
7. **Bounds (12 s).** Offerer: OFFER, scan up to 6 s, connect and opening, BIND; once it scans or connects the call ends as link lost 12 s after OFFER if not bound; a scan that found nothing leaves the old link under the normal liveness rules. Armed phone: advert until 7 s after OFFER arrived; 12 s after it, without an accepted BIND, it ends the call when its old link failed or closed and otherwise disarms. An offerer that hears its peer again before breaking the old link sends REFUSED with the new reason 7 (abandoned), and the armed phone disarms at once.
8. **Re-assertion (items 6 and 14 of the record).** After BIND: key frame request, own key frame, current microphone and camera signals, own LABELS once; the phase is ACTIVE on both (renewal starts only from ACTIVE). A hang-up during a renewal ends the renewal; the peer ends at its bound.
9. **BIND (item 8).** Accepted only as the first BMS1 record of the connection whose proof consumed that ticket, once, with the current ticket; on any other link it is ignored and logged. The old link is closed after BIND and its late records are dropped unopened (item 7).
10. **Squatters (item 9).** A connection without a valid proof 1 s after its challenge is dropped at once (a wrong proof at once); the set keeps advertising until its window ends; at most 8 connections are challenged per attempt.
11. **Downgrade (item 10).** Bit 4 is signed in the end-to-end hello; stripping it only removes renewal. Nothing is negotiated on the new link (see Review 2, finding 1).
12. **Privacy (item 11).** Per-attempt UUID, fresh RPA, no announcement; on API 29-33 the advert stays discoverable (the platform cannot clear the flag) and logs `nonDiscoverable=false`.
13. **Hop-local (item 12).** Direct calls only, checked: relay count 0, no relayed route, link node ID equal to the end-to-end node ID, GATT, ACTIVE, not a verification session. A phone that receives OFFER on a call outside that scope answers REFUSED not direct.
14. **Gate (item 13).** Added: the Redmi case (Android 11 peripheral at 7.5 ms; another app's advertising set started mid-call, or the DEBUG hook `test_call_tx_stall_after_s` on the sending phone), and the silence a renewal costs (`call_renewal_silence`: last record on the old link to the first on the new one) next to today's 8 s. CF-CALL-21 and USER_GUIDE are amended in the change that promotes the switch, not before.

## Review 2 (2026-10-21, second reviewer, skeptical): six findings, all fixed in revision 2 before coding

1. **The pinned hop handshake would put the identity on the air.** Review 1 kept a full BMH2 handshake on the new link "pinned to the old peer". BMH2's signed hello is cleartext; BMH3 (default on for user sessions) exists to hide it, and a pseudonymous stranger call has no real identity to pin at the link layer. A renewal would undo both for every observer near the call. **Fix:** no link handshake on the new link. The opening proves knowledge of `K_renew` both ways (offerer's PROOF first, armed phone's CONFIRM after) and derives the hop keys from `K_renew` and both sides' fresh randomness. On a direct call the end-to-end peer is the hop peer, so this pins exactly the old link's peer; a pseudonymous call stays pseudonymous; nothing new is visible. Cost accepted: the new hop keys have no fresh Diffie-Hellman of their own, but they come from the call's ephemeral end-to-end keys, which already protect all content of this call, so a compromise that reveals them reveals the call anyway.
2. **Break-before-make could kill a call that would have recovered.** In review 1's order the offerer closed the old link right after OFFER. A stall that clears by itself (F17's first instance, 10.06 s) or an armed phone that cannot register a server would then turn a surviving call into a lost one. **Fix:** the offerer keeps the old link until it actually sees the armed advert; if it does not within 6 s, or hears the peer again, the renewal is abandoned and the call continues as before. Because a false trigger now costs only a scan and an advert, the trigger moves earlier: 1 s of Stage A's soft state (4 s of silence) instead of 3 s, which shortens the silence a renewal costs.
3. **Sequence race between the old writer and BIND.** If the offerer's old writer sealed a record after BIND was sealed, the armed phone could receive BIND (sequence n) and later open an old-link record with sequence n + 1, after which the new link's next record would be refused as reordered (fatal). **Fix:** the offerer stops and joins its old writer before sealing BIND. Both readers open records under one lock with the link generation check, and the armed phone opens BIND and moves the generation inside that lock, so no old-link record is opened after an accepted BIND; failures of the old reader and writer while armed end only those threads.
4. **A registration hang longer than the bound.** On a full 32-slot table `openGattServer` can wait about 10 s for its registration callback. **Fix:** a 3 s worker bound and a REFUSED answer (rule 3).
5. **A squatter can hold the only admission slot.** The GATT video server admits one subscriber; a squatter that subscribes first blocks the real offerer until it is dropped. **Fix:** the 1 s proof deadline frees the slot; the offerer retries with a new sighting while time remains; at most 8 connections per attempt bound the work.
6. **Two offers at once.** If each side can still read the other (one-way stalls in both directions at different moments), both may offer. **Fix:** the caller (role 0) keeps its offer and answers REFUSED collision; the callee abandons its own and arms.

**Residuals accepted.** A renewal scan needs the app's scan-start gate (at most 5 starts per 30 s, Android's own limit): a phone that just started several scans, or a backgrounded app whose scans the platform throttles, may find no slot; its offer then ends as not found and the old link stays under the normal rules. A hostile peer can make a phone advertise twice per call for 7 s each. A HANG_UP lost during a renewal is not re-sent; the peer ends at its 12 s bound. The two bounds run on two clocks (OFFER sent, OFFER received), so the armed phone may end a little after the offerer; neither side can hang. The renewal advert makes the armed phone connectable to anyone in range for up to 7 s, bounded by the squatter rule. Option B (make-before-break), relayed calls and CoC renewal remain later stages.

## Review 3 (2026-10-21, independent reviewer): merge after fixes; all nine fixed

The default-off guarantee and the cryptography held (no AEAD nonce reuse, no hijack found). Fixed on the same branch: (1) liveness no longer lives only in the reader and writer threads: a quiet end of either marks the link dead, and a per-call tick ends the call when no renewal owns its liveness (the zombie call after a failed scan or a refused registration); (2) the armed phone keeps the server of the attempt in progress apart from the server that carries the live link, so a later attempt never closes the live link; (3) the offerer's GATT open runs inside the remaining connect budget and stale sightings are cleared; (4) servers are adopted and closed under one lock with teardown; (5) the opening's two halves and the BIND check are pure code that the tests drive, with negative cases (another call or ticket, a reflected confirmation, BIND with the wrong sequence, an old-link record after BIND); (6) the bound is checked before BIND is sent; (7) old writers are interrupted and joined on both sides and a signal in flight is re-queued; (8) only a scanning offer is a collision, and a yielding callee does not count a second attempt; (9) the opener accepts type 12 only when bit 4 was negotiated, `K_renew` exists only in sessions where both hellos signed bit 4, and a zero ticket in a proof is refused. Docs: the empty scan response, the record-lock rule, the scan-gate residual and the iOS bit-4 check (PLAN).

Re-review (same day): all nine confirmed, three more fixed. N1: a renewal keeps owning liveness through BOUND until the switch has reset the timers, and the supervisor forgets an END verdict while a renewal owns liveness, so a renewal about to bind is never ended and a handback gets the full 1 s grace. N2: signals a replaced writer wrote but had not flushed go back to the head of the queue; microphone and camera signals are not re-queued, because the re-assertion after the switch sends their current state. N3: an armed phone that finds no session or key refuses and disarms instead of staying armed.
