# Design M: messaging v2 (chat threads, files of every format, receipts, forward secrecy, carriers)


**Goal.** A person you have verified can send you text, voice notes, photos and any file (a PDF, a zip, a video, an APK) with the same trust model as a call: end to end encrypted, authenticated to the contact, no server, no internet. Delivery is delay tolerant: phones that are adjacent exchange at once, and later (phase 3) other phones may carry sealed bundles between people who are never in range at the same time. Messaging must never steal the radio from a live call or stream.

**What users get** (the phase that delivers each is in the plan below).

- One *conversation* per contact: a thread with bubbles, date separators, a composer, and honest per-message state (waiting, sending with progress, delivered, read, not sent). Phase 1.
- An attachment sheet: Photo or video, File, Voice note. Photos are made smaller by default with a visible "Original" choice (and the location data is removed either way when we re-encode). Any file type can be sent up to 64 MB. Files above 1 MB are not pushed at the receiver: the receiver sees a small card (name, size, picture thumbnail), downloads on a tap or automatically up to a chosen size, and can cancel and resume. Phase 1.
- Receipts: two checks when the contact's phone has the message, filled checks when they read it (read receipts are off by default and only work when both people turn them on). Phase 1.
- "Keep the link open" while a thread is on screen and the contact is nearby, so text arrives within about a second instead of at the next exchange. Phase 1.
- Forward secrecy for stored messages: each message is protected by a key that the recipient deletes after opening it (a prekey, or from phase 2b a Double Ratchet message key), so a seized phone or a later key leak cannot decrypt old bundles that carriers or the sender still hold. Phase 2 and 2b (before any carrier ships).
- Other phones carrying sealed bundles for you (opt-in, 64 MB, pauses on low battery). Phase 3.
- Not in this design: group chats (sketched, phase 4), reactions, typing indicators, link previews, message editing, multi-device, cloud backup, video transcoding.

## Why v1 is not enough (facts from the code, 2026-10-12)

| v1 behaviour | Consequence | Fix in this design |
| --- | --- | --- |
| `MessagesActivity` lists "Inbox" and "Sent" separately and picks the contact in a spinner | No conversation; a reply is not next to what it answers | One thread per contact (the 16-byte conversation ID already exists in `BSM1`, derived from the two node IDs) |
| Cards (`BCC1`) are a second contact system: paste text, compare a 20-digit safety number, accept | Two ways to add a person, easy to skip verification | The mailbox card travels inside the verified-contact flow; a card whose identity key hashes to an already verified contact is accepted without a second comparison |
| Attachments: photo (1280 px, 300 KB target) and voice (2 min); whole message is one `ByteArray` and one bundle of at most 256 chunks (2 MiB) | No files; large memory use per message | `ATTACHMENT` manifest plus 1 MiB segments, streamed from and to disk |
| Opened messages are deleted at the bundle's expiry hour (default 72 h) | Conversations vanish after three days by default | Delivery lifetime and retention are separate; default is keep until deleted |
| An exchange needs both phones on the Call screen and a tap, or the auto-sync policy (65 s to 10 min backoff) | Chat feels like e-mail by pigeon even when the person is next to you | A per-thread live link (below) |
| Per exchange 8 MB, per neighbour 20 MB/day, 50 bundles per sender per day, own queue 32 MB | A single 10 MB file cannot be sent | Two admission tiers: accepted contacts get large allowances, unknown adjacent phones (future carriers) keep today's numbers |
| Receipt = class 0 bundle with an hour | Fine, but no read state, no batching | `RECEIPT` with a status and up to 64 IDs |

## Decisions

**M1. One conversation per contact, one contact system.** A thread belongs to an accepted contact. Messages from non-contacts stay refused (Design A QA2). The mailbox card is exchanged inside the authenticated link as today (`CARD 9`); a card whose identity key hashes to the fingerprint of a verified contact (the Contacts tab, `BVMID1`/`BVMID2`) is accepted at once, because the user already compared that identity in person and the card is signed by it. Any other card stays pending behind the safety-number comparison. If a verified contact's card arrives with a different identity or mailbox key, the thread shows "<name>'s keys changed" and sends nothing until the user compares again (PATTERNS 8.3; today a changed key is silently ignored). A card is accepted only if its `created ms` is greater than the stored one for that identity (a replayed old signed card cannot roll a key back). A first message can be written as soon as a contact exists; it waits until the two phones meet. Migration from v1: accepted cards become threads, v1 messages stay readable as legacy rows, and messages still queued unsent in the v1 outbox are re-sealed once as version 3 bundles at the first v2 start (the v1 bundle is withdrawn). A peer that answered a v2 `HELLO` with `DONE(error)` is shown in the thread as "Their app is older: update to receive" until it answers a v2 hello.

**M2. What is a message.** Content `BSM2` (PROTOCOL) replaces `BSM1`. Kinds a v2 sender emits: text (at most 8000 bytes, which with the header fits one chunk), attachment manifest, segment, receipt, prekeys (phase 2). Voice notes and photos are attachments with a presentation hint, not separate kinds, so they share download, resume and storage. Location stays defined and unused. A thread is keyed by the *authenticated* sender (the contact whose slot opened the bundle): the conversation ID inside the message must equal `SHA-256(sorted node IDs)[0:16]` of this phone and that sender, and `reply-to` is honoured only for a bundle in the same thread; a mismatch is refused, so a contact can never file a message into another contact's thread. A reader that meets an unknown kind or a newer bundle version stores nothing, replies `REFUSE invalid` and counts the event; it never shows a half message. Every message carries a random 16-byte *message ID* inside the sealed content; the receiver deduplicates on (authenticated sender, message ID) as well as on the bundle ID (finding 3), and a bundle header must have exactly one key slot (finding 8).

**M3. Attachments of every format.**

- *Inline or segmented.* A file of at most 1,000,000 bytes travels inside its manifest bundle (inline): one bundle, no second step, and it is carriable by phase 3 couriers. A larger file (up to 64,000,000 bytes) is cut into segments of 1,044,480 bytes (255 blocks of 4 KiB, which keeps a segment inside 128 chunks and block aligned in the vault). Each segment is its own class 4 (bulk) bundle. The manifest lists, for every segment, its 32-byte bundle ID and its chunk count, so the receiver can verify before it fetches, knows what to ask for and what each segment must contain, and checks a whole-file SHA-256 at the end. The manifest also carries a random 32-byte *file key*; each segment's content key is `HKDF(file key, index)`, so a segment bundle needs no key slot of its own (its header carries only the pair tag). One authenticated, forward-secret seal (the manifest) therefore protects the whole file, instead of one prekey per segment (review M-R2).
- *The receiver pulls.* Bulk segments are never listed in `SUMMARY`. The manifest (small, class 0 to 2) arrives first and creates a card in the thread. When the user taps Download (or the automatic limit allows it) the receiver sends `WANT` for the segment IDs it learned from the authenticated manifest, with a synthesized admission entry (class 4, the tag of the pair, the manifest's expiry, the chunk count from the manifest). The sender serves them to the authenticated recipient only. This makes the receiver the owner of its airtime and storage (the Knit model), removes the "unsolicited 60 MB" abuse and makes resume natural: chunk bitmaps persist per segment, so an interrupted download continues from the next missing chunk. A WANT for an unlisted bundle is honoured only when the bundle is one of the sender's own bundles addressed to that authenticated peer. A receiver can stop a download with the new `CANCEL` message (the sender abandons that served bundle at the next chunk boundary) and ask again later with a new WANT; chunks that arrive within 5 seconds after a CANCEL are dropped without counting as poisoned or duplicate.
- *Not carried.* Class 4 bundles are refused by carriers (phase 3). A big file therefore needs the two phones to meet; the thread says "Waiting for <name> to be nearby" and shows the size. Files of up to about 1 MB (inline) can travel through couriers. This is deliberate: a 64 MB file cannot fit the measured walk-past window (28 s leaves 0.7 to 1.5 MB), and carrier storage (64 MB) must not be consumed by one transfer.
- *Formats.* No allow-list for sending. Receiving: the file name is a display label only (NFC, path separators, control, bidirectional-format and zero-width characters removed, 96 bytes at most, never a path: files are stored under a local random ID, so a sender-chosen file ID can never collide with or overwrite another file; a repeated file ID with different segment IDs from the same sender is refused). The MIME type is the sender's claim, accepted only as `type/subtype`. The app *sniffs* the bytes itself (magic numbers for pictures, audio, video, PDF, ZIP/APK/JAR, DEX, ELF, PE, scripts with a `#!` line) and the sniffed type overrides the claim everywhere: for the icon, for the preview, and for the type handed to another app. "Open" exists only for a small allow-list of safe sniffed types (pictures, audio, video, PDF, plain text); everything else, and every installable or executable type, has only "Save to Downloads" behind a warning. Open hands the bytes to the system through a `ContentProvider` that is not exported and gives each external app a one-time read grant for that file, revoked when the thread is left or after 5 minutes; it serves through `StorageManager.openProxyFileDescriptor`, which decrypts on demand, caps open descriptors at 4 and wipes its block cache on release, so no plaintext file is created in our storage. The other app can of course copy the bytes it is shown; the guarantee is about our storage. Save copies into the user's chosen location through the Storage Access Framework (outside our encryption, the user's decision). Nothing is parsed, executed or installed automatically.
- *Pictures and thumbnails.* A zero-click decode of attacker-chosen pixels is the classic messenger attack surface, and a size or heap check does not contain a native decoder bug (finding 10). So **nothing is decoded automatically**: a received picture or file shows a generic type icon, its name and size, and a picture is decoded only after the user taps it, from the sniffed header size (header limit 40 megapixels), down-sampled to the display, never at full size, in a service with `isolatedProcess` and no permissions where the platform guarantees one and otherwise in-process with the same bounds (the user chose to open it). The manifest still carries a JPEG thumbnail (at most 16 KiB, header of at most 320 x 320 px) so that automatic previews can be switched on later: `test_mv2_auto_thumbnails` (Experimental, off) may turn on only after an isolated, resource-limited, time-limited decoder is proven on every reference phone (T-M9); until then the thumbnail bytes are carried and never decoded. Hint fields (width, height, duration) never size an allocation.
- *Photos on send.* The photo path re-encodes: EXIF orientation applied first (`BitmapFactory` ignores it), transparency flattened onto white, longest edge 1600 px, JPEG q80, every metadata segment gone, plus a 320 px thumbnail (carried in the manifest, shown only when automatic previews are on). "Original" keeps the pixels: for a JPEG a small segment filter rewrites the file with every APP and comment segment removed (EXIF including its embedded thumbnail, MakerNote, XMP, ICC kept only if requested) and a minimal orientation tag added; for PNG, WebP, HEIC and other formats the bytes go unchanged and the sheet says they may carry hidden data. Video: a lossless remux with `MediaExtractor` and `MediaMuxer` that copies the audio and video tracks and drops the location and device metadata atoms (no transcoding; a compressor is a later option, Q-M10); other files are sent as they are, with the size and the expected time on the learned link rate shown before sending. A video that the platform cannot remux is sent as a file with the warning.
- *Voice notes.* Unchanged from v1 (AAC in MP4, 2 minutes), as an inline attachment with its duration in the manifest.
- *Auto-download.* Inline attachments always arrive with the message. For segmented files: Never, Up to 8 MB (default, Knit's in-mesh tier) or Up to 64 MB, only from accepted contacts, only when no call or stream is running, and only while the contact's share of the vault (25%, M7) has room; anything larger waits for a tap.
- *Size limit.* 64,000,000 bytes (62 segments). The limit follows storage, quota and the time table below, not a Bluetooth maximum: it is a policy number to be revisited with measured goodput (and a Wi-Fi bearer, which would lift it).

**M4. Delivery states and receipts.** Own message states: *Waiting* (queued, nobody to give it to; clock), *Sending n %* (a transfer is running), *Delivered* (the contact's phone holds and has opened the message: two checks; for a file, the card, not the bytes), *Downloaded* (a file whose segments the contact has fully received and verified; shown as "Delivered, downloaded" and the only state after which the sender's sealed segments are deleted), *Read* (filled checks; only with mutual read receipts), *Not sent* (lifetime over, damaged or too many failed attempts; with a Retry that makes a new bundle), and, from phase 3, *Handed on* (one hollow check: a courier holds it, which never counts as delivery, the Meshtastic lesson). Delivered, Downloaded and Read are independent facts, each kept as its own flag per message and set at most once (finding 18): receipts are deduplicated by (bundle, status), so an earlier receipt never suppresses a later one, and a receipt that arrives after the state became *Not sent* still sets its flag; the thread shows the highest applicable state. Delivered comes from the in-session `DELIVERED_LOCAL` when the contact is adjacent, or from a receipt bundle (status 1) when it travelled through carriers; Downloaded is receipt status 3; Read is status 2. Receipts are never answered by another receipt, they batch up to 64 IDs (sent at once in a chat session, batched with a random delay only on the carried path), and they never remove a carried copy by themselves (the recipient's adjacent carrier is told by `DELIVERED_LOCAL`, hop-local, as in Design A). Receipts reveal a coarse hour only. Read receipts are a switch that is off by default and symmetric: a sender asks for one only when its own switch is on, and a receiver answers only when its own is on, so turning it off is invisible and costs you seeing theirs (Signal's rule).

**M5. Ordering and duplicates.** The displayed time of a message is its sender time clamped to `[arrival - 14 days, arrival]`, ties broken by bundle ID, and the sender time must fall inside the created hour of the (carrier-visible) bundle header, so neither a future nor a past clock can place a message out of its real window. A bundle ID is content addressed and a tombstone stays until expiry plus 3 hours (Design A), so redelivery never makes a second bubble; a retry from the user's Retry button is a new message by design. The sender never re-seals a message that was queued, so the same bytes are offered to every carrier (Knit's "sealed once, re-sent verbatim"), except that an authenticated key-gone signal (M9) re-seals it once under the same message ID, so a replacement for an already opened message is dropped.

**M6. The thread link ("chat session").** An exchange today ends when both phones have nothing more to say. When a thread is on screen, both phones have the feature on, the contact is adjacent and neither side runs a call or stream, the exchange stays open as a *chat session*: either side may send a further `SUMMARY` with the new bundle (text arrives in about a second on a healthy link), a `PING` every 20 seconds keeps the connection alive (60 seconds without any record ends it; a PING never counts as transfer progress, M12a), it ends when the thread is left for 2 minutes or after 30 minutes (then re-opens if the thread is still open), and a call or stream ends it within one chunk exactly as today. If both phones have the thread open and each tries to connect, the phone with the lower node ID is the initiator and the other accepts. Starting a call from the open thread closes the session first (the call reuses the same link and endpoint), so the call-setup time with an idle session must equal the control arm (T-M3, T-M14). The responder's 60-second cooldown and 10-per-hour cap stay for unknown phones but are relaxed to 5 seconds and 60 per hour for an accepted contact whose `HELLO` set the chat flag; this means the responder must read `HELLO` before it applies the cooldown (today it checks first). What starts a session is unchanged and honest: a thread open on a phone that discovers the contact (the tab that lists people nearby already scans while it is visible), or the contact's phone scanning and finding this phone reachable. Receiving while the app is in the background is *not* promised in phase 1; it is measured first, with the v1 code and its DEBUG controls, in phase 0 (T-M8) and decides whether phase 3 adds an opt-in background check.

State-machine changes that this needs in the v1 link code (`StoreForwardLink.kt`), each with a JVM test (review M-R8): `onSummary` accepts repeated SUMMARY messages in a chat session instead of failing after the first (`peerSummaryDone`); DONE is held while the session is a chat session and a simultaneous `DONE(IDLE)` with a late SUMMARY is defined (the late SUMMARY is ignored and its bundles wait for the next exchange); the `offered` map is extended as new bundles are created; a bundle may be WANTed again after it was served and finished or after CANCEL (the "repeated WANT" violation then applies only to a WANT for a bundle whose job is still running); the 1,024 SUMMARY-entry limit is per 1,024 *bundles offered*, counted over a window of 30 minutes in a chat session, not per exchange; the tag table is refreshed when a card is accepted mid-session; the connection watchdog is 60 seconds in a chat session while the transfer-progress deadline stays 10 seconds per chunk (120 s total per non-chat exchange); the writer takes work from a priority structure (below) instead of FIFO.

**M7. Storage and retention.** The sealed archive (96 MB cap, unchanged mechanism) keeps only text, listing records and manifests *without* inline data. All file bytes, including inline attachments, go to a *file vault*: one random 256-bit key per file, kept in the file's sealed meta record, and the bytes in 4 KiB AES-GCM blocks (nonce = block counter, AAD = local file ID, block index and a final-block flag, so truncation is detected and a segment can be written at its offset). Default vault cap 1 GiB with a visible "Storage used by messages" row and "Free up space"; no single contact may hold more than 25% of it (the receiver stops asking, and refuses inline attachments with `REFUSE quota`, when that share is full), so one contact cannot starve the others (review M-R11). Retention is independent of delivery lifetime: *delivery lifetime* is how long the network keeps trying (text and inline 3 days, segmented files 14 days; 1, 3, 7 and 14 days remain selectable under Advanced); *retention* is how long a delivered message stays on the phone (default until deleted; an optional per-conversation disappearing timer from 1 hour to 4 weeks, sent inside the message and counted from the first delivery acknowledgement on the sender and from reading on the receiving phone, the Briar rule). A timer shorter than the receiver's floor (1 hour) is raised to the floor, and the thread shows a notice "Messages in this chat disappear after reading" with a Keep action per message, so a contact cannot silently impose "vanish in a second". Approved partial downloads are exempt from the 24-hour stalled-partial eviction (they expire with the message's lifetime). Own outgoing queue: 512 MiB per contact and 1 GiB overall including sealed segments (the segments of a downloaded file are deleted at once). Waiting messages per contact: 100. Sealed bytes are immutable (finding 11): a vault block is written once, a crash retry rewrites it only with identical bytes or uses a new vault file with a fresh key, sealed bundles are retransmitted verbatim, and anything that must change gets fresh keys. Physical accounting and global ingress caps are in M12a. All of it lives under `noBackupFilesDir/store-forward`, is excluded from backup and removed by the emergency wipe, as today.

**M7a. Small before large.** Inside one exchange the writer always serves the smallest waiting class first and interleaves at chunk granularity (Serval's size lanes): a text or receipt written while a 10 MB segment is streaming goes out before the next chunk of the segment, and a segment is never queued ahead of a message. This also bounds the time a live call must wait to preempt, as today. It replaces the FIFO job queue of v1 with a priority structure keyed by (class, remaining bytes).

**M8. Admission tiers.** The v1 numbers (8 MB per exchange, 20 MB per neighbour per day, 200 bundles per day, 50 per sender per day) were written for strangers. v2 keeps them for an adjacent phone that is *not* an accepted contact (the carrier tier of phase 3) and adds a contact tier: 128 MiB per exchange and 512 MiB per day in each direction, 200 messages per contact per day, and a separate allowance of 1,000 receipts per contact per day (receipts and read receipts are bundles but must not eat the message allowance; a bulk segment counts bytes, not messages). A contact is still limited by the receiver's own pull and by its 25% vault share: an attacker contact cannot make the phone store more than it asked for, except inline attachments of up to 1 MB, which are bounded by the 200-message allowance and the vault share.

**M9. Forward secrecy.** The v1 slot derives both keys from the recipient's long-term mailbox key `R`; a later compromise of `R` opens every retained bundle and its sender. Options considered (revised after the second review, finding 20: the first version of this table rejected the Double Ratchet because it "needs ordered, lossless delivery", which is wrong: the Double Ratchet specification supports lost and out-of-order messages by storing bounded skipped message keys):

| Option | What it gives | Cost and risk |
| --- | --- | --- |
| A. One-time and rotating prekeys, one prekey seal per message | Each message (or file manifest) is sealed to a prekey the recipient hands to that one contact in advance and deletes after opening; the long-term keys only authenticate the sender (deniable). With no one-time key left the sender uses a rotating prekey. Never the static key | A continuous dependency on material from the peer: batches, refills, a Keystore alias budget, spent-ID tracking, a `PREKEY_GONE` re-seal path; a contact not met for 21 days cannot be sent a forward-secret message. About 1.6 k lines |
| **B. *A and B side by side, on this app's constraints.*

| Criterion | A: prekey per message | B: bootstrap plus Double Ratchet |
| --- | --- | --- |
| Sending to a contact not met for 3 weeks | Blocked ("Waiting to exchange keys") once the keys' 21-day use window ended | Works; the chain continues without the peer |
| Material needed from the peer | Continuous (20 one-time keys per contact, refills, a rotating key every 7 days) | One bootstrap per direction: the rotating signed prekey plus a few one-time keys |
| Forward secrecy | Per message with a one-time key; up to about 36 days of exposure with the rotating fallback | Per message; skipped keys are the only retained secrets and are purged at the expiry of the messages they could open (at most 14 days plus 2 hours) |
| After a past compromise | Heals as new prekeys are issued and old ones expire | Heals at the next reply (a new DH step); a one-way sender stays on one chain |
| Loss, reordering, duplicates through carriers | Each bundle is independent; duplicates by bundle ID | Skipped-key window (256 per contact); duplicates by bundle ID, and a used key is gone |
| Failure modes found by review | Replay of batches, re-seal duplicates, consumption crashes, exhaustion, Keystore load | State commit on crash, skipped-key flooding (bounded), simultaneous start, a corrupted state needing a visible session reset |
| Header visibility to carriers | Masked prekey ID | Ratchet public key hidden by header encryption (the receiver trial-decrypts at most 3 header keys per session) |
| Size | 1.6 k + 0.9 k tests, 7-8 agent-days | 2.8 k + 1.8 k tests, 15-18 agent-days in total (bootstrap 7-8, ratchet 8-10) |

*Verdict.* The recommendation changes from A to B, built in two steps because A's machinery is B's bootstrap: phase 2 delivers the prekey bootstrap (batches, slot version 4, storage rules below) and, with `test_mv2_ratchet` off, uses it as option A (a prekey seal per message); phase 2b adds the sessions (slot version 5) and `test_mv2_ratchet` on becomes the default after its tests. Both arms stay switchable. The reasons B wins are the 21-day blocking window (a real failure for the off-grid user whose contact is away for a month), the removal of the continuous prekey traffic and the Keystore alias load that produced most of the second review's findings, and post-compromise healing. B costs about 1.8 times as much and brings session-state risk; if the user prefers the smaller step, A alone satisfies the Q10 rule and remains correct. Neither option gives *metadata* forward secrecy: the tag is derived from the static pair secret `Kp`, so someone who later obtains `R` and `S` and holds captured bundles can match their daily tags to the pair and learn who talked on which day, even though the payloads and the sender field stay sealed (finding 5). That is disclosed in the user text; erasable ratcheted tag chains (see M10) are the Experimental route and decision Q-M11.

*What forward secrecy achieves, precisely* (review M-R5, finding 5). `k2` needs `ECDH(S, R)`, so a leaked prekey alone opens only the sender-identity part. Forward secrecy protects *captured or retained ciphertext* (what carriers and the sender's outbox hold) against a *later* compromise of the static keys and of the prekey or message key; it does not protect a seized, unlocked phone (the archive stays readable), a message while its key is still held, or the addressing metadata above. Compromise of `R` lets an attacker impersonate any sender toward that recipient (key-compromise impersonation, as in Noise X). The signature on a prekey batch only stops prekey substitution; it is a non-repudiable statement that the issuer gave these keys to this contact, a small deniability cost that is accepted.

*Rules that apply to the bootstrap (and to A), from the reviews.*
- *No downgrade (finding 1).* Each contact has a pinned minimum security version. Once a contact's phone has sent a version 4 or 5 bundle or a `BPK1`, this phone refuses any lower version from or to it (`REFUSE invalid`, visible in the thread as "Sent without forward secrecy was refused"). Version 2 and 3 bundles are read only on a direct link from a contact whose pin is still below 4; they are never carried and never re-offered to a third phone. Phase 3 carrier admission accepts only version 4 and 5 headers, and phase 3 does not ship until this pin exists.
- *Spent keys stay spent (finding 2).* Key IDs are serial numbers that the issuer never reuses (a persisted counter). The phone that receives a batch persists, per issuer, the set of IDs it has used (as ranges) and refuses a batch entry whose ID is in it or whose ID is already bound to a different key; an equal-generation batch is idempotent. A replayed signed batch therefore cannot resurrect a consumed key, also across crashes (the used set is written before the seal is used).
- *Consumption is one recoverable transaction (finding 4).* Opening a message does: (1) append a journal record "open-intent: bundle ID, logical message ID, key ID"; (2) store the message, the logical ID and the bundle tombstone; (3) delete the key; (4) mark the journal record done; only then is the delivery acknowledged. A restart replays unfinished records forward. A one-time key is *claimed* by the first bundle that opens with it; a second bundle naming a claimed key is refused as a replay even if the key still exists.
- *Budgets (finding 9).* At most 40 unused one-time keys outstanding per contact and 400 overall, counted from the issuer's own records (a peer's `prekeys held` claim only schedules a top-up, never raises a cap); at most 2 batches per hour per contact and 12 per hour overall, including the immediate batch after `PREKEY_GONE`; a slot that fails to open costs the sender (and the supplying neighbour) double the allowance of a good bundle, and more than 20 failed opens per hour from one neighbour ends the exchange.
- *Storage (finding 13).* Every prekey gets its own Keystore wrapping key on every API level (API 31 and later: the prekey itself is a Keystore EC key), deleted when the key is used or expires; the number of Keystore aliases is capped at 200 overall, and contacts beyond the cap are issued rotating keys only until aliases free up. Sub-batches of 5 are not used, because a rewritten file would stay decryptable by older copies while its wrapper survives. The alias creation time and limits are measured on the required phones in a spike before phase 2 starts (blocking). Erasure on flash is best effort and the user text says so; the emergency wipe enumerates and deletes every alias and file.
- *Lifetimes.* Every key carries a `use-until` time of issue + 21 days; the sender never seals to a key past it; the recipient deletes the private half 15 days after `use-until`, so no bundle that was legally sealed can outlive its key. A new rotating prekey is issued every 7 days; up to three are usable at once.
- *Re-seal after `PREKEY_GONE` (finding 3).* Every message has a random 16-byte *logical message ID* inside the sealed content (`BSM2`), and the receiver deduplicates on (authenticated sender, logical ID) as well as on the bundle ID, with the same tombstone lifetime, so a replacement bundle for an already opened message is dropped. A sender re-seals only on a refusal that comes from the authenticated adjacent recipient over a direct link, or on an end-to-end `RECEIPT` status 4 (`key gone`) sealed by the recipient; a hop-local refusal from a carrier never causes a re-seal.
- *File keys are short lived (finding 14).* The file key in a manifest is kept in a separate transfer record, not in the archived manifest, and is erased as soon as the file is complete and verified, abandoned, withdrawn or expired; the vault has its own key. A later compromise of the archive then cannot decrypt captured segments.

The user decides Q10 with these tables; until then phase 3 is blocked.

**M10. Carriers (phase 3).** As Design A v2/v3 with these additions from the reference apps and the reviews. *Two admission paths (finding 7).* The recipient path is v1's: a header is accepted for chunks only after its slot authenticates a contact as the owner of the tag. The carrier path cannot do that (an opaque carrier holds no key) and is charged to the authenticated supplying neighbour instead: strict header decode, class 0 to 3, version 4 or 5 only, at most 256 chunks, every chunk checked against the hash list, expiry inside the allowed window, at most 10% of the carrier quota per tag and 25% per supplying neighbour, and the neighbour's own daily byte and bundle allowances (all non-contact neighbours together are also capped, M12a); a carried bundle is never charged to a contact's sender allowance. Carriers store only class 0 to 3 bundles (never bulk); evict by the bundle's creation hour (global, not the local receive time) then bundle ID, so carriers converge (Knit); keep a seen window of expiry + 3 hours (Kabootar); typed refusal reasons (quota, tag quota, neighbour quota, expired, bulk, version); quotas rebuilt by scanning at start; receipts return as ordinary class 0 bundles, batched, with a random 0 to 60 second delay on the carried path. *Copy tokens (finding 16).* Binary spray-and-wait, 6 copies for classes 0 to 2 and 2 for class 3. A hand-over is a two-step journalled transaction: the giver records "handing n tokens", the taker answers `ACCEPT` with the count it stored, the giver commits; a crash between leaves the giver holding the tokens (a duplicate budget is possible, a lost one is not). The last token goes only to a phone that asks for the bundle's tag, which a carrier cannot verify, so the copy limits are cooperative and are not claimed to hold against a malicious carrier. *Digest (finding 15).* `HELLO` carries the first 8 bytes of SHA-256 over the sorted list of (bundle ID, chunks-held bitmap hash) of everything held; equal digests may skip the SUMMARY but never replace it: a full SUMMARY is exchanged at least every 6 hours per neighbour regardless. XOR of IDs is not used (manipulable, blind to partial chunks). *Per-message tags (finding 17, Experimental, blocking before it is promoted).* Directional chains: `Kdir = HKDF(Kp, "tag-dir" || sender node ID || recipient node ID)`, `tag n = HMAC(Kdir, counter n)[0:8]`, the sender persists its counter, the receiver precomputes the next 32 and keeps skipped tags for up to 256; on every direct meeting the `HELLO` carries each side's next counter so a stranded window re-aligns over the authenticated link, and the daily tag stays valid in parallel. Opt-in "Help carry messages" (default off, 64 MB, 50 MB/day out, paused below 20% battery), a visible "Carrying n messages" and "Clear carried messages".

**M11. Metadata exposure.** Phase 1 puts nothing on air that the link does not already protect: an eavesdropper sees one call-transport link; the adjacent contact learns what it is sent. For carriers (phase 3) the earlier table overstated the hiding of the recipient (finding 6); the corrected table:

| Observer | Learns | Does not learn |
| --- | --- | --- |
| Radio eavesdropper | Link presence, sizes and timing of records | Anything inside BMS1 |
| Adjacent phone that is a contact | The conversation, because it is the endpoint | n/a |
| Carrier | Which adjacent phones (by link identity, which rotates with the discovery epoch when rotating IDs are on) handed it each bundle and took it; created and expiry hour; class 0 to 3; padded size band; a pairwise daily tag (unlinkable across days and pairs, but shared by every bundle the pair creates that UTC day, and constant for one bundle's life); the copy count it was given | The sender's or recipient's node identity from the bundle itself, the content, attachments (bulk is never carried) |
| Carrier that hands a bundle to its recipient | That the phone it is talking to is the recipient of tag T (the recipient asks for the tag, takes the bundle and sends `DELIVERED_LOCAL`), so it learns the recipient's link identity for that epoch, and with the neighbour that gave it the bundle, a candidate pair | The content; which node ID the link identity is, when rotating IDs are on and the carrier is not a contact |

**M12. Abuse and bounds.** All numbers are hop-local and per authenticated adjacent identity unless M12a says global. Reassembly is keyed by (peer, bundle ID) and bounded by the header's chunk count (at most 256), each chunk is checked against the hash list before it is stored (poisoned chunks counted, four abandon the session), a segment ID not named by an accepted manifest is never fetched, manifests are bounded (name 96 B, MIME 100 B, thumbnail 16 KiB, 62 segment entries), decoders run only after a tap and on size-bounded input (header check at 40 megapixels but decoded down-sampled to display size, thumbnails JPEG only and at most 320 px), and the reader of any message runs inside a catch that turns every failure into a counted refusal. Per contact: 100 waiting messages, 200 messages and 1,000 receipts per day, 512 MiB per day, 25% of the vault; per exchange 128 MiB; unknown adjacent phones keep the v1 numbers. Proof of work stays an optional phase 3 measure for non-contact senders.

**M12a. Physical accounting, global caps and control budgets (findings 12 and 19).**
- *Reserve before accepting.* Before a `WANT` is sent or a `HEADER` accepted, the receiver reserves the physical bytes the transfer can occupy: staged ciphertext of the bundle (at most 2.1 MB per segment), the final vault bytes, the metadata rows and the tombstone. Staged segments are imported into the vault and deleted one at a time, so the peak for a file is vault size + two segments. Reservations are summed over every transfer in flight; a transfer that does not fit is refused `quota`. The free-space floor is 200 MB of the device's storage: below it, nothing new is accepted.
- *Global ingress.* Besides the per-neighbour limits, all non-contact neighbours together may supply at most 64 MB per day and 16 MB per hour, all contacts together at most 1 GiB per day; at most 8 bundles are in flight (receiving) at once; metadata is bounded (20,000 seen/tombstone entries, 2,000 bundle records, 2,000 archive rows), so rotating link identities (identity churn) cannot multiply the allowance.
- *Liveness is not progress.* A link has two independent deadlines: connection liveness (any valid record, a PING counts; 60 seconds in a chat session) and transfer progress (a transfer that has a running job must move a chunk every 10 seconds, whatever pings arrive; 120 seconds total per non-chat exchange). A chat session that is idle but live ends after 30 minutes or 2 minutes without the thread open. A PING more often than once per 10 seconds is a protocol violation.
- *Control budgets.* At most 20 control records per second and 2,000 per 10 minutes per link (SUMMARY, WANT, CANCEL, PING, receipts in flight); at most 60 `CANCEL` per minute and 30 `WANT` for the same bundle per hour; at most 30 asymmetric operations (slot opens, signature checks) per exchange from an unauthenticated or non-contact peer. Exceeding a budget ends the exchange with `DONE(rate limited)`.

**M13. Groups (phase 4, sketch only).** Not in this design and not wired: until groups are designed, bundle headers of versions 3, 4 and 5 are required to carry **exactly one** key slot, and a decoder rejects any other slot count (finding 8: a slot authenticates the fixed header fields and the hash list but not the other slots, while the bundle ID hashes every slot, so extra slots could be changed to mint a new ID for a message the recipient can still open and bypass ID-only deduplication). A group design must therefore add a signed *logical message ID* and a commitment to the complete recipient set (a hash of all slot tags in every slot's AAD), a creator-signed roster with an epoch and a takeover check (bitchat `GroupProtocol.swift:63-71`), a re-key on every roster change delivered as a bundle (bitchat's weakness is that offline members miss it), the sender authenticated inside each slot as today, and per-member read receipts shown as counts. Group calls and group chats share the roster; design it once with Design B. Not scheduled.

## Throughput and the sizes that make sense

Goodput here is link payload including a few percent of framing (hash lists, tags, 8 KiB chunk records); connection setup adds 2 to 6 s once per session (not per message in a chat session). Planning rates are the measured ones: healthy 300 to 1000 kbps, the weak ASUS to A15s GATT pair about 65 kbps. A walk-past contact (28 s) leaves 0.7 to 1.5 MB.

| Item | Bytes on the link | 1000 kbps | 300 kbps | 65 kbps |
| --- | ---: | ---: | ---: | ---: |
| Text, receipt | about 1.3 KB | under 1 s | under 1 s | under 1 s |
| Photo, default (1600 px) | 300 KB | 2.5 s | 8 s | 38 s |
| Voice note, 2 min | 360 KB | 3 s | 10 s | 46 s |
| Inline limit | 1 MB | 8 s | 28 s | 2.1 min |
| File | 10 MB | 82 s | 4.6 min | 21 min |
| Largest file | 64 MB | 8.8 min | 29 min | 2.3 h |

So: text, photos and voice notes are comfortable everywhere; a file of 1 MB can complete in one walk-past; 10 MB is a sit-together transfer (and a weak pair needs a coffee); 64 MB is practical only on a healthy link and with a Wi-Fi bearer would be minutes. The send sheet shows the estimate from the learned rate for that contact, and a transfer that is slower than its estimate says so.

The permission is asked once, when the first conversation opens (Android 13+); a refusal is respected. Nothing is posted by a process that was restarted without the switch on. One reading choice: "FLAG_SECURE-sensitive" is applied as "a message meant not to persist (a disappearing timer), or whose text is not fully shown, never gives text to the notification shade".

## Dial failures, cooldown after a lost link, progress-aware total, and the aligned-writes A/B (2026-10-13)

**1. The A15s dial to the ASUS failed 6 of 7 times.** Symptom: the A15s (OPPO, Android 10, GATT client) connects, subscribes, requests 2M and the exchange never gets the peer's link hello; about 5 s later it reports `EOFException`, and the ASUS (GATT server) reports `incoming_handshake: result=failed | reason=EOFException` a further 5 s later. In the type-b failures the link hello completed and the exchange then crawled or died within 15 s (`helloMs` 1.0 to 2.5 s instead of 0.3 s, `hello=-1` and `INTERRUPTED` or `TIMEOUT` at 5 to 13 s). The ASUS-initiated exchanges (ASUS central) were 100% good in the same runs. Cause: the GATT server read path is not at fault (the CCCD write, MTU 517 on both sides and the first writes are ordered correctly: Android delivers the stack's one-way server callbacks to the app one at a time and in order, and the pipe exists before the first write is delivered). The failure is the one already measured for calls with HCI snoop (`AdaptivePhyMemory.SETUP_STALL_MS`: with the A15s central to the ASUS, the ASUS to A15s direction stops right after LE PHY Update Complete on 2M; the A15s times out 5 s later and the ASUS 5 s after that). The log timing matches exactly: every ASUS-side EOF came 4.9 to 5.0 s after the A15s side, and the A15s side came 5.0 s after the PHY update. The call dial has had the 2M protections since 2026-10-10 (stall guard, one 1M retry to the callee's current advertisement, bad-2M memory); the message-exchange dial (`startMessageSync`) opened its link with the endpoint PHY and none of them. Fix: `MessageDialPhy` gives the message dial the same three protections plus an early-loss rule (an authenticated 2M exchange that died within 15 s with no HELLO and no chunk marks the peer bad on 2M). Switch `test_message_adaptive_phy` (default on; SWITCHES). Re-check: A15s dials the ASUS 10 times, expect `adaptive_phy: link=message ... setup_stall` then `link_phy ... effective=1M` on the first, 1M from the second on, all complete; and the preservation arms (ASUS dials the A15s, S24 and M31 pairs unchanged on 2M).

**2. The proto=1 attempt before the proto=2 session is not a second dial.** The app starts one link per `sf_sync` control or tap. `proto=1` on a session line only means "the peer's HELLO was not read": a responder that refuses with `DONE(rate limited)` answers before its own HELLO, and a link lost before the HELLO never learns the version. No peer was marked legacy in these runs (no `does not speak Messaging v2`, `PEER_APP_OLDER` or `outcome=FAILED`). What did produce extra attempts: (a) each admitted exchange that the link cut before anything moved still stamped the responder's 60 s per-neighbour cooldown, so the retry 46 s after a failed A15s dial was refused `RATE_LIMITED` (10:38:35 interrupted, 10:39:21 refused); (b) the driver's own `sf_sync` controls arrived inside the cooldown of the previous finished exchange (for example 16 s and 22 s after a completed one), which the cooldown correctly refuses. Fix for (a): the responder gives the 60 s spacing back when an admitted exchange ends `INTERRUPTED` or `TIMEOUT` with no chunk moved and nothing opened (`NeighborLedger.refundCooldown`); the hourly count is not refunded, so connect-and-vanish is still bounded to 10 an hour (60 for a chat contact). (b) is the cooldown working; a driver that wants a second exchange waits 65 s (the auto-sync interval already does). Not changed: a v2 pair that both offer `CHAT` is already admitted after 5 s.

**3. The 120 s total limit cut slow transfers.** The A15s answering (GATT server, notifications) moved 164 chunks (1,337,296 bytes) in 120 s at 89 kbps: the first 1 MB segment (125 chunks, 1,017,808 bytes) finished at about 91 s and the next queued bundle was cut after 39 chunks, so the session ended `TIMEOUT`, the cut bundle waited for another session behind the cooldown, and a 5 MB file (about 1.05 MB per segment, 4 segments) needed about four sessions, each with a fresh link; with `test_gatt_aligned_writes` it moved 236 chunks at 128 kbps and still hit the limit (11:10:41: one segment complete at 64 s, a second cut at 54 of 128 chunks). The fixed total remains right for a quiet or stuck exchange, wrong for one that is moving. Now (non-chat, v2 only): the total is extended while the last 4 chunks (either direction) all moved within the last 10 s, up to `sessionHardCapMs` = 15 minutes (8 MB per exchange at 89 kbps is about 12 minutes); the 10 s liveness and 10 s progress deadlines are unchanged and still fire at once on a stall, and a trickle (one chunk per 9 s) passes progress but is cut at 120 s. v1 exchanges keep the fixed total. Switch `test_mv2_progress_total` (default on; off is the fixed 120 s). Re-check: a 5 MB file A15s to ASUS in one session at about 89 kbps (about 7.5 minutes) and a stalled link still ending after 10 s.

**4. The chat session outlived the opener's thread.** `ChatPresence.lastInterestMs` returned "now" whenever the app was in the foreground, on the phone that dialed too, so the dialer's `tick()` never saw its thread-left grace run out (`sf2_thread_close` on the opener, no `chat end why=thread_left` for 8+ minutes with both apps in front). Design M6 lets the foreground keep a session only on the *answering* phone. Now the tick ignores the foreground screen for a session this phone dialed (`StoreForwardLinkSession.isInitiator`); the dialer ends it with DONE(IDLE) about 2 minutes after leaving the thread, and an answering foreground phone still cannot hold it alone. Dial ownership: when both threads are open the lower node ID dials and the higher dials itself 4 s later; a phone with only its own thread open dials whatever its ID, so a failing lower-ID dial (the A15s) is already backed up by the higher-ID phone when its thread is open. No role swap was added: with item 1 fixed the failing dial is the exception, and a swap would need the other phone to hold a thread it does not have.

**A/B: `test_gatt_aligned_writes` on the A15s answering direction (candidate device-family policy, proposed, not promoted).** ASUS dials, A15s answers and sends a 1 MB file; alternating arms, three runs each, same pair, same placement, same build (f0a89e03), 120 s window (the exchange hit the total limit in all six, so goodput is read from the window):

| Arm | Run times | Chunks in 120 s | Goodput kbps (active) |
| --- | --- | --- | --- |
| off (3 x 512-byte-value notifications = 3 LL PDUs of 251+251+17) | 11:07, 11:13, 11:18 | 164, 164, 165 | 89, 89, 89 |

The ratio is +44% (236/164 = 1.44), reproduced exactly three times in each arm, and it is the prediction of the design: 88 to 96 kbps is one 251-octet PDU per 15 ms connection event, so the A15s controller as peripheral sends one data PDU per event and the value size decides how many events a notification costs (3 versus 2). The same phone as central sends 600 to 700 kbps with write commands (several PDUs per event), so the limit is peripheral-role scheduling, not the radio. Proposed entry for the DeviceFamilyPolicy registry (nothing is promoted: the registry needs official sources and test data beyond the two local phones): id `gatt-aligned-values-one-pdu-peripheral`, matcher = OPPO CPH2xxx / the A15s SoC and Bluetooth stack family on Android 10 AND the local role is GATT server AND `ConnectionParameters` show one PDU per event (measured, not assumed); behaviour = size notification values to whole 251-octet LE data PDUs (`gattValueBytes(mtu, alignToLePdus = true)`), off-switch `test_gatt_aligned_writes=false`; confidence = low until a second phone of the same family shows it; sources still to cite: Bluetooth Core Specification Vol 6 Part B 4.5.10 (data length extension, 251-octet data PDU payload), Vol 3 Part A 3.2.8 (L2CAP basic header) and Vol 3 Part F 3.2.9 (ATT_MTU and the 512-byte attribute limit), the AOSP GATT server notification path (`gatt_sr.cc`), and a vendor or chipset note on peripheral-role PDUs per connection event, none of which was checked in this session. Until the registry entry is reviewed, the switch stays Experimental and off by default (SWITCHES).

## A15s as a sender: the 2M link dies on streams and calls, and the stream path had no protection (2026-10-13)

**Roles.** A stream source dials the viewer: the A15s source is the GATT client and LE central, writes ATT write commands (opcode 0x52) to the ASUS server, and the ASUS answers with notifications. A call dialed by the A15s has the same roles. The pair that works (ASUS source or caller to the A15s) has the A15s as peripheral.

**Which side closes first, and why.** The A15s link layer, by connection timeout. In all nine stream attempts that ended on their own, the A15s stack reported `onClientConnectionState status=8` (HCI reason 0x08) and the ASUS reported `Disconn Complete reason=8` 5.0 s later (the two clocks differ by 2.45 s, read from the matching PHY-update callbacks); the A15s stops transmitting when it gives up, so the peripheral's own 5 s supervision timer starts there. No local close, no status 133, 62 or 143 and no `congested` on the A15s side. `Immediate child control channel stopped; closing the link: EOFException`, `Bluetooth stopped: EOFException`, `GATT input interrupted` and the ASUS `GATT sender disconnected (end of stream)` are consequences, not causes. Time from the 2M PHY update to the A15s timeout: 7.45, 6.08, 17.65, 7.86 s (cold-1), 8.59, 10.81, 8.60 s (cold-2), 7.78, 5.38 s (control-1); the A15s last heard the ASUS 0.4 to 12.7 s after the PHY update (timeout minus 5 s), so the failure is not a fixed offset from the switch. Two more attempts ended by an app close after the link crawled (control-1: one blocking write took 8.0 s, TX 9 kbps, queue age 7.9 s).

**Which direction dies.** Peripheral to central, on 2M. The ASUS kept hearing the A15s until the A15s gave up (its timeout came exactly 5 s later), while the A15s heard nothing from the ASUS for the last 5 s. Around the switch the central to peripheral direction also stalled once: in `stream-cold-1` the 357-byte end-to-end hello write, queued on 1M just before the update, reached the ASUS 2.45 s later, after which the ASUS replied, and the A15s's timeout (timeout minus 5 s) puts its last reception at about that reply. In the call (`call-control-3`) the ASUS logged `onServerCongestion congested=true` that never cleared and an L2CAP queue of 15 packets against a quota of 20, which is a controller not getting acknowledgements. Same signature as the earlier HCI snoop (`AdaptivePhyMemory.SETUP_STALL_MS`). Logcat cannot separate the A15s receiver from the ASUS transmit path: that needs the HCI snoop (the A15s reports `mSnoopLogSettingAtEnable = full`).

**What it is not.** (1) The encoder: attempts 1, 2 and 4 of `stream-cold-1` died before any encoder was started (libaom first ran at 15:35:43), encode p95 was 48 to 64 ms (load about 0.6 to 0.7 at 320x240@10 and 640x480@14.7), and the link layer timer runs in the controller. Two attempts did die 0.4 s and 3 s after the encoder started, so a contribution on top cannot be excluded, but it is not needed. (2) Connection priority: HIGH on both, 7.5 ms then 15 ms, identical in the attempts that failed and (messages) in the 1M dials that worked. (3) Scanning: the A15s scanner (mode 2) was running in `stream-cold-1` attempt 1, but in `stream-control-1` attempt 1 it stopped (`source slots full`) 0.9 s before the last reception and the link still died. (4) Wi-Fi: both phones logged `Wi-Fi not connected`. (5) A stream-only write path: calls and streams fail the same way.

**1M works.** `lane3-asus-a15s-m31-20261013/b5-mv2-33b0b869` (message dial, same pair and roles): the first 2M link was closed at the 3 s stall guard, the 1M retry found the ASUS's new advertisement after 3.9 s and completed the exchange; the next dials started on 1M (`reason=remembered at=connect`), set up in 1.3 to 1.8 s and read the peer hello in 0.26 to 0.34 s (the `RATE_LIMITED` results are the responder's 60 s cooldown, not the link).

**Why the stream kept failing.** The call dial remembers a hop peer that went bad on 2M and starts the next link on 1M (`AdaptivePhyMemory`), the message dial got the same in `MessageDialPhy`, but the stream source had only the lookup: nothing ever recorded a bad peer for a stream, so every redial (the viewer re-requests about 8 to 13 s after each loss) used 2M again, for the whole run.

**Why the call looked different (symptom b).** `b2-weaklink-ab/call-a15s-asus-control-r1`: the stall guard fired correctly at 3.005 s and the A15s closed its link, but the ASUS (callee) kept the dead link: its disconnect callback came about 11 s later (`incoming_handshake: result=failed | reason=EOFException`, then 1.6 s to advertise again), so `rediscover=none` after 8 s, the retry connected to the old address and timed out after 12 s (`Call could not connect: Timed out connecting GATT video`). ## A15s as a sender: the alive-but-stalled 2M link (b10-97a95ad4 defaults run d2, 2026-10-13)

**What happened.** Hop authentication took 0.84 s on 2M, the end-to-end handshake finished 0.6 s later, the encoder started at +1.2 s. Then the A15s wrote 7 to 13 kbps for the whole 90 s: the writer blocked 99 percent of every window (`flush p95 3.6 s`, `frame-call p99 4.5 s`), the sender queue grew to 2,850 records (65 s of video), and the ASUS showed 10 frames and then a frozen picture. The link itself stayed up: 95 authenticated heartbeats from the ASUS arrived (about one per second), so there was no supervision timeout, no heartbeat timeout and no early-loss line. The A15s transmit direction on 2M was almost dead while the receive direction was fine.

**Why nothing fired.** (1) The early-loss rule needs the link to end (connection timeout, heartbeat timeout or a setup the owner closes); this link never ended. (2) The one-PDU-per-event rule did evaluate it after 18 s of backlog and returned `kept | kbps=7 | blocked=0.99`: `AdaptivePhyPolicy` deliberately keeps 2M when the mean is under a quarter of one PDU per event ("far below one PDU per event is a stalled link", added for mesh4-7a6c401c 0001, an ASUS relay's downstream link at 8 kbps while it was a peripheral upstream) and it decides only once per link, so the stall was never judged again. The exemption was written for a relay's scheduling collision; here the sender is a plain single-link source. Only d2 of the b10 runs ended this way (every other 2M link either died, setup-stalled, or sat at 87 to 90 kbps and moved).

**What "BLE GATT source slots full; viewer discovery stopped" meant.** Only that the source's admitted fan-out is one child (`Source fan-out: 1 children from measured BLE GATT: probe 734 kbps`) and that child had just authenticated, so the broadcaster stopped advertising for more viewers (it restarts when the slot frees). It is a normal line (it appears in every authenticated single-child stream) and was not related to the stall.

**Fix (`test_stalled_2m_move`, default on; control arm `=false`).** The policy now reports that case as `STALLED` instead of `KEEP`, and `AdaptivePhyLink` decides: a stalled writer on a link that is not a relay's own (`RelayUpstream` plus `relayPhyGuard`, the original mesh4-7a6c401c case) and whose peer is still heard (the inbound pipe received any record within 4 s, `GattBytePipe.heardWithin`) moves that link to 1M and records the peer bad on 2M (`reason=stalled_one_way`), exactly like the one-PDU move. A relay's links and a link the peer is not heard on keep 2M and remember nothing (a dead link belongs to the timeouts). Replay: `AdaptivePhyPolicyTest` feeds the d2 writer profile (7 kbps then 9 kbps, 99 percent blocked, 15 ms interval) and expects one `STALLED`; the 40 kbps band still moves as a one-PDU link; the relay, silent-peer and control cases keep.

**Recommendation, not implemented: drop the backlog built on the bad PHY at a PHY move?** For a live stream I recommend yes, once, at the move, and only when the queue is already older than the viewer can use. At the move the queued records were produced for a link that is gone; in F the queue was 6.7 s and drained to only 4.5 s in the next 60 s (fixed 300 kbps over a 90 to 157 kbps link), 63 to 69 percent of the run frozen, and in d2 it was 65 s: content that old is not live video, and the viewer's playout window (about 2 s) can never absorb it, so keeping it buys no continuity, only delay on top of the freeze. The user's no-frame-loss preference is about not discarding frames to hit a latency target while the viewer can still show them; a one-time catch-up skip when the backlog exceeds roughly twice the viewer playout (about 4 s), to the next keyframe (request one), loses frames that were already useless and then runs at the new link rate. It is no substitute for rate control: a fixed-rate stream above the link's rate grows its queue again at the excess rate, so the skip should log a notice and the continuous answer stays Automatic rate control (the fixed-rate runs are a test artefact). I would ship it as an Experimental, default-off switch (`media age` family), A/B it on the ASUS to A15s stream (F and b10 3-asus-src), and judge it by frozen percentage and the age of the first frame after the move, with the loss of the skipped frames reported next to it; calls already have the bounded-age experiment and need a separate decision.

## A15s as a sender, the backlog skip at a PHY move (Experimental, 2026-10-13)

**What it does** (`test_phy_move_skip_backlog`; default on for fixed-rate streams since 2026-10-14, off with Auto quality, SWITCHES). When a live stream sender's own link moves from 2M to 1M (`AdaptivePhyLink` after `one_pdu_per_event` or `stalled_one_way`; a relay's moves and the relay forwarder never call it), `skipBacklogAfterPhyMove` compares the age of the oldest queued video with `PhyMoveSkip.thresholdMs(viewerPlayout)` = max(4 s, 2 x (assumed 250 ms base + the delay the viewer reported)). Above it, `shedAtomically` removes the queued video with the existing codec-safe plan: everything before the newest keyframe that is still inside the viewer's playout, or all queued video when none is, plus dropping arriving inter frames until a keyframe arrives (re-requested every 1.5 s through the same path as the bounded-age experiment, at most 15 s). Audio, codec configuration, rotation and lifecycle records are never touched, and calls and audio-only live never skip. Line: `BENCHMARK phy_move_skip: role=stream_tx | skipped=true | skippedRecords= | skippedAgeMs= | thresholdMs= | viewerPlayoutMs= | awaitKeyFrame= | queueAfter=`; `skipped=false` is logged when the switch is on and the queue is younger than the threshold. Tests: `PhyMoveSkipTest` replays the 6.7 s backlog (all video dropped, audio and configuration kept, a fresh keyframe becomes the resume point) on a real queue.

**What it is not.** It does not change the rate: a fixed-rate stream above the new link's rate grows its queue again at the excess (the F and 3-asus-src runs are fixed 300 kbps over a 90 to 157 kbps link). Automatic rate control stays the continuous answer; a viewer that hears the skip as a jump is the price for not showing seven seconds old video.

**A/B plan.** ASUS source to A15s viewer, GATT, stream 640x360@15 fixed 300 kbps (the F and b10 `3-asus-src` cases), frozen APK, `test_reset_learned_state` before each run so the 2M start and the move recur, 90 s, three runs per arm, same placement, alternating arms: control (switch absent) against `test_phy_move_skip_backlog=true`; add a third pair of arms with the stream under Automatic rate control to separate the skip from rate control. Read: the `adaptive_phy ... to=1M` line (move time), `phy_move_skip` (skipped records and age, awaitKeyFrame), the viewer's frozen percentage, longest stall and the age of the first frame after the move (media-age lines `videoQueueAgeNowMs`), and the sender queue age at 30, 60 and 90 s. Pass reading: frozen percentage falls and queue age after the move stays under the threshold, with the number of skipped frames reported beside it. A run in which the move does not happen proves nothing about the skip (log `skipped` absent). Preservation: S24 to M31 and ASUS to M31 streams, a relay chain and a call with the switch on show no `phy_move_skip: skipped=true` line.

## Audio chain ASUS to M31 (relay) to A15s: not a regression of the guard, a dead anchor followed by a stale dial (2026-10-13)

**Question.** Did the A15s's hop stage get slower (2M setup, stream PHY memory, setup-stall logic, `phy_after_auth` plumbing) or does the guard see audio-only children differently? **Neither.**
- No commit since the passing builds touches `ReceiverStreamForwarder.kt`, `RelayChildStallGuard.kt` or `RelayEstablishFallback.kt`; the `GattVideoClient.open` changes (deferPhy, hooks) leave the request sequence identical while the new switches are off, and the logs show the same order as the passing run (priority, MTU, services, CCCD, PHY request after the 15 ms update).
- The guard measures inbound bytes from the child since the link opened, for audio-only children as for video; its `stage=hop silentMs=2005` means the A15s sent nothing after the M31's hop hello. In the passing run the hop reply took 369 ms (`handshakeMs=369 maxSilentMs=180`).
- The link was dead in both directions from the 15 ms connection update, the signature the guard was written for: music run, M31 central to A15s peripheral: update to 15 ms at 51.19 (M31 clock), PHY request 3 ms later, nothing else; the A15s logs its last reception at 51.39 and its own connection timeout 5.16 s later (56.55), and "GATT sender disconnected (end of stream)" is that timeout, not a close by the M31 (the M31 closed at 53.23, its terminate never arrived). Voice run: update at 17.65, A15s timeout 22.78. b5: the same two lines. That is the Exynos 9611 child anchor landing in a dead part of the parent's 15 ms cycle (relayfix-0725a213: 9 of 55 attempts). The passing builds simply did not draw a dead anchor; three failing chains out of three do not prove a changed rate (two passing, three failing, same pair, random anchor phase), and nothing in the logs shows the stack or the app changing the phase.

**What turns one dead anchor into a failed chain** (this is the defect we own).
1. The guard closes the link at 2.0 s and counts the stall as establishment failure 1 (by design, `isRelayStallEstablishmentFailure`).
2. The child still holds the dead link for about 3 s more, then restarts: its receiver advertising set starts and stops within 6 ms (music: `adv_set_churn start` and `stop` at 56.628 and 56.634 on the A15s) and its route cooldown (8 to 13 s) begins. The relay's scanner sees that single advertisement 3.2 s after the close and dials it.
3. Both dials (the open retries once) end in a 5 s `status 133` (the receiver is gone). The relay counts failure 2 and logs `relay_parent_fallback ... action=withdraw_offer | failures=2 | markMs=300000`; every later request of the child gets `skip_connect` for 5 minutes, so the chain never forms (the A15s's 20 s retries for 10 minutes).
The voice run reached failure 2 differently (two quick 133s while the A15s application was only 4 s old, then a connected link with a dead anchor), so this fix does not cover that start; see "Not fixed".

**Fix (`test_relay_stall_holdoff`, default on).** `RelayStallHoldoff`: when the guard closes a child link the relay records the time; sightings of that child within 10 s (the child's route cooldown less the time its dead link needs to expire) are skipped with `relay_child_stall: action=holdoff | remainingMs=` and are not counted. A successful end-to-end handshake clears it. The child's real next request dials a fresh anchor phase (about 84 percent of attempts). `RelayStallHoldoffTest` replays the music timeline: without the hold-off the stall plus the first stale dial mark the child for 5 minutes and the real request at +17 s is refused; with it the sighting at +3.2 s is skipped, only the stall is counted, and the request at +17 s dials.

**Not fixed.** (a) A dead anchor itself: the guard shortens it from 5.9 s to 2 s and the retry redraws the anchor; `test_relay_reanchor` and `test_relay_upstream_dck` remain the experiments for avoiding it. (b) The voice-run start: the relay's first two dials failed at once (status 133 after 354 ms and 1,078 ms) 4 s after the A15s application started and 0.7 s after its first advertisement; a relay should not count a failure of the first dials to a child whose advertisement is under a second old, but there is no measurement of what the A15s stack needs at that time, so it is not changed. (c) The A15s was relaunched cold for every chain case in these runs, which is unlike a user's phone; the rerun below keeps the A15s application running.

**Rerun plan.** Same chain (ASUS source, M31 relay, A15s leaf, GATT, Voice then Music), frozen APK from this branch, A15s started at least 60 s before the M31 and ASUS, 10 min each, three runs per preset. Pass reading: a dead anchor, when it happens (`relay_child_stall ... stage=hop`), is followed by `action=holdoff` lines instead of 133 dials, `relay_parent_fallback ... withdraw_offer` does not appear, and the A15s joins within about 30 s of the stall (`relay_child_stall ... result=ok`), with hop 2 units flowing. ## Audio chain: dead-anchor stalls counted apart from refusals (b14 music r1, 2026-10-13)

**What music r1 shows.** The hold-off worked (no stale 133 dials), but the M31 relay's stall guard caught dead-anchor links four times in a row: `relay_child_stall stage=hop silentMs=2004` at 20:45:04.2 and `2005` at 20:45:20.1 (15.9 s apart, outside the 10 s hold-off), then `relay_parent_fallback ... withdraw_offer | failures=2 | markMs=300000`; the mark expired at about 20:50:20 and two more stalls at 20:50:27.4 and 20:50:42.4 withdrew the offer again. The A15s joined nothing for 10 minutes. Four of four links drawing a dead anchor in one session is not the 16 percent per attempt seen in relayfix-0725a213; in this session something about the pair made every attempt dead, and r2 and r3 (same build) formed on the first dial. The guard did its job; the withdrawal policy is what made it a permanent failure.

**Why the 5-minute mark is wrong for stalls.** The mark exists for refusals (GATT status 133/62, the stack reporting HCI 0x3E): the child cannot be connected to, and handing it to another parent is right. A stall means the connection was made and the link layer then delivered nothing after the connection update; the next link redraws the anchor. Treating two of those like two refusals withdraws a reachable child for 5 minutes after 16 s.

**Fix (`test_relay_stall_separate`, default on).** `EstablishmentFailureTracker.onStall`: stalls (`RelayChildFailureKind.STALL`, classified first so a stalled attempt whose message names a 133 is still a stall) have their own list, need 3 within 2 minutes (a dead anchor at 16 percent, three in two minutes is rare in a healthy session) and mark the child for 30 s, escalating 60, 120, 300 s on consecutive marks without a success; a completed end-to-end handshake clears the level. Refusals keep 2 failures within 2 minutes and the 5-minute mark; stalls neither add to nor reset them. Hop-local (a per-child key on the relay, nothing is sent). Log: `relay_parent_fallback ... kind=stall` with `markMs` on a mark and `action=count_stall` for a counted stall that does not mark. `RelayStallSeparateTest` replays the four r1 stall times: the control rule marks at the second and fourth, the new rule marks never, and it covers the 30/60 s escalation, the window, the success reset, the refusal rule and the classifier.

**What this does not fix.** A session in which every link is dead stays dead; the child is simply retried (the child's route cooldown spaces the dials about 16 s apart) instead of locked out for 5 minutes, and after three stalls in two minutes the mark is 30 s, then 60 s, so the relay still stops spending the child's slot on a hopeless pair. The cause of a persistently dead pair is open: the A15s's last reception coincides with the 7.5 to 15 ms connection update in every dead link (b5, b13, b14), which points at that update on the MediaTek peripheral as much as at the Exynos child anchor; the next phone arm to try is the child link without the 15 ms update (priority left at its connection value) on this pair, together with an HCI snoop of the A15s.

**Rerun plan.** Chain ASUS source, M31 relay, A15s leaf, GATT, Music then Voice, frozen APK from this branch, A15s running at least 60 s before the chain starts, 10 min each, five runs per preset, plus `test_relay_stall_separate=false` once per preset. Pass reading: when a stall happens the log shows `count_stall` (and `holdoff` for sightings in the next 10 s) and the A15s joins on a later request within about 40 s (`relay_child_stall result=ok`); `withdraw_offer` appears only after three stalls inside two minutes and then with `kind=stall markMs<=30000`; the control reproduces `failures=2 markMs=300000`. Preservation: refusal cases (status 133 to a vanished child) still withdraw for 5 minutes after two failures; video relay chains unchanged.

## The viewer's input overflow after a stalled-2M move (b1-a5a8f056 stalled2m d2, 2026-10-13)

**What happened.** The A15s wrote 7 kbps for 20 s on 2M, `stalled_one_way` moved the link to 1M at 21:42:01.98 with about 17 s of audio (`audioQueueAgeMaxMs=16652`) and 20 s of video (`videoQueueAgeNowMs=20556` at 21:42:03.8, 25.6 s by 08.8) queued, and the sender then wrote at link speed (48, 62, 78 ... 131 kbps). The viewer logged `GATT video receiver input queue overflowed` at 21:42:14.31, 12 s after the move, and nothing after it: the per-2-s status lines had already stopped at 21:41:50 (12 frames), no `GATT sender disconnected`, no route cooldown, no reconnect. The A15s kept writing and kept receiving the viewer's authenticated heartbeats every second until the end of the capture, so the sender never saw a problem.

**What overflowed.** The viewer's GATT input pipe (`GattBytePipe`), bounded at 512 chunks, a chunk being one GATT value. The audio backlog is the cause: the audio writer takes audio ahead of video, so the first thing the move released was 17 s of 20 ms Opus records (about 850 records of about 80 bytes, one or a few per GATT value), and the viewer's receive loop paces audio at real time by design (`OpusAudioDecoder.offer` applies back-pressure and plays late audio, never discards it; the Android buffer-pool counters in the log show the audio decoder busy for 15 s after the move). 850 small records against 512 chunks overflows after 10 to 12 s, which is the observed time. The decoder input queue (41 frames) is not the culprit: its offer does not block (it drops and asks for a keyframe), and `decoder 1/41` stayed idle.

**Why there was no recovery.** `GattBytePipe` closed itself on overflow, but nothing ended the link: the GATT connection stayed up, the viewer's heartbeat thread kept answering, and the receive loop stayed in its audio back-pressure (the exception that would end it, `Audio decoder stopped consuming for 3000 ms`, only fires when the decoder stops, not when it merely plays slowly). The sender's only liveness test is those heartbeats. So one phone wrote into a dead input and the other reported it healthy until the capture ended: a zombie session. That is a bug whatever the flood was.

**Fixes** (both default on, control arms `=false`).
1. `test_gatt_input_failure_ends_link`: a failing input pipe (overflow, bad chunk header, reordering) cancels the connection, so the sender sees the loss and the existing redial and re-request path recovers. The pipe is also bounded by bytes first (1 MiB, about 16 s of a 500 kbps stream) with a 4,096-chunk bound, so a backlog of small records no longer overflows after 40 KB.
2. `test_phy_move_flood_guard`: at a PHY move on a live stream, media queued longer than 8 s (four times the largest playout) is dropped once: video codec-safely (resume at a queued keyframe still inside the playout, else wait for a requested one), audio older than the viewer's playout (a sender gap to the viewer, which realigns on the timestamp jump; the Opus decoder already handles that case). This is a correctness bound, not the preference the Experimental `test_phy_move_skip_backlog` (4 s video, audio kept) tests: the user direction "late audio is played, never discarded" is about audio that is late within the viewer's window; 17 s of audio at a 2 s maximum playout cannot be played in sync, and writing it at link speed into a receive loop that plays it at real time takes the session down. The guard changes nothing below 8 s, so the F case (6.7 s) and the one-PDU moves seen so far are untouched. Calls and audio-only live never use it.
`PhyMoveSkipTest` replays the queue (850 audio records over 17 s: 750 removed, the newest 2 s kept; the guard thresholds), `GattBytePipeTest` replays the 850 small records against the default pipe (no overflow; the old 512 would overflow) and the byte bound.

**Not fixed / open.** (a) The exact blocking point of the viewer's receive loop after the overflow is inferred (the log shows no exception and the audio decoder counters running); the link-end fix does not depend on it. (b) A viewer in the same state against an older sender still sees the 17 s burst; the byte bound keeps it from overflowing but it then plays the late audio. (c) The 20 s detection (3 windows after warm-up) is what lets the backlog grow; a faster detector for a 7 kbps writer is a separate change.

**Rerun plan.** Same pair and conditions as `stalled2m` (A15s source, ASUS viewer, memory reset, 90 s), frozen APK from this branch, five runs plus one run each with `test_phy_move_flood_guard=false` and with `test_gatt_input_failure_ends_link=false`. Pass reading: after `stalled_one_way` the log shows `phy_move_skip ... kind=flood_guard | skippedAudio=` (hundreds) with `awaitKeyFrame` and a keyframe request; the viewer shows no `input queue overflowed`, resumes video within about 10 s of the move, and its status lines continue to the end. Control (guard off): the byte bound alone keeps the pipe alive, so expect late audio and late video but no zombie; with the link-end fix also off the original zombie should reproduce. Preservation: S24/M31 and ASUS/M31 streams show no `phy_move_skip`; the 6.7 s F case shows none (below 8 s).

## Audio chain: the M31's dials to the A15s fail with 0x3E and the 5-minute refusal mark (b5-audio-chain-cb548fc5 music r1 and r3, 2026-10-13)

**What each failed dial is.** From the M31's stack at 22:21:38.8 to 39.15 (r1): the A15s scan result for the address arrives at 38.756 (rssi -51), `connect()` at 38.818, `GATT_Connect` to the accept list at 38.842, the link is created (handle 0x00a0), and 270 ms later `Failed to read remote features status:Connection Failed Establishment` and `bta_gattc_open_fail ... GATT_ERROR(133)`. That is HCI 0x3E: the M31's controller sent the connection request and the peripheral never answered the first anchor points, six connection events in a row. On the A15s no connection is ever reported (`onServerConnectionState` absent). So it is not a stale or outdated address (the address was scanned 12 ms before the dial, from an advertising set 0.5 to 4 s old), not an A15s refusal in the application sense, and not a collision with an A15s dial (the A15s makes none; its scanner stopped at 22:21:37.36, before it started advertising at 38.28). One PHY detail: the retries were requested on 1M after the 2M ones, which changes nothing, because connection establishment always runs on the advertising PHY (the same observation as relayfix mesh4ab-52681dbf loop14b-1 0006, where an M31 relay as central logged ten Connection Complete events each followed 270 ms later by 0x3E).

**Per-session sticky, or a high per-attempt failure rate?** r1: eight of eight dials failed with 0x3E: four at 22:21:38.8 to 42.4 and, after the 300 s mark, four more at 22:26:46.5 to 50.1 (the same handle 0x00a0 each time). r3: 16 0x3E events and two withdrawals (22:45:11 and 22:50:21). r2: the first round failed twice with 0x3E (22:33:23.3 and 24.3) and the third attempt, one second later, connected (handshake 428 ms, `relay_child_stall result=ok`), so the failure is not an absolute refusal; voice and the control had none. The child changed its address every 15 to 30 s in between (40:C5.. then 6F:88.., 58:0B.., 58:0D..), so the address is not the variable. What stays constant is the M31's parent link (ASUS to M31, 15 ms interval, anchor fixed for the session) and the A15s's controller state; with the data at hand (no HCI snoop of the M31 or the A15s) a bad relative phase between the new connection's first anchor and the parent's events fits "most attempts fail in some sessions, and r1 and r3 never got a good one inside the 2-failure, 3-second budget", but it is not proven. The b14 dead-anchor links (A15s last reception at the 15 ms update, four of four in one session) are the same kind of session-level effect one step later in the life of the link. The next measurement is an HCI snoop of the M31 and the A15s in a failing session.

**Is the 5-minute mark the right reaction?** No, when the child keeps asking and has no other parent. The mark's purpose (RelayEstablishFallback) is to make the child choose another parent; here the M31 is the only relay and the requested chain forbids the direct source. The child kept requesting every 15 to 20 s (92 sightings skipped by `skip_connect` in r1), so the withdrawal only removed the relay's chance to retry, and the relay's two failures were spent within 3 s because the child, advertising in burst mode, was rediscovered every second (dial, 133, 1M setup, dial, 133, mark).

**Fix (`test_relay_refusal_escalation`, default on, control arm `=false`).** (1) Refusal marks escalate 30, 60, 120, 300 s on consecutive marks (the `EstablishmentFailureTracker` schedule the Experimental establishment budget already uses), cleared by a successful link, instead of a flat 5 minutes. (2) A refusal round holds the next dial to that child off for 10 s (`RelayStallHoldoff`), so the two failures that mark a child are at least 10 s apart and a transient or phase-dependent failure gets a second chance with a different timing. Hop-local, nothing sent. `RelayRefusalEscalationTest` replays the r1 pattern (a sighting every second): the control arm spends both failures at 0 and 1 s and withdraws for 300 s (4 dials in 10 minutes); the new arm dials at 0 and 10 s, marks 30 s, dials again at 40 and 50 s, marks 60 s, then 120 s and 300 s (about 10 dials), and a success resets the level.

**Not fixed.** If the cause is a session-level phase between the M31's parent link and a new central link, retries only help when the phase moves; they cost two 1-second dials per 30 to 300 s. The way to move it from the app is a connection update on the parent link, which only the ASUS (central) can start. An HCI snoop of the M31 in a failing session should show the connection events around the failed 0x3E and settle it.

**Rerun plan.** Chain ASUS source, M31 relay, A15s leaf, GATT, Music (the preset that failed) and Voice, frozen APK from this branch, A15s running at least 90 s before the chain starts (as in b5), 10 minutes each, five runs per preset, one run each with `test_relay_refusal_escalation=false`, and the HCI snoop of the M31 and the A15s pulled for any run with a 0x3E. Pass reading: a run that fails its first two dials shows `holdoff` lines between them (rounds at least 10 s apart), `withdraw_offer ... kind=refusal markMs<=30000`, and the A15s joins on a later dial within about 2 minutes (`relay_child_stall result=ok`) in sessions where the failure is transient; in a session that stays dead the log shows dial pairs at about 0, 40, 110, 240 s instead of one pair per 5 minutes. Control: `=false` reproduces `markMs=300000` after two dials 1 to 3 s apart. Preservation: the loop14b M31 case (a child with another parent) still falls back within the first mark; video relay chains unchanged.

## Change impact (for the inventory at implementation)

Phase 1 touches the store-and-forward node, store, link and crypto, the Messages UI, the Contacts tab and notifications, and adds a `ContentProvider`. It changes no call or stream stage. Per AGENTS, cases that use the changed link stages with the feature on are new; with it off, call and stream cases are not affected by phase 1 (the preservation check T-M14 proves it). The v1 messages cases (if any) are NEEDS RETEST on the first build that contains phase 1, because the content format, the bundle version and the retention behaviour change. This design changes these requirements: v1's "archive expires with the bundle" (retired: retention is separate), the 2 MiB message limit (kept per bundle, lifted per attachment), the per-exchange 8 MB (kept for non-contacts).
