## Automatic prefers hardware AV1 (design decision 2026-10-27, release 0.4.1)

Decision: Automatic encoder selection sends with a hardware AV1 encoder (MediaCodec component reporting `isHardwareAccelerated`) whenever the sending phone has one; the review judged an A/B unnecessary. Streams use it regardless of viewers, because a source cannot know every downstream viewer; the existing join check refuses a viewer that does not advertise AV1 decode. Calls keep the per-call check: a peer without AV1 decode, or a legacy peer that asks for VP9, gets VP9. Software AV1 (bundled libaom, Android `c2.android.av1.encoder`) is never promoted by this rule because of heat; manual and DEBUG `test_codec` choices, DeviceFamilyPolicy VP9 call profiles and thermal policy are unchanged. Control arm `test_prefer_hw_av1=false` (SWITCHES).

Evidence: the S22 controlled 720p/15 comparison above (AV1 versus VP9 overlap VMAF/PSNR BD-rate 44.1%/48.7% lower for AV1). Limits: that comparison used the S22 MediaCodec AV1 encoder, which is the Android software component (the S22 has no hardware AV1 encoder), so it measures the AV1 bitstream against VP9, not a hardware AV1 encoder; hardware encoders usually trade some efficiency for speed, and no hardware AV1 encoder has been measured here. Residual cost: the same run measured warm compute margins of 1.05-1.19x real time for AV1 against 1.24-1.34x for VP9, so AV1 still costs more compute; on dedicated hardware this is expected to be smaller, but heat and battery on a hardware AV1 phone remain unmeasured. Before the change the static order (`VideoCodec.selectionPriority`) already ranked hardware AV1 first; this record makes the rule explicit, adds the component exclusion hook and the per-session `BENCHMARK encoder_choice` reason.
