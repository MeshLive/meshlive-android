# Design GD: one stable app GATT database (draft 2026-10-20, revision 2 2026-10-27 after review 2, not built)

**Status: design for review; no code until the coordinator and the user approve it.** No wire change: the services, UUIDs and characteristics stay as they are; only when they are added and removed changes. Switch when built: `test_stable_gatt_database` (Experimental, default off). Related: Design CD (the CoC path without a GATT client); this note helps the GATT transport and the GATT client that Design CD keeps for link priority.

**Why.** A connecting phone that opens a GATT client walks the peer's whole GATT database before anything else runs (about 0.75-1.45 s measured; Design CD "Problem"). On AOSP `main` an unbonded central can skip that walk: it reads the peer's Database Hash and reuses a database stored under the same hash, while a bonded central reuses its address-keyed cache unless a Service Changed indication arrived (Design CD "What AOSP does", with source links). Both reuses fail whenever the peer's database changed since the last connection, and MeshLive changes it all the time.

**What changes the database today (each add or remove changes the Database Hash and sends Service Changed to bonded peers).**
- Video data service `c8d5a105-...`: `GattVideoServer` opens its own server and adds the service (GattVideoTransport.kt:1537, :1585) and `close()` removes it (:1688). Instances: the call endpoint (AndroidPrivateVideoCall.kt:793, closed at :4046 and :4393, rebuilt 1.5 s after every call, CF-CALL-21, and at every RDI boundary, PROTOCOL "Rotation"), the stream receiver (AndroidVideoReceiver.kt:521, one per join), the private-call relay (BluetoothPrivateCallRelay.kt:799), the stream relay (BluetoothVideoRelay.kt:317) and the dual-listening second server (DualListeningAndroid.kt:40).
- Control service `c8d5a101-...` with the PSM characteristic: `BleL2capControlServer` (BleL2capControl.kt:953; open :1115, add :1146, close :1222). Instances: the call endpoint (AndroidPrivateVideoCall.kt:774), the receiver (AndroidVideoReceiver.kt:213), the call relay (BluetoothPrivateCallRelay.kt:780), the stream relay (BluetoothVideoRelay.kt:294).
- Probe service `7f3c0a10-...` (InboundProbe.kt:284, :304), DEBUG launches with the probe extra only.
- A viewer join removes the call endpoint's services and adds the receiver's (`call_reachability: endpoint stopped | reason=joining_stream`): two changes per join. Measured: the viewer's `GATTS_AddService ... uuid=c8d5a105...` 0.11 s after the selection, and the bonded source's client then rediscovered the whole database on that connection.

**Proposal.**
1. *One server, fixed order.* A process singleton opens one `BluetoothGattServer` and adds, once and in this order, the video data service and the control service (with its PSM characteristic). Nothing is removed while the process lives. The probe service, DEBUG only, is added last and only in a probe launch, so it never changes the order of the others. Within one phone state the handles and the hash are then the same on every connection; a process restart removes and re-adds them in the same order, so the hash comes back unless another app's services changed meanwhile.
2. *Roles share it, nothing is added or removed per role.* Each role that today creates a server instead takes a lease: `enable(role, handler)` and `disable(role)`. The singleton routes every callback by connection: a new central connection is offered to the enabled roles in a fixed precedence (an active stream join or relay before the idle call endpoint, matching today's single-owner rule where a join stops the call endpoint); the accepting role binds that device, and later writes, reads, CCCD changes, MTU and notification completions for that device go to that role only. A connection no enabled role accepts is closed (`cancelConnection`) as today when no server existed. A read of the PSM characteristic returns the PSM of the role that bound the connection, or, before binding, of the role whose listener is advertised.
3. *Availability stays in the adverts.* Whether a phone is callable or joinable is still said only by its advertising sets; the always-present services carry no availability. A phone that connects while no role is enabled is refused at admission, exactly where a missing service failed it before.

**Privacy.** PROTOCOL "Pre-handshake exposure" (RH2) already notes that any connected central can read the Database Hash, that it is "probably the same in every epoch" and could link epochs for a silent probe (unverified). This design makes it certainly the same for a whole process lifetime. Options for review: (a) accept it (the tarpit slows silent probes; a probe must connect, which the advert does not reveal); (b) add one constant-content characteristic whose 16-byte UUID is derived from the epoch, re-added at each boundary, so the hash changes per epoch: cache hits then work within an epoch (most reconnections, calls back and stream rejoins) and the boundary costs one Service Changed. Recommendation: (b) if the review rates the linkage as real, (a) otherwise.

**Risks.**
- *Fan-out of one callback object.* Every role's traffic passes one `BluetoothGattServerCallback`; a role that blocks in a callback stalls the others. Rule: callbacks only dispatch to the bound role's executor, never block.
- *Notification pacing.* Android paces server notifications through `onNotificationSent`; whether that queue is per server or per connection differs by stack. Today a call and a relay each have their own server; sharing one could serialise their notifications. The phone test measures throughput with a call and a stream relay at once before any default changes.
- *Server loss.* Bluetooth off/on or a stack restart invalidates the server; the singleton must reopen it and re-add the services in the same order (one Service Changed), and every enabled role must re-bind. Covered by the existing Bluetooth-off handling, extended.
- *Two copies today.* Dual listening currently can hold two video data services at once (two handles for one UUID); with one server there is one copy and routing replaces the second server. Old phones that discovered two copies never relied on the second (to verify).
- *Registration pool.* Fewer server registrations is a gain (`GattPoolBackoff` server-side refusals).

**How to verify a cache hit on phones.**
- On the connecting phone (Android 13+ with the stack's `bluetooth` logcat tag at verbose, or an HCI snoop): a hit shows an ATT Read By Type for UUID 0x2B2A (Database Hash) and then **no** primary-service discovery (no `GATTC_Discover ... disc_type=1`, no run of `bta_gattc_disc_res_cback` lines); the stack logs `bta_gattc_read_db_hash_cmpl` followed by the hash load, and no `BTA_GATTC_SRVC_CHG_EVT` on the connection. A miss shows the full discovery: `bta_gattc_start_discover`, then a run of discovery results lasting several hundred milliseconds.
- In the app: the connect to `onConfigureMTU` time and the `LE link: ... event=setup` timestamp on the connecting phone drop from about 0.75-1.45 s to tens of milliseconds on the second and later connections to the same phone.
- On the listening phone: no `GATTS_AddService` or service-deleted callbacks between connections (`btapp_gatts_handle_cback ... service_added_cb / service_deleted_cb`).

**Test plan.**
- JVM: the add order is pinned (a fake server records `addService` calls: exactly the two services once, in order, and no `removeService` or `clearServices` for the process lifetime, whatever the role sequence: call, call end, rotation, join, relay start and stop); routing (fake connection, write, CCCD and notification events reach only the bound role; an unbound connection is refused; the PSM read answers the bound role's PSM); server loss re-adds in the same order.
- Phone A/B, switch on and off, frozen build: the 8 vab cases and unbonded joins and calls (M31, Xiaomi, A15s, S24), second and later connections to the same phone: connect to MTU and connected to authenticated; hash-hit evidence as above; no Service Changed at call end, rotation or join.
- Stress: a call and a stream relay at once on one phone, throughput and continuity both, against the switch off.
- Bluetooth off/on during a call listener and during a join.

## Review 1 (2026-10-20, second reviewer): approve with changes, gated behind `test_stable_gatt_database`

AOSP claims verified on main (bta_gattc_act.cc, bta_gattc_cache.cc) with a caveat: (1) the aconfig flag `skip_unknown_robust_caching()` (bug 317128464) skips the hash read in exactly the unbonded empty-cache case, so the unbonded gain must be measured per required phone before it is claimed. (2) **Blocker:** connect-time routing cannot work (the server can't tell which advertising set a central used, and it sees links this phone opened as central): bind on the first hop write (hello/BDO1 role + RDI), queue earlier CCCD/MTU events, and never `cancelConnection` links owned by local clients or other roles; the PSM read is ambiguous with two listeners. (3) The hash is probably already constant across epochs today (the same services are re-added); option (b) is sound only with a secure-random per-epoch UUID and still loses to a full walk (RH2 residual), and a mid-call re-add sends Service Changed during media: recommend (a) plus a stated residual. (4) Server loss: serialise adds on onServiceAdded, re-bind on a fresh first write, rebuild notification queues. (5) Measure each phone's idle hash stability first (system/Phone Link/wearable services). (6) The pacing test binds a call, a relay and a receiver at once.

## Revision 1 (2026-10-20): review 1 addressed

These rules replace the matching parts of the proposal above.

0. **Addressed (review 5): measure before building.** Step one is a measurement, not code: on each required phone, read its Database Hash (0x2B2A) from another phone every minute for 30 minutes while MeshLive is idle, then across a call, a join and a boundary, with system, Phone Link and wearable services as they are. A phone whose hash changes on its own gains nothing; the record lists per phone whether its idle hash is stable.
1. **Addressed (review 1): the unbonded gain is measured per phone.** The aconfig flag `skip_unknown_robust_caching()` (bug 317128464) skips the hash read in exactly the unbonded empty-cache case. For each required phone as the connecting phone, the first and second unbonded connection to a MeshLive phone are captured (HCI snoop or the stack log): an ATT Read By Type for 0x2B2A means the hash path runs. The unbonded gain is claimed only for phones where it does; for the others the design helps bonded peers only.
2. **Addressed (blocker): bind on the first hop write, never cancel a link we did not accept.** The server cannot tell which advertising set a central used, and its callbacks also report links this phone opened as a central. So: a connection is bound to a role on its first write to the video data characteristic, which carries the link hello (and `BDO1` where used) with the role and the RDI; CCCD writes and MTU changes that arrive before that are queued per device and replayed to the role that binds. A connection no role binds is answered with an error on its writes and is never closed with `cancelConnection`; links owned by this phone's own GATT clients or by another role are never touched. The PSM read happens before any write, so it cannot be bound: the control service's PSM characteristic answers with the PSM of the one role whose CoC listener is advertised (today a join stops the call endpoint, so only one is); a phone that advertises two CoC listeners at once (not done today) needs per-role PSM characteristics, which would be a wire change and is out of scope.
3. **Addressed (review 3): option (a), with the residual stated.** No per-epoch characteristic. The hash is probably already constant across epochs today (the same services are re-added); with this design it is constant for a process lifetime. Residual (to PROTOCOL "Pre-handshake exposure" when built): a central that connects and reads 0x2B2A, or walks the database, can link this phone's epochs while the app runs, without completing BMH2; the stranger tarpit limits silent probes; a full walk would show the same anyway.
4. **Addressed (review 4): server loss.** Services are added one at a time, each after the previous `onServiceAdded`; after a loss the server is reopened and the same two services are re-added in the same order; every binding is dropped and a role re-binds only on a fresh first hop write; notification pacing state is rebuilt per connection.
5. See 0.
6. **Addressed (review 6): the pacing test binds a call, a relay and a receiver at once** on one phone, and compares throughput and continuity of all three against the switch off.

## Review 2 (2026-10-26/27: reviewer and reviewer Opus, independent) and Revision 2 (2026-10-27)

Verdicts:
- **reviewer:** first priority, conditional approval after revision.
- **Opus:** build only the scoped variant below, after the pre-build measurements.

Both reviews found the hash path already working on modern connecting stacks. Opus measured it from the stack logs of the saved runs: S24, S22 and Xiaomi as the connecting phone hit the Database-Hash cache 81% (unbonded) to 91% (bonded) of the time (`robust caching support is N`, then `hash found in cache` vs `service discovery finished`). The walks that remain come from three sources:
- Android 10-13 connecting phones
- peers whose controller reports LMP below 0x0a (M31, A15s)
- Android 10/11 servers (ASUS)

The S22 and ASUS HCI profile (2026-10-26) adds a fourth cost. On a bonded pair, both servers send Service Changed right after LL encryption. That forces a full mutual discovery: about 30 ATT round trips each way at the 30 ms creation interval with 27-byte PDUs, from about +180 to +910 ms. The MTU, CCCD and BMH2 wait behind it. Most real users are unbonded; benchmark pairs that are bonded overstate the setup.

**GD-lite: a cheaper first stage (proposed by the coordinator and Opus; recommended as stage 1).** The call endpoint keeps its GATT server and control service registered across rotation boundaries and after calls. It re-announces instead of re-registering, and the PSM characteristic answers the current listener's PSM. No singleton and no routing: the call endpoint is already the one inbound owner most of the time. This removes the database changes at every call end (rebuilt 1.5 s later today) and at every boundary, which are the changes that invalidate the cache and send Service Changed to bonded peers. Joins and relays keep today's servers until full GD. Same switch, same acceptance; Android 12+ first.

**Decision input: walk split measured 2026-10-27** (offline). The data covers 519 direct-call GATT setups matched to the connecting phone's stack log and 689 other setups (streams and relays). Medians / p90 in ms. The table gives, for each connecting-phone class, the outcome and the app's MTU wait:

| Connecting phone | Peer | Outcome | App MTU wait |
| --- | --- | --- | --- |
| Android 10-12 (A15s, ASUS, M31): no robust caching; the address cache is never found (`can't open GATT cache file`) | any | walk in 356 of 356 | 676 / 1361 (about 1.35-1.46 s into an S24) |
| Android 14+ (S24, S22, Xiaomi), peer controller below BT 5.1 (A15s, ASUS, M31: `LMP version 0x09 < Bluetooth 5.1. Ignore database cache read`, or no hash characteristic) | legacy | walk in 91 of 94 | 480 / 533 |
| Android 14+ | Android 14+ | hash hit in 62 of 69 | 229 / 324 (Xiaomi 137) |

Bond state is readable only on the S22 and S24 (the others never log it): unbonded walks take 481 / 533 ms and hits 207 / 242 ms; bonded walks take 770 / 972 ms. The Service Changed that every bonded reconnection receives is harmless when the hash matches: 33 such setups took 267 ms. It costs the full walk only when the peer has no usable hash. Service Changed on live links hit 1.4-2.2% of saved call and stream windows (42 in total). None of the 21 in calls coincided with a media gap on that phone, and the 38 in streams coincided less often than the base rate. In 37 of 59 the peer's own GATT server had added, removed or re-advertised a service up to 3 s before.

**Consequence.**
- GD (and GD-lite) cannot shorten setup for any pair that includes an Android 10-12 phone or a BT 5.0 controller, which is half of the required phones. The pairs it could help (Android 14+ to Android 14+) already hit the hash cache 81-91% of the time.
- Its remaining value is tidiness: fewer Service Changed indications at call end and at boundaries. That has no measured media effect.
- **Recommendation: deprioritise GD for latency.** Keep it as a later hygiene item: GD-lite at most, Android 12+, with acceptance unchanged.
- The walk sits on the critical path because the connecting phone opens a GATT client. Only CD (CoC with no GATT client before the handshake) removes it, and only for the CoC transport. On GATT calls between legacy pairs the walk (0.5-1.4 s) has no app-side remedy except running the call over LE CoC. **CD revision 2 becomes the latency priority;** its privacy item (masked contact-only PSM) is the gate.

**Status: revision 2 for the coordinator and the user; no code.**
