# Design G: naming and identity display v2 (names off the air, generated stranger names, one precedence function, mutual in-person verification, Visible by name)

**Designed 2026-10-12; not coded; independent review done before coding (findings below).** Wire rules: PROTOCOL.md "Naming v2". Research: how Bitchat, Briar, Meshtastic, Meshenger, Knit, Signal, Threema, SimpleX, AirDrop and Quick Share name people (the comparison table is in the private block at the end). It builds on, and does not replace, "Peer labels" (signed `BNL1` names inside the session), rotating discovery IDs, BMH3 with stranger pseudonyms (Design F), the UTS #39 look-alike check and the verified-contact store with the Contacts screen.

**What people will see (plain words).**

- Nobody broadcasts a name. Phones nearby show up as a friendly generated name such as "Blue Otter". The name is made from the phone's current 15-minute random discovery ID, so it changes when the ID changes and cannot be used to follow anyone. Your own phone shows what others see: "Others nearby see this phone as Blue Otter until 14:15".
- When you call or answer someone you have not verified, the name they chose for themselves arrives inside the encrypted call and is shown with a tilde: "~Rahul". The tilde means "this is what they say; nobody checked". You see "~Rahul" only if Rahul set a name; otherwise you keep the generated name.
- People you verified in person show under the name you gave them, with a shield. What they call themselves later never changes your list. If someone who is not your contact claims a contact's name, or a contact's key changes, you get a clear warning instead of a silent change.
- Verifying is done together, face to face: each phone shows a code and scans the other's. A photo of a code stops working after five minutes or after one use. A scan proves you reached the phone that holds that key through a secret from its screen; it does not prove you stood in front of it, so the app asks "Is this Rahul's screen you scanned?" before it marks anyone. The shield means "I scanned them"; "scanned each other" appears when they scanned you too.
- An optional switch, "Visible by name to everyone for 10 minutes" (for a meeting, a camp, a festival line), lets people nearby see a name you pick next to a separate ID that exists only for those ten minutes (your ordinary ID never carries the name). It turns itself off after exactly ten minutes.

**Decisions in one table.**

| # | Question | Decision | Default and off-switch |
| --- | --- | --- | --- |
| G1 | Where does a self-chosen name go? | Never into any advertisement (outside G5). Only into signed `BNL1` labels inside the endpoint session, as today. The existing design already does this; what changes is when it is sent and the default. | "Names and subjects" ON once its phone test passes (today OFF); the name itself is empty until the user types one; audience setting below; switch in Settings > Features |
| G2 | What do strangers look like before a connection? | A generated two-word name from the current rotating ID (call-ready phones, stream offers), from the throwaway key for an incoming stranger call, never from a stable key; handle for fixed-prefix adverts as today | ON with rotating IDs; `generated_names` switch (OFF shows "Nearby phone" and the handle as in 0.2.0-beta) |
| G3 | Who wins, yours or theirs? | Your label always wins for a verified contact. One precedence function names every row on every screen. Their claimed name is a detail, never the title. Key and look-alike warnings. | Always on; the warnings have no off-switch |
| G4 | What is "verified"? | In-person scan, both ways, with a live check (`BVMID2`). Code-only comparison no longer gives the shield. | `bvmid2` (ON by default since 2026-10-19, design decision Q-QL1, after N5 and the Design QL phone test passed); "Accept older verification codes" (`bvmid1_compat`, Advanced, default OFF) for 0.2.0-beta phones |
| G6 | Blocking | Referenced only; the two features it must plug into are listed | Separate feature |

## G1. Names stay inside the session

**What exists.** `BNL1` labels (PROTOCOL "Peer labels") are identity-signed, bound to the call or stream ID, sent in BME1 type 10 only when both endpoint hellos carry bit 5, and never on air. The link and the endpoint session are encrypted, so a radio sniffer sees neither bit 5 nor the name (a relay in a relayed call still reads the endpoint hello's bits, an existing residual). The callee's name goes out only at Accept (or at Ringing to a verified contact). The caller's name and subject, since Design F review PR6, are held until the callee's `REVEAL` is verified, so a copied advert collects nothing. The only public naming surface is the stream title page (a title, not a person; the Go-live dialog says it is public).

**What is missing or wrong.**

1. The switch ships OFF (`CallFeatureDefaults.NAMES_AND_TITLES = false`), so nobody sends a name. It bundles two things with different risk: names inside the session, and public title pages. Split them: "Names and subjects" (in-session, default ON once its phone test passes) and "Show my stream title to everyone nearby" (title pages, keeps its present rule: public by default for a stream the user titles, with the note).
2. PR6 means a stranger who rings sees no name at all, only a generated pseudonym name. That is the safest rule and the worst call experience: the callee must accept, and so reveal who they are, before learning who is calling. Disaster and camp use is mostly stranger to stranger.
3. There is no audience control: a set name goes to everyone you call.
4. A stable name is a stable identifier: every stranger you call can compare notes. Nothing says so in the UI.

**Decision.**

- **Audience** ("Who sees my name", Settings > Your ID; only shown when a name is set): "Everyone I call or answer" (default), "Only people I verified", "Nobody". With no name set nothing is sent and the callee sees the generated name (fresh per attempt, so strangers cannot link two calls). Copy next to the field: "Everyone you call sees this name and can compare it with what other people saw. Leave it empty to stay anonymous."
- **Callee's name:** with "Everyone I call or answer" unchanged (at Accept, or at Ringing for a verified contact). With "Only people I verified" it is sent only after the caller's reveal is verified and found to be a verified contact (before that the callee cannot tell a stranger from a contact whose lease expired; review F11). Declining or letting it ring reveals nothing.
- **Streams:** unchanged. The stream title is the only label; a person name on broadcasts would link every broadcast to a person and is out of scope.
- **Text rules (added; review F13):** the existing rules do not block the tilde or its look-alikes (`LabelText` skips the Common script), so a name may not start or end with `~` or a tilde look-alike, may not contain a shield or lock symbol, a tilde anywhere, or the app's own separators, and may not reduce (UTS #39 skeleton, spaces and punctuation removed, case folded) to a generated name (so "BlueOtter" and "Blue 0tter" fail too). The receiver drops such a label (fails safe, like any bad label). Screens draw a claimed name in its own styled element, never in one string with the marks. The existing rules (32 bytes, NFC, no bidi or format characters, Moderately Restrictive scripts, no handle-shaped text) stay.
- **Compatibility:** nothing new on the wire. A 0.2.0-beta peer has bit 5 off (its switch ships off) or on (explicitly enabled): labels flow only when both carry it, so against such a peer the new build simply shows the generated name. A 0.2.0-beta peer with labels switched on shows the early name by its old rules (quoted, no tilde).

## G2. Generated names for strangers

**Rule.** `name = adjective[i] + " " + noun[j]` where `d = SHA-256("BluetoothVideoMesh/Naming/StrangerName/1" || 0x00 || input)`, `i = d[0]`, `j = d[1]`, and `input` is exactly one of:

1. the 6-byte RDI of a version 5 / compact v2 advert (call offers, stream offers, forwarder offers), as seen by a scanner or as computed by the owner for its own role-0 and role-1 IDs;
2. the 16-byte node ID of the throwaway key of an incoming stranger call (per connection or per attempt, from Design F), on both phones of the call.

Nothing else is ever an input: not the node ID, prefix, fingerprint, handle or lease key of a real identity, not a per-install secret, not the advertising address. The function has no overload that accepts those types, and a test greps the callers. A fixed-prefix (version 2) advert, a Classic role or a Visible-by-handle window has no rotating ID: it keeps the full handle as today (the handle is stable by construction, so a stable-key name would be a tracking handle). A name derived from the RDI discloses nothing the advert does not already disclose, and changes whenever the RDI changes (every 15-minute epoch, and between roles: the same phone is "Blue Otter" as call-ready and "Gold Fox" as a stream source, which is the unlinkability of role 0 and role 1 working as designed).

**Why derive it from public bytes.** The same input gives the same name on every phone, so people can say it aloud ("I am Blue Otter") and the owner's own phone can show it. A per-phone secret would remove that and add nothing against an attacker, who can advertise any RDI anyway.

**Display.**

- Nearby and watch lists: the generated name as the title, "Nearby phone" and the role (can take calls, is broadcasting) below, a colour chip from `d[2] & 7` (never the only cue) and no signal strength or distance next to a name (Telegram's People Nearby was trilaterated and removed). A stream offer without a title is "Blue Otter, broadcasting" with a camera mark. A stream title read from a title page stays "unconfirmed".
- Own phone (Settings > Your ID and on the Call screen): "Others nearby see this phone as Blue Otter until 14:15" (the next boundary), with a second line while broadcasting; shown only while the phone is advertising, with the suffix when it knows of a collision and otherwise a note that a number may be added if another phone has the same name.
- Incoming stranger call: "Gold Fox is calling" (name from the throwaway); the caller's screen says "You appear as Gold Fox", which lets two people confirm out loud that the call on the screen is the one they mean. It authenticates nothing (16 bits, see below), so the ring screen shows "Not verified". A redial is a new attempt and arrives under a new name; the ring screen says "A new call. Calls from the same phone show a new name each time." so a caller who redials is not mistaken for several people.
- While a call or join is running the title is pinned to the name it started with (the ID changing at 14:15 does not rename an open call).
- After a self-claimed name arrives: the title is the name in its own style with the tilde mark and the words "calls itself" ("~ Rahul, calls itself"), "Gold Fox - not verified" as the second line. Words always accompany the glyph (review F17); a screen reader says "calls itself Rahul, not verified".
- A recognised contact (presence lease) keeps "Mum, seen nearby, unconfirmed". Contacts are never given a generated name.
- Recents: a stranger's entry stores the generated name and the time only (strangers' names are not cached, as today); it is not a handle for later. This amends Design F step 5, which replaced the recent-calls entry by the revealed real identity: the real node ID and fingerprint of an unverified stranger stay in memory for the call and are persisted only if the person is then verified (review F20: a seized phone should not hold a list of stranger keys).

**Collisions.** Two phones in one list can draw the same name (16 bits: about 0.7 % at 30 phones, 7 % at 100). The list grows the label until the rows differ, never merges rows by name (the OSHI mistake): same name gets two digits from `d[3] % 100` ("Blue Otter 42"); if those also match, the last four hex digits of the RDI. The digits come from the RDI, not from arrival order, so every phone that sees the same rows shows the same text. A copied ID is flagged only when two addresses carry the same RDI at the same route cost at the same time, repeatedly (review F4: one ID on a second address inside an epoch is normal, and a relay mirrors a child's ID at route cost + 1), with "More than one phone is using this ID" and a second tap. Because anyone can advertise any RDI (a name that collides with a friend's costs about 2^16 hashes, and with the digits 2^24), the name is a convenience for picking a phone in a room, not a credential: a call to a copied advert fails the existing discovery binding (the reveal must open the selected RDI), the subject is held until then, and trust comes only from verification. A phone that sees only one of two colliding rows shows no suffix; the design says so rather than promising uniqueness.

**Confusables and imitation.** The list is ASCII lowercase, so generated names have no cross-script confusables. The checks that matter run at display time with `LookAlike`: a self-claimed name that has the same skeleton as, or is identical to, (a) a contact label, (b) your own name, (c) a generated name, or (d) another row visible now, is handled by kind (review F14: an alarm that fires constantly teaches people to ignore it). For (a) a contact label: the alarm wording "Not your contact Mum" (the present code excludes identical text; identical must now be flagged too, because a stranger claiming exactly "Mum" is the most likely imitation). For (b), (c) and (d): a neutral note ("2 people nearby call themselves Rahul"), never a warning. Contact labels are forced unique (Meshenger), case- and skeleton-insensitive, in "Save contact as" and rename.

**Word lists (`names-v1`, replaced by `names-v2` on 2026-10-12, see "Word lists v2" below).** Two lists of 256 words (`assets/names/adjectives-v1.txt`, `nouns-v1.txt`; 16 bits; with `d[3]` that is enough because collisions are resolved at display time). Original work written for this project and released under GPL-3.0-or-later with the app; no third-party list is copied, so no attribution is owed (EFF wordlists, Diceware, BIP39 and Knit's lists were studied only for method; EFF lists are CC BY 3.0, Knit is GPL, BIP39 is MIT: all compatible, none used). Rules for entries: common English words of 3-7 letters, a-z only, one meaning, easy to say aloud and unlikely to be misheard; nouns are animals and plain natural things; adjectives are colours, materials and calm qualities. Also screened out for the places MeshLive is meant for (review F23): colours and animals with a political, religious, caste or insult reading in common target cultures (for example red, orange, saffron, green, black and white as party or community colours; cow, pig, dog, donkey, monkey, rat), read by speakers of at least Hindi, Arabic, Spanish and French before freezing; the lists are frozen only after 256 entries each pass every rule. Not allowed: any word on the offensive-word lists used offline for screening (LDNOOBW English plus Spanish, French, German, Hindi and Arabic transliterations; the screening lists are not shipped), words with a sexual, violent, medical, religious, national, ethnic or political reading, and words that carry authority, emergency or trust cues (police, army, official, admin, help, rescue, safe, free, verified, trusted, urgent, fire, medic) because in a disaster a name must not look like a message. Within a list: edit distance of at least 2 between any two words, no homophones (CMU dictionary check), no entry that is a prefix of another. All 65,536 pairs are screened against the offensive lists as phrases and as concatenations. The files, their SHA-256 and the screening report are committed; the hash is a test constant, so any edit fails the build. The list is frozen once shipped: changing it changes every phone's display of every ID, so a new list is `names-v2` with a release note, never an in-place edit. Localisation: the lists are English in v1; translated lists keyed by the same indices would make two people with different phone languages read different words aloud, so they are an open question rather than a default.

**Honest limits.** 16 bits are not an authenticator and not a short authentication string: a man in the middle can generate keys until the throwaway names match in seconds. The generated name is for finding and saying, the safety code and QR for knowing. It makes it easy to say "call Blue Otter", which also makes it easy for a bystander to hear the name; the rotating ID bounds the lifetime of that to the epoch.

**Off-switch.** `generated_names` (Settings > Advanced, DEBUG `test_generated_names`): off shows the 0.2.0-beta text ("Nearby phone", the handle). Everything else keeps working.

## G3. Your label wins; one precedence function

- **One function names a person on every screen** (nearby list, watch list, ring screen, in-call header, call log, notifications, Contacts, Verify), in this order, first match wins (Meshtastic's single security-state function, #7117, and Threema's tilde and dots):

| Rank | State | Title | Mark | When |
| --- | --- | --- | --- | --- |
| 1 | Key changed | "Not Mum" or the handle | red warning, call refused or explained | prefix of a verified contact with a different key (existing `MISMATCH`), or a name claim, below |
| 2 | Blocked | (Blocked-people feature) | grey | referenced, not designed here |
| 3 | Verified contact | your label | shield | the session key equals a verified fingerprint |
| 4 | Recognised contact | your label, "seen nearby, unconfirmed" | no mark | a presence lease matched an advert; no connection |
| 5 | Self-claimed | "~Name", generated name below | tilde | a verified `BNL1` kind 1 from an unverified peer |
| 6 | Generated | "Blue Otter" | none | rotating advert or stranger throwaway |
| 7 | Handle | full handle | none | fixed-prefix advert, Classic, Visible-by-handle window |

  A help screen "What the marks mean" lists the seven rows. Lock-screen notifications use no name (existing Q16 decision).
- **Your label wins.** The contact's own current name is never the title. It is shown in the contact's detail and once, as a note, when it changes ("Sunita now calls herself 'Sunita K'. [Use it as your label] [Ignore]"; nothing changes unless you tap). Not shown beside the label in lists (Briar shows "alias (their name)" always; the open questions ask whether to copy that).
- **Where their claimed name is kept.** A new sealed file `identity-verification/contact-claims.bin` (same Keystore key and `AtRestCipher`, atomic writes) maps contact fingerprint to the last verified claimed name (at most 32 bytes) and the time. Only contacts get an entry; strangers' names stay in memory for the session. It is separate from `verified-contacts.bin` so a downgrade to a build without it loses only the note, never a contact. Forget and wipe delete it.
- **The verified mark belongs to the key.** The store is keyed by the full fingerprint (existing). A name change does not touch it, so the Bitchat #1708 attack (a verified key renames itself "medic") has nothing to attack: the title is your label. The converse is covered by the name-claim warning.
- **Name-claim warning (soft key change).** A reinstalled or replaced phone has a new key and a new prefix: it is a stranger. If its self-claimed name equals or looks like a contact's label or that contact's last claimed name, the ring screen and list say "Not your contact Mum. If Mum has a new phone, scan her code again in person." **Before the reveal** (review F12) the same condition may be a real contact whose presence lease expired, who arrives as a stranger; the text is then neutral: "Says they are Mum. The app will check when you answer." The alarm wording appears only after a reveal with a different key, or for a stranger who never reveals. After an in-person mutual scan of that phone the Verify screen asks "Is this Mum's new phone? [Yes, replace Mum's key] [No, add a new contact]"; replace keeps the label, forgets the old key (and its presence leases, starting a new generation) and logs nothing else. Without the in-person scan nothing is offered.
- **Hard key change.** A phone that has a verified contact's prefix but another key is the existing `MISMATCH`: refused by default, with "This phone claims to be Mum but its key is different from the one you checked. Someone may be pretending to be Mum." No change to the mechanism; the text and the precedence row are new.
- **No second source of names.** The OS Bluetooth name is never used (existing rule).

## G4. Verified means scanned in person, by both

**Today.** `BVMID1.<fingerprint>.<name>` is a static code; a verification succeeds only when a live endpoint handshake has that fingerprint, which is why a photo proves nothing alone. The remaining gap is social (a photo passed off as a meeting). Verification is one-sided per phone; presence leases need both sides, so a one-sided scan gives no recognition. The safety code can be compared over any channel and also marks "verified".

**Decision.**

1. **Meet in person screen** (Settings > Verify a contact, Contacts > Add contact, the lock in a call). Top half: your code (`BVMID2`); bottom half: the camera. Either phone may scan first. Text: "Hold the phones together. Each of you scans the other's code."
3. **Mutual by construction (Briar).** The displayer sees the inbound tagged connection with the scanner's real key and shows "Rahul scanned your code. Now scan Rahul's code." It marks nothing until it has scanned the other phone's code. Each scan is its own tagged session, so each phone learns the other's scan from a real authenticated event (review F7), and "You and Rahul verified each other" needs both events. A shoulder-surfer who photographs a code and scans first can win the race: the displayer then sees his claimed name and handle, the real person sees "That code was already used", and a second fresh attempt cancels the pending scan at once with "Two phones used your code. The first one may not be the person in front of you. Start again." (review F9; a radio observer replaying a sniffed first message cannot raise this alert). He learns only the fingerprint the code already showed, and he cannot become verified on the displayer's phone because the displayer must scan his code in person. While the screen alone has made the phone call-ready, it accepts only the code's tag and closes every other connection (review F10).
4. **Outcomes, in words.** "You verified Rahul" (you scanned), "Rahul verified you" (they scanned), "You and Rahul verified each other" (both: the shield and "Save contact as" prefilled with their claimed name, editable; leaving it empty keeps the handle). The shield means "I scanned them" and is set on the scanner's phone on its own scan; "verified each other" is a separate fact that needs both scans. Presence leases move only inside an answered call between two phones that have each other verified (Phase 2 rule, unchanged), so recognition starts after the first answered call that follows a mutual scan; the screen says "Your phones will recognise each other after your next call." (review F8). A one-sided result says so ("Rahul has not scanned your code yet").
5. **Code-only comparison** (the 60-digit safety code) stays as a read-aloud aid on the same screen, but no longer gives the shield. A contact marked that way today keeps working, shows an outline mark "Checked by code" and a button "Scan to confirm"; no existing contact loses protection or the leases it already holds at upgrade. New code-only checks create the same outline mark, keep the `MISMATCH` refusal and the expected-contact check, and get no new leases until scanned both ways (review F18). This follows the direction "verified is in person only" and keeps old data.
6. **Fallbacks.** Rotating IDs off or a phone that cannot start a non-connectable advertising set: the screen offers the BVMID1 flow (needs an existing connection). "Accept older verification codes" (`bvmid1_compat`, Advanced, default off since the G-Q4 compat review) shows BVMID1 beside BVMID2 for a 0.2.0-beta phone and lets a BVMID1 scan give the shield; it is a labelled downgrade because BVMID1 has no capability. With it off, a BVMID1 scan on a new build gives only the "Checked by code" outline.
7. **Remote adds** (a pasted link, an introduction) are out of scope; if added later they can never produce the shield (Meshtastic: verified never arrives via a relay).

## G5. Visible by name for 10 minutes

**Behaviour.** Settings > "Visible to everyone nearby" has two buttons that share one window state and one countdown: "By ID" (today's "Visible by handle for 10-25 minutes", unchanged: fixed prefix, so old builds and people who know your handle can find you) and "By name" (new). Starting one ends the other (never both: a name next to a fixed prefix would give observers a permanent name-to-key table). "By name" asks for the name to show (empty, with a hint to use a nickname, and a confirmation if it equals the name used in calls, because a real name in a public window is the risky default; review F16), explains the cost in two lines, shows a persistent notification with a countdown and "Stop now", and reverts by itself after exactly ten minutes. Phones nearby show "~Rahul - Blue Otter" until then. If "Block unknown callers" is on it asks whether to allow calls from anyone for the same ten minutes; the answer reverts with the window.


1. a **window offer**: a connectable set advertising announcement version 8 (the version 5 layout, 22 bytes) whose six prefix bytes are the phone's **role 3 ID** for the current epoch (role 3 is reserved for this window; the ID is derived exactly like roles 0 and 1, so it is unlinkable to them) and whose route-token field carries `SHA-256(name)[0:4]`. A caller selects it like a call offer, opens it with `BDO1` (role 3) and meets a throwaway key as for any stranger call;
2. **name pages** (version 7): a non-connectable scannable set carrying `version 7 | window RDI (6) | SHA-256(name)[0:4] | page (index<<4|count) | 1..10 name bytes`, up to four pages, one per second.

A scanner shows a page's name only if the window offer it is currently seeing carries that same hash (review F2: without the hash anyone could attach "~Police" or "~Informer" to someone else's live window ID). Nothing is signed, so the name is shown "~Rahul, calls itself", never with a mark. Nothing is broadcast before the button is pressed or after the window ends; a phone that cannot get the free advertising sets says "This phone cannot show a name to others" and does nothing.

**Privacy cost, in plain words.** For ten minutes anyone nearby with the app, or a scanner that knows versions 7 and 8, can link the name to the window ID. The ID your phone used before the tap and the ordinary ID it keeps using during the window never carry the name, so an earlier log of them gains nothing; an observer who sees both in the same place at the same time can still guess they are one phone (the residual of any two adverts from one place). If the ten minutes span the 15-minute change, the window ID changes with the epoch and the name carries over, so those two window IDs are linked to each other and to nothing else. The window ends at exactly ten minutes, so no named ID outlives the name. Visibility does not give anyone your real key (callers still meet a throwaway) and does not make you reachable more than "Reachable for calls" already does, but it does invite stranger calls, so the ring limits and the tarpit stay unchanged. No distance, signal bars or ordering by closeness appear next to a name.

**Ending.** Exactly ten minutes after the tap (`elapsedRealtime`, so a wall clock moved back cannot extend it); Stop, an app restart or Bluetooth off end it earlier. No jump to another epoch is needed and the monotonic epoch of the ordinary IDs is never advanced by a window, so the first draft's problems (review F1, F5: continuity link to the next ID, drift past the two-epoch tolerance) do not arise. The "By ID" window keeps its 10 to 25 minutes.


**Interaction with rotating IDs and the 0.2.0-beta window.** The window needs rotating IDs on (the role 3 ID is a rotating ID). The existing Visible-by-handle code (window state, notification, 1-8 s restart, 25-minute cap) is reused for the shared state; "By ID" keeps its present meaning and wording. That a 0.2.0-beta phone shows no phantom row and still calls the ordinary row is a required phone check (N7).


## G6. Blocking (referenced)

"Block unknown callers" and "Blocked people" are being built separately and stay local. Design G needs only: (1) a `BLOCKED` row in the precedence function above (keyed by full fingerprint, so a rename does not escape it, as in Bitchat and Knit); (2) the rule that a stranger can be blocked only after the reveal gave a real key, while "Block unknown callers" acts on the untagged connection before any ring; (3) the Visible-by-name prompt above; (4) generated names are never block handles.

## Threat model

| Threat | G1 names in session | G2 generated names | G3 label and warnings | G4 verification | G5 Visible by name |
| --- | --- | --- | --- | --- | --- |
| Tracking | A stable name links every stranger session of one user; audience control, empty default and a plain warning; generated name when empty | Name is a function of the rotating ID: no new linkage | none | `K_qr` is random, per code | Links the name to the window ID only (never to the ordinary IDs), and the two window IDs across a boundary inside it; opt-in, exactly 10 minutes |
| Impersonation | "~" marker, look-alike and identical-name flags, reserved forms refused | Chosen collisions possible; display-only, flagged, binding at reveal | Your label wins; soft and hard key-change warnings | Photo useless after 300 s and first use; key possession proven live; scoped session | Anyone can advertise their own name; nobody can name another window ID (offer hash) |
| Replay | Labels bound to the call ID (existing) | none | none | Tag bound to RDI, epoch and msg1; replay cache | Pages attach only to a currently seen window ID |
| Contact-graph leakage | Name goes to verified contacts only at Ringing after the real-key path; stranger callers get no contact signal | none | Claims file is local, sealed | Only the displayer learns the scanner; mutual completion needed for leases | The window is independent of contacts; no contact data is broadcast |

## Tests and phone checks
