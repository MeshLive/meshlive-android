# Connection review 2026-10-27: design notes (not built)

A read-only review of connection setup and reconnection (integration/20261026) found the defects fixed on fix/connection-bugs (see SWITCHES for the new switches) and these items, which change the wire, the security model or several owners at once, so they are recorded here for review before any code.

**A17: a transient relay FAIL reason.** A helper that cannot set up its next hop right now (a 0x3E/133 dial failure, a scan-quota deferral, its own link busy) answers FAIL 4 (timeout) or 1 (no route). The caller's route table then marks the pair failed (`markFailed`, NO_ROUTE marks it harder), so a route that would work two seconds later is skipped for the whole mark. Proposal: FAIL reason 7 "try again" meaning "this hop is fine, its next hop failed transiently"; the caller retries the same route once inside the remaining SETUP budget and does not mark it. Wire: PROTOCOL "Experimental relayed calls" decoders reject unknown reasons, so a helper may send 7 only when the hop's link hello negotiated a new capability bit; an older caller keeps receiving 4. Security: no new information beyond what FAIL 4 already reveals (a hop below exists and failed). Needs a PROTOCOL rule and a review.

**A18: call glare (both phones dial each other).** Today the second phone's incoming link is refused because its own outgoing state exists (`state != null` in the incoming path), and the first phone's call is refused for the same reason on the other side: both calls fail. `test_coc_single_initiator` was meant to fix this but is **broken by first principles**: the higher-ID phone holds its dial and "yields" when its own `callRunning` becomes true, yet the peer's incoming call is refused at exactly that point because the higher phone already holds an OUTGOING state, so the yield ends both attempts. **Removed 2026-10-27 (switch audit, slice C) as impossible by first principles:** the yield happens only when the peer's call reaches the higher phone, and the higher phone refuses that incoming link exactly because it already holds the OUTGOING state it is yielding from, so the experiment can only end both attempts or behave as if it were off; no A/B can show it better. It had no phone run. Its switch `test_coc_single_initiator` (and the runner tunable `coc_single_initiator`) no longer exists. Proposal: decide glare at hop authentication of the incoming link: if the authenticated peer is the node this phone is dialling (same node prefix or verified contact key) and the lower node ID wins, the losing phone drops its outgoing attempt without a failure notice and accepts the incoming link as a normal incoming call (it rings, or auto-accepts when the user's own dial is still within N seconds, a UX decision for the user). No wire change; identity is decided only after authentication, never from an advert.

**B6: silent-source keepalive.** A stream source with nothing to send (camera paused, audio-only silence suppression, encoder stall) sends no BMS1 media; viewers and relays only see link heartbeats, and the media liveness timers (relay trickle, viewer frame age) read the pause as a dead route, so children re-anchor while the source is healthy. Proposal: the source's existing heartbeat carries a "source alive, no media" flag (or an empty, authenticated media keepalive every 2 s, end-to-end sealed so relays cannot forge it); relays forward it unchanged; viewers reset media liveness on it but not playout. Wire change (a flag or record type), so PROTOCOL first; relays that do not understand it must still forward it opaquely.

**B13: forwarder shutdown semantics.** One table for what a relay does to its child: upstream terminal record (forward it, wait at most 2 s for the child's ack, then close); route withdrawal (send WITHDRAW, wait at most 5 s for its ack); upstream link loss (close at once, built here as S3: the child sees the loss immediately and recovers, instead of 2 s later); local stop by the user (today the same as loss; proposal: send WITHDRAW with reason "relay leaving" so the child prefers another parent at once and does not count this parent as failing); capacity shed (unchanged). The local-stop case is a wire change (a new withdrawal reason) and needs PROTOCOL.

**T14: PSM in the advert.** The LE CoC PSM is dynamic per listener but stays fixed for the listener's life and is readable in the GATT PSM characteristic and, in some modes, the scan response. Across rotating-ID epochs a fixed PSM links the old and new IDs of the same phone (a passive tracker that sees PSM 0x0081 under ID A and then under ID B learns A = B). Proposal: re-open the CoC listener (new PSM) at every rotating-ID boundary while idle (calls and streams keep theirs), and never put the PSM in an advert; the reader gets it only over the GATT read after connecting. Cost: one listener restart per epoch; measure the gap with the existing reannounce silence. Privacy design, so PROTOCOL "Discovery privacy" and a review first.

**Simplification proposal (no behaviour change intended).** Setup retries are decided in at least seven places with their own budgets: `leSetupRetryAllowed`, `StallRetryDials`, `RelayEstablishBudget`, `RelayHopPolicy.connectRetryAllowed`, `MessageDialPhy`, `PeerAddressBook`/`LeConnectFailureClassifier`, and now the Experimental `FastFailRedial` and `FastEstablishDials` (one shared backoff, `FastEstablishDials.delayMs`, since the 2026-10-27 integration; their windows still differ); deadlines in another six (`LeSetupBudget`, the 15 s early-loss window, `CallSetupDeadlines.HOP_AUTH_MS`, the caller answer deadline, the relayed SETUP deadline, `DualSetupBudget`); ACL waits in four (`GattLinkLifetime.awaitAclDown`, `SetupRetryAclWait`, `awaitPreviousAcl`, `PendingGattCloses`); failure classes in five (`ConnectDurationClass`, `LeConnectFailureClassifier`, `isRelayEstablishmentFailure`, `isRetryableGattVideoFailure`, `TwoMRetryMemory`). Several fixed in this review were interactions between them (T3: a stall-retry Stop gave fewer dials than the ordinary rule; T1: an ACL wait that never ends on Android 10/11; A6: memory recorded on the wrong class). Proposal: one `ConnectRetryPolicy` (input: failure class, attempt, elapsed, one absolute `SetupDeadline`; output: dial after N ms / give up with a reason), one `SetupDeadline` object created per user action and passed down (no thread-locals), one `AclWatcher` per remote address (break-before-make for every dial), and one `ConnectFailureClass` used by retry, memory and fallback. Migrate one caller at a time behind the existing switches, with each old rule kept as a control arm until a phone A/B shows no regression.
