# Known interactions (second-order effects)

- **Queue grace <-> overflow paths:** large-frame grace lets sender/relay queues exceed their normal limit; code that assumes one removal makes room breaks (7b8c28c7). Test overflow while oversized.
- **Queue grace <-> rate control:** grace intentionally hides big-frame backlog from the rate controller, so single huge frames freeze without a downshift; sustained overload still downshifts.
- **Keyframe interval <-> recovery:** with a 60 s safety keyframe, recovery depends on requests (decoder errors, drops, joins). The 1-8 s backoff applies to unforced requests, which include relay-forwarded child joins: a child joining shortly after a recovery may wait.
- **Scanning <-> media:** any BLE scan on a phone carrying media (source when full, middle, legacy msmnile Classic) costs airtime and caused 0.3-1 s stalls.
- **Learned capacity <-> radio state and peers:** stores persist; Wi-Fi band, weak peers and relay vs fan-out produce different numbers. A relay ceiling (M31 GATT 774 kbps) now refuses that relay for 7 days.
- **CoC chunk size <-> throughput:** safety on ASUS-class stacks costs ~15% CoC throughput on clean pairs.
- **Probes <-> phones:** `link_capacity.py` restarts the app per direction and writes probe maxima into each phone's learned store.
- **Playout anchor <-> adaptive delay:** re-anchoring and adaptive growth both move the shared audio/video anchor; keep `MediaPlayoutClockTest` covering both.
- **Decoder timing <-> calls:** release-at-playout/low-latency now apply to private calls too.
- **Keyframe waits <-> service metrics:** after an overflow the sender drops video until a keyframe, so offered >> sent is self-inflicted; samples flag it, and fairness/rate decisions must use overflow drops only.
- **Temporal layers (experimental) <-> encoder rate control:** asking a vendor encoder for layers changed its bitrate accuracy (S24/M31 Exynos VP9 +40-60%), and libaom's SVC layer rate control mis-sized frames after keyframes. Keep this in mind before reviving any layered scheme.
- **No loss <-> latency <-> rate control:** with nothing dropped, a link slower than the stream shows up only as backlog and late arrivals; rate control must react within seconds or viewers drift toward the maximum delay. Audio drift is corrected by speed, never by skipping.
- **Temporal layers <-> hidden stack queues:** the lower visible FPS with layered M31 VP9 was not the decoder (hardware, software, low-latency off and release-at-playout off all gave 9.5-10.5 FPS); bursts sat in the Bluetooth stack where thinning cannot see them. Pacing fixes that only when frames are droppable.
- **Reference structure <-> quality:** how frames reference each other is itself a quality setting (~2.5 VMAF between libaom's own one-layer structure and a minimal one). Any change to references needs a same-build VMAF comparison where nothing is dropped, not only congestion cases.
- **Rate decisions <-> measurement noise:** predictive triggers built on the train estimate fired falsely (startup trains, CoC median 10-25% low); delivery evidence at the receiver (late arrivals) is the trustworthy signal for its own link.
- **Thinning <-> rate control <-> trim:** three adaptive loops on one stream. Thinning answers bursts within 125 ms, the rate controller only chronic shortfall, and the trim only steady encoder bias after a settling period; a faster outer loop collapsed VMAF to 40.5.
- **Hop-local rule <-> relays:** a relay cannot slow the source, so a child it cannot serve is withdrawn to reroute; only the link's own child reports lateness to its parent.
- **Encoder requests <-> actual bitstream:** an encoder flag or schema is a request (libaom ignored per-frame no-update flags; the S24 encoder layered while reporting no schema). Anything that drops frames must check the bitstream, and every A/B for it must include a case where frames are actually dropped.
- **Wi-Fi <-> every measurement:** 2.4 GHz Wi-Fi halves affected phones' Bluetooth; results without `radio_conditions` are not comparable.

**Switch register audit, 2026-10-27 (conflicts between switches, A/B validity and open design items).** A read-only audit of the switch register against the code found the overlaps below. "OPEN" means a design item that is not implemented; "partly addressed" means a change is on the branch `fix/switch-bugs`. Plain-language summary first; code references are kept in the private copy.

- **B1 Relay child recovery: nine overlapping switches (addressed on simplify/relay-pacer, F3; not yet phone-run).** One relay-child recovery policy now classifies each failed attempt once and feeds one dial decision per side; one line per launch (`BENCHMARK relay_recovery_config`) records the raw switches and what is in effect (`anyHoldoff`, `escalatingRefusalMarks`, the effective trickle and grace). Every switch keeps its meaning and the defaults decide exactly as before (a JVM replay of the earlier call-site logic over all 256 combinations of the eight relay-side switches). The budget and keep-2M now share one PHY rule after a failure before any link existed (keep 2M); the budget arm keeps the same PHY and now logs it. The escalation flag stays shared on purpose (the budget's flat-300 s control exists only with refusal escalation off), now named in the config line. Original finding: The stall guard, separate stall counting, the stall hold-off, refusal escalation, the establishment fallback, the establishment budget, hold-in-place, keep-2M, cold start and re-anchor all act on the same failed child link. The establishment budget and refusal escalation share one flag, so the budget's documented flat-300 s control does not exist while escalation is on, and the budget and keep-2M both decide the PHY after a failure before any link formed; none of the four combinations was tested. Proposed (F3, OPEN): one relay-child recovery policy with one effective-config log line, control arms pinned by the existing tests.
- **B2 `relay_child_reanchor` gates four behaviours (addressed on simplify/relay-pacer, F3).** The child-side parent-link watch and the same-parent preference have their own DEBUG switches, `test_relay_parent_watch` and `test_relay_prefer_parent`; not given, the watch follows `relay_child_reanchor` and the preference is off (since build 4, "Relay same-parent preference off" below), so its control arm keeps its meaning, and `relay_parent_trickle` and `relay_recovery_grace` can now be A/B-tested with or without the relay-side close (the inert-arm tables name the new parents). Original finding: The relay-side close, the child's silence and trickle close of its parent link and the preferred-parent grace all follow this default-on switch, so `relay_parent_trickle` and `relay_recovery_grace` cannot be A/B-tested alone. It also masks `relay_reanchor`, the Experimental arm that has never fired in a measured run. Splitting the child-side parent-link watch out of it is part of F3.
- **B3 Pacer seeding fights relay-child shedding (addressed on simplify/relay-pacer, F4; arms Experimental and off, so defaults are unchanged).** The drain guard is shed-aware: a fall in queue age across two reports that also saw the queue drop media (shed, keyframe-wait drops, thinning) is not draining (`pacer_seed_raise_blocked ... shed=`). Under the lead cap, cycles the cap held keep the last sustained drain alive instead of letting it expire while media waits. The 400/500/250/600 ms thresholds are documented together in PacerSeedPolicy.kt and logged in `BENCHMARK pacer_queue_config`; they were kept, because each answers a different question and changing one would change the defaults. Original finding: The seed-raise drain guard calls the link "draining" when the queue age falls, but on a relay that queue is the child queue, which relay-child media age sheds to a keyframe, so a shed looks like draining and another +25% raise follows on a slow hop. The thresholds also differ (400 ms shed floor against 500 ms seed-raise), and the lead cap holds the writer while the sustained-drain meter discards held cycles, so the time queue falls back to the fixed budget exactly while the child is late. Proposed (F4, OPEN): one pacer seed policy and one per-child queue policy, with a shed-aware drain guard and separate relay-queue and playout budgets.
- **B4 Benchmark launches never measure the shipped configuration (partly addressed on fix/switch-bugs).** In a benchmark launch every release-ON feature reads only its extras and defaults to OFF: rotating IDs, BMH3 and its pseudonyms, Find iPhones, voice calls, ringback, ear pause, lock-screen calls, call notifications, names, generated names, title pages, names before answer, BVMID2, audio-live, the call resolution ladder, reachability and audio focus and ringer. The promoted GATT call policy (video fragments plus speech-led playout) is never set either. Messaging v2 is the one exception: it follows its release default. On the branch the runner gets a `test_user_launch=true` variant that runs the shipped defaults, and tunable names for the features it did not know, so the shipped configuration can become an inventory dimension. Until a case uses it, no measurement describes what users run (one line in TESTING).
- **B5 Speech-led playout without fragments (partly addressed on fix/switch-bugs).** Speech-led playout is applied to every direct GATT user call, also when no fragments were negotiated (the peer lacks the bit, or the call is relayed). Only the pair fragments plus speech-led was measured ("Call head-of-line A/B"), and the register itself warns against speech-led alone. The branch gates it on negotiated fragments.
- **B6 Stall tolerance is effectively on for renewal-capable calls (documented; decision open).** The register called it Off, but a call that negotiated link renewal (the default for direct GATT calls) runs the 14 s Stage A rule whatever the switch says, because renewal needs more than 8 s. CF-CALL-10 (8 s) is therefore not true for those calls. Decision needed: amend CF-CALL-10 for renewal-capable calls, or give renewal its own tolerance and keep Stage A experimental.
- **B7 The setup-stall retry stack shares one absolute 15 s window (OPEN).** The stall guard (3 s), the ACL wait (5 s), the rediscovery (8 s) and the dials (1.5 s apart) all run inside it. The proposed `stall_rediscover_ms=20000` arm is not clamped, so it takes the whole window and leaves one dial; the two arms interfere and need a clamp or a joint A/B.
- **B8 Native Opus (OPEN; read from code, not observed on a phone).** Packet loss concealment fills the first 100 ms of any timestamp gap, including a mute, a push-to-talk release and DTX, which adds a ghost before the silence alignment. Call FEC (10% LBRR) runs on reliable ordered links where audio is never shed, the same argument the register used to reject FEC for audio-only live.
- **B9 Audio packing (documented).** Coalescing takes only plain 20 ms audio units, so with call audio pairs on, and on relayed or legacy routes that already pair or batch, it does nothing.
- **B10 Thinning's audio-only level can trip the child's trickle close (fixed on simplify/relay-pacer, latent; JVM wiring only).** The child's weak-link pause is now passed to the trickle test as a pause (the silence test still closes a link that delivers nothing). Original finding: At the audio-only level (Opus about 32 kbps) the child's trickle close (below bitrate/8 for 5 s) fires because the weak-link pause is not passed to it, and the loop repeats. Latent: on phones thinning never left level=full.
- **B11 Encoder rate loops stack (OPEN).** The output-rate trim, the quantizer floor, the bitrate adjuster or frame-rate adjuster, and the keyframe and scene-cut holds all adjust the same encoder. `test_encoder_framerate_adjuster` silently re-enables the trim, so that arm is the frame-rate adjuster plus the trim.
- **B12 One budget knob drives two arms (addressed on simplify/relay-pacer, F4).** `test_playout_time_budget_ms` (tunable `playout_time_budget_ms`) overrides the viewer's playout budget alone; `test_time_queue_budget_ms` keeps its meaning (both budgets when the new knob is absent). Original finding: `test_time_queue_budget_ms` sets both the relay time-based queue and the viewer playout target, so arm A3 cannot vary them separately. F4 would give them separate budgets.
- **B13 Overlapping transport mechanisms (OPEN).** Scan restarts from the stall watch, the stale-scan restart, renewal of all scans, Bluetooth-ON recovery and the scan-failure back-off all spend the same 5-per-30 s start gate, so starving it is possible (not verified). `scan_recovery` drives two unrelated behaviours, which confounds its A/B (F9, OPEN: split it and merge the two silence detectors; design review plus A/B, because it changes default-on behaviour). The CoC-to-GATT fallback has three overlapping paths (`coc_auto_gatt`, the per-attempt dual fallback and stream stage 1), and their ordering was not verified on phones. The PHY family has about 20 switches and 13 writers of bad-2M memory; the precedence is coherent apart from one item tracked as a code fix.
- **B14 Advanced gating hid stored choices (FIXED 2026-10-27 for the relay-child media age).** The relay-child media age choice was honoured only while Manual video settings (the Advanced toggle) was on, so a stored OFF silently reverted to ON when Advanced was turned off; it now counts with or without Advanced, as rotating IDs and the neutral name already did. Relayed calls keep the gating on purpose, now stated in their spec (`advancedOnly`): the experiment's switch is shown only in Advanced and defaults off, so with Advanced off it is off and never runs hidden.
- **B15 Catalog snapshot timing (FIXED 2026-10-27, latent).** The feature snapshot existed only after `MainActivity` ran, so anything earlier (a receiver, a provider, the boot-resume service start) would have read release-ON features such as BMH3 and names as OFF. The application now registers every spec and resolves a person's launch at process start; `MainActivity` resolves again with its own launch (a DEBUG benchmark run then reads its extras). No affected reader had been found.
- **B16 Dependencies the catalog did not model (FIXED 2026-10-27).** `dependsOn` is now a list: `bmh3_pseudonyms` depends on `bmh3` and `rotating_ids`, `find_pcs` on `rotating_ids`, and their rows grey out when rotating IDs are turned off. Their run-time checks were already gated on rotating IDs, so behaviour is unchanged. `names_before_answer` has one default (the spec's).
- **Simplifications.** F6 is built (2026-10-27): rotating IDs, the neutral name, Messaging v2 and its chat session, relayed calls, call reachability and reachable-while-browsing, the call resolution ladder, the measured Auto ladder and the GPU scale ladder are catalog specs resolved by the one rule (`FeatureCatalog.resolve`). The rule gained five stated options instead of per-feature code: a constant flag (no preference key, no Settings row), a benchmark default (Messaging v2 and its chat session run on in a benchmark launch without their extra), aliases of an extra (the neutral name's earlier extra), an extra that decides in any DEBUG launch (the two ladders and reachable-while-browsing) and Advanced-only stored choices (relayed calls). Every moved feature resolves exactly as before for every launch, extra and stored choice (`FeatureResolutionMatrixTest`); the call and naming constants, Messaging v2 and its chat session, audio-only live and the title pages no longer read stored keys that no build ever wrote. All features appear in the one `features:` snapshot line. F3 (one relay-child recovery policy) and F4 (one pacer seed policy and one per-child queue policy) are built too (see B1-B3, B10, B12; phone A/B pending). Not built (OPEN, need design review): F9 (split `scan_recovery`, see B13).
- **Objectively-worse review of six relay/pacer experiments (2026-10-27, AGENTS removal rule): none removed.** The rule needs a valid A/B on every eligible phone at the same settings showing the arm worse, or no better at extra cost, with no win anywhere. `seed_raise_drain_guard`: one pair only (A55 <-> M31, Option C A/B on e03ad81f, 3 reps): A55 -> M31 400 kbps frozen 0.27% vs 0.32% control, mean queue 26 ms vs 355 ms; 550 kbps 0.31% vs 0.63%, 13 ms vs 330 ms; at 1 200 kbps (link-limited) every arm 53-61% frozen with no guard lines. Not worse, possibly better, one pair: kept; missing: every eligible phone, relay child links (now shed-aware). `link_pacer_peer_seed`: one overnight A55 <-> M31 A/B, no effect; the weak-peer case it targets (ASUS -> A15s) was never run: kept; missing: a weak-peer pair and the other phones. `relay_upstream_dck`: mixed, not uniformly worse: parent hop 105%/101% of off, audio relay formed 8/8 vs 5/8 (wins), but the full chain with a child gave parent 274 vs 389 kbps and child frozen 83% vs 67% (n=3, low-battery S24): kept; missing: the charged-S24 re-test with n>=6 and an HCI snoop on both relay candidates. `relay_time_queue`: inert on phones because the drain was 0 kbps on slow GATT hops (319 of 319 lines, lane 9), a measurement gap that `relay_drain_sustained` was built to fill, not evidence against the arm: kept; missing: the Q31 C2 arms A0/A1/A3 on a relay chain with the sustained drain on. `relay_drain_sustained`: seen once (88 kbps, lane 10), verdict inconclusive; one cause of inertness under the lead cap was fixed here (B3): kept; missing: the same C2 A/B. `relay_child_thinning`: never left level=full on phones (lanes 9 and 11: 185 `relay_child_layer` lines, queue age at most 876 ms against a 600 ms behind limit held for 1-1.8 s), i.e. the load never stressed it, not a bug found in the policy; its B10 loop is fixed here: kept; missing: a relay test whose child link is forced behind (for example a slow child hop at the stream rate) on every relay-capable phone.
- **Arms that are not switchable (OPEN design item).** Q-M1 chose conversation rows in Contacts (option B), but the Chats tab (option A) was built and is shown whenever Messages is on; neither is a separate arm, which breaks the rule to keep the losing arm switchable. This, the `.apk.zip` share arm of `AppShare` (no caller: the chooser share is a stub in the core build) and the verified-contact `WARN` policy (no selector) are listed in PLAN as unbuilt arms, not as switches.
- **Invalid or unverified A/B runs.** The setup-retry A/B is INVALID: all 40 runs started on a remembered 1M, so the stall and retry code under test never ran; it says nothing for or against `setup_retry_acl_wait` or `stall_retry_dials`, and must be rerun after `test_reset_learned_state`. The blank-frame A/B for `drop_leading_blank_frames` has no evidence that the arm was applied (unverified) and needs analysis or a rerun before the S22 black-first-frame result counts either way.
- **Read-nowhere and half-wired switches (cleaned up 2026-10-27).** Dead code that was not an experiment arm is removed and its idea kept in PLAN: the ADPF hint session (its controller was never instantiated; switch `adpf_hint` and registry `adpf-hint-session`), the scan pause while dialling (no dial path called it; switch `scan_pause_during_connect`, registry `scan-pause-during-connect`, and the `connectOverlapMs` tag that was therefore always empty), the 32-bit tier's MediaCodec preference, the priority rollback hook, the `experimentalBle1mPhy` alias (tests use the PHY switch itself), the boot-resume release opt-in (no writer) and the stored push-to-talk preferences. Stored preferences that were read but never written are now constants: `experimental_coc_gatt_threshold` (always 12), `encoder_rate_control` (its read was overwritten by the Manual-settings value before use), and the keys of the features that are on with no off switch by design decision 2026-10-17 and 2026-10-21 (`experimental_voice_calls_v2`, `feature_call_ringback_v2`, `feature_call_ear_camera_pause_v2`, `feature_call_lock_screen_v2`, `feature_call_notifications_v2`, `experimental_peer_labels_v2`, `feature_audio_live_v2`, `feature_messaging_v2`, `feature_mv2_chat_session`, and `feature_stream_title_pages_v2`, whose one-time migration read the never-written labels key). The Git history from the first local commit shows no writer for any of them, so no installed build holds a value. Still listed as **Not wired** in the register: the reserved audio-live adaptive and relay-children names and Messaging v2 auto-thumbnails.
- **Bugs fixed by the same audit (code, 2026-10-27; JVM tests only, not yet on phones).** A release build is never a benchmark launch: any `test_` extra from another app used to skip onboarding, the go-live disclosure and the End-live confirmation, bypass the relay battery pause and Recent calls, flip the Help-relay default (A1) and apply three GATT PHY arms (A2). A call link renewal that cut a fragmented video frame no longer ends the call on the next video record (A3). Refusal escalation's hold-off has its own map, so the stall hold-off control arm changes one mechanism (A4). The Bluetooth-ON epoch stays attached when the restart-recovery entry is switched off (A5). A phy-after-auth link lost before its 2M request is not a 2M loss (A6). The lock-screen notification-permission ask reads the real setting (A7). The update screen keeps a run's extras (A8). One-step playout growth no longer changes call clocks (A9). Registry reporting: superseded proposals, switch-gated entries and one off-switch rule (A10). Hotfix: A1 and A2 (release-reachable) and A3 (both features are on for every direct user GATT call); A7 is latent while call notifications have no off switch.
