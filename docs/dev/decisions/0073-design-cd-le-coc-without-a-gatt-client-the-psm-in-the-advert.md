# Design CD: LE CoC without a GATT client (the PSM in the advert; draft 2026-10-20, revision 2 2026-10-27 after review 2, not built)

**Status: design for review; no code until the coordinator and the user approve it.** Wire rule: PROTOCOL "Draft: direct LE CoC (Design CD)". Switch when built: `test_coc_direct_psm` (Experimental, default off, both sides).

**Problem.** Before any LE CoC media flows, the connecting phone opens a GATT client to the listener's control service only to read the PSM characteristic (`c8d5a102-...`, BleL2capControl.kt:37 and the read about :1676) and keeps that client open to hold connection priority ("Keeping the GATT control connection active for CoC link priority"). Opening a GATT client makes the Android stack walk the peer's whole GATT database before our MTU request and PSM read run.

**What AOSP does (verified 2026-10-20 against `main`; which releases carry the hash path is not verified).** `bta_gattc_conn` (system/bta/gatt/bta_gattc_act.cc) loads the address-keyed discovery cache only for a bonded peer (`btm_sec_is_a_bonded_dev(p_clcb->bda) ? bta_gattc_cache_load(...) : gatt::Database()`). For an empty cache, `GetRobustCachingSupport` (bta_gattc_cache.cc) returns `UNKNOWN` on a peer with LMP version 0x0a or later, so the client first reads the server's Database Hash; `bta_gattc_read_db_hash_cmpl` then reuses a database stored under that hash (`bta_gattc_hash_load`), bonded or not. Every completed discovery is stored under its hash (`bta_gattc_explore_srvc_finished`, `bta_gattc_hash_write`); only the address-to-hash link is bonded-only. A Service Changed indication (`is_svc_chg`) forces a new discovery. So the earlier statement "the cache is for bonded devices only" is true of the address-keyed cache, not of the hash cache: an unbonded central on a stack with the hash path skips the walk when the peer's whole database hash is one it has stored. Sources: https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/bta/gatt/bta_gattc_act.cc and https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/bta/gatt/bta_gattc_cache.cc. Consequence for us: every add or remove of an app GATT service (each GattVideoServer, the CoC control service, the inbound probe) changes the hash, so a stable app database would also help unbonded centrals; that is a separate item (stable GATT database), not this design.

**Proposal (stage 1, Android 22-byte announcements only).**
1. *Advert field.* LE dynamic PSMs are 0x0080-0x00FF (Bluetooth Core, L2CAP LE PSM ranges), so one byte is the whole PSM. Byte 19 of the 22-byte announcement (`streamFps`, always 0 in call offers and viewer requests) carries the listener's PSM in a **call offer** and in a **viewer request without a recovery hint**; 0 means "no direct PSM". A viewer request with a recovery hint (bytes 14-19 are the hint) carries none. Stream offers carry none (their source connects; it does not listen). No flag or capability bit is spent: a value 0x80-0xFF is the signal.
2. *Who writes it.* Only a listener whose PSM changes with the RDI: a per-session LE CoC listener (Android 11+), reopened at every boundary as today (PROTOCOL "Rotation"). Android 10 keeps one long-lived listener per role (AOSP leak, `CocListeners`), so its PSM never changes; an Android 10 phone never writes byte 19 (it would become a passive cross-epoch identifier) and is reached through today's GATT path.
3. *Connecting phone.* A sighting with byte 19 in 0x80-0xFF and both switches on: `createInsecureL2capChannel(psm)` on the advertised address (API 29+, which the CoC transport already requires), with no `connectGatt` before it; then the hop handshake (BMH2 or BMH3) over the channel, unchanged, and the same admission and identity checks as today. A connect failure, a 4 s connect timeout or a handshake failure on that channel falls back once to today's path (GATT control read, then CoC), logged as `coc_direct: fallback | reason=`.
4. *Link priority (the role of the kept GATT client).* An app can ask for connection priority only through a `BluetoothGatt`. After the CoC handshake completes, the connecting phone opens a GATT client to the same address in the background, requests HIGH and keeps it, as today's control link does; its database walk now runs while media already flows. Until it completes the link uses the stack's default interval (the central's creation interval, about 30-50 ms). The peripheral has no public API to request priority. Measured in the test plan: interval timeline and the first 5 s of throughput and continuity.
5. *Interoperability.* Old readers decode byte 19 as `streamFps`, which call offers and viewer requests never use (to verify, V1); an old connecting phone keeps today's path. A new connecting phone facing an old listener sees 0 and keeps today's path. Every listener keeps serving the control service and its PSM characteristic for old phones and for the fallback.
6. *iPhone and Windows.* An iPhone advertises only a local name and service UUIDs (the compact form), so it carries no byte 19; carrying a PSM there is a later compact-form change. An iPhone connecting to Android could use byte 19 (iOS opens a channel by PSM after `connect`, and its discovery is explicit and per service, so the saving there is small). Windows has no LE CoC API and keeps GATT; it ignores byte 19.

**Privacy.** Today the PSM is readable by any phone that connects, before the handshake (PROTOCOL "Pre-handshake exposure", RH2). Byte 19 makes it readable by any passive scanner. It changes at every RDI epoch only because the listener is reopened; AOSP allocates dynamic LE PSMs from a small range and, by the reading to be verified (V2), in increasing order, so consecutive epochs can carry related values (for example 134 then 135): a weak cross-epoch link that a crowd of phones using the same range blurs. Review item: measure the allocation sequence across rotations with the raw observer, and whether to reopen the listener more than once per boundary to break the sequence.

**Expected saving.** The walk, the MTU exchange and the PSM read leave the critical path: about 0.7 s (S22 connecting: 995 ms minus the 64 ms CoC connect and about 0.2 s of handshake) to about 1.3 s (ASUS connecting), more on peers with a large database (1.45 s for the S24 in the unbonded call). Risk: the stack may still open internal GATT clients on a new LE link (device-name read, LE Audio or hearing-aid probes); the phone test measures it.

**Test plan.**
- JVM: byte 19 round trip; 0 = absent; a viewer request with a recovery hint never carries it; an Android 10 listener never writes it; old-decoder acceptance of a non-zero `streamFps` in call offers and viewer requests (V1); the fallback runs once.
- Phone A/B, switch on and off, frozen build: the 8 vab CoC cases plus unbonded CoC joins and calls (M31, Xiaomi and A15s connecting; S22, S24 and ASUS listening). Gates as today. Stage metrics: connected to authenticated, selection to first surface, interval timeline, first 5 s of throughput and continuity, fallback count.
- Interoperability: old build x new build both ways for calls and streams.
- Privacy: raw-observer capture of byte 19 per phone across two boundaries.

**Verification items.** V1: no old reader rejects or uses a non-zero `streamFps` in a call offer or viewer request. In this repository (2026-10-20) `streamFps` is read only for stream offers (the audio-only offer kind, AudioLiveProtocol.kt:352; the compact encoder, CompactDiscoveryAnnouncement.kt:212 and :241; a forwarder's own offer) and `DiscoveryAnnouncementCodec.decode` accepts any value; still to check against the released builds. V2: AOSP dynamic LE PSM allocation order. V3: which Android releases have the hash path of robust caching.

## Review 1 (2026-10-20, second reviewer): approve with changes, gated behind `test_coc_direct_psm`

Citations and the byte-19 layout verified (MeshControlMessages.kt 145-207). (1) **Blocker:** a call relay's mirrored offer (`PrivateCallRelayChain.parentOffer`, `child.copy`) would carry the child's PSM from the relay's address: zero byte 19 or write the relay's own PSM; check `ReceiverStreamForwarder` viewer requests too. (2) **Promotion blocker:** AOSP `L2CA_AllocateLePSM` allocates from a shared cursor that `L2CA_FreeLePSM` does not move (l2c_api.cc), so the next epoch's PSM is the old one plus a small step, linking RDIs: add byte 19 to the rotid_tracker P5 check, test a randomised cursor step (open/free a random number of throwaway listeners), report the measured residual. (3) Zero byte 19 across a boundary unless the listener was reopened. (4) Fall back only on transport failures before the first handshake byte, never after an authentication result (tarpit, BDO1); require a current-epoch sighting. (5) Request HIGH priority as soon as the background client connects; keep it for the link. (6) State exactly which announcement versions and windows write byte 19; V1 must cover every released decoder including iOS. (7) Detect the listener type rather than the SDK. Test gaps: relay mirror, waiting viewer across a boundary, stale PSM, tarpit count, interval timeline, privacy over 3 boundaries per required phone.

## Revision 1 (2026-10-20): review 1 addressed

These rules replace the matching parts of the proposal above.

1. **Addressed (blocker): only the listener's own announcement carries byte 19.** A phone writes byte 19 only into an announcement it builds for its own listener. Every mirrored or derived copy writes 0: the call relay's parent offer (`PrivateCallRelayChain.parentOffer`, PrivateCallRelayChain.kt:133, a `child.copy` that would otherwise keep the child's byte 19 under the relay's address) and any other copy made with `DiscoveryAnnouncement.copy`. Stage 1 never writes the relay's own PSM (a relay's upstream listener is a later step). A forwarder's viewer request to its parent is built by the ordinary request builder for the forwarder's own listener, so it may carry the forwarder's PSM; its downstream stream offer is a stream offer and never carries one (byte 19 is its real frame rate). Implementation note for review: one choke point stamps byte 19 when the advertising set is started from the owning listener, rather than at each builder.
2. **Addressed (promotion blocker): the shared PSM cursor.** AOSP allocates LE dynamic PSMs from a shared cursor that freeing does not move (`L2CA_AllocateLePSM` / `L2CA_FreeLePSM`, l2c_api.cc), so an epoch's PSM is the previous one plus a small step. Before opening the listener at each boundary the phone opens and frees a secure-random number (0 to 15) of throwaway listeners, so the step is random. That is not enough by itself: the promotion gate is the rotid_tracker P5 check run on byte 19 (pairs of consecutive epochs linked by the PSM above chance, per required phone, over at least 3 boundaries), and the measured residual is reported in this record before any default changes. If P5 fails, the design stays off.
3. **Addressed: byte 19 is zero across a boundary unless the listener was reopened in this epoch.** A re-announcement on a new RDI (for example a waiting viewer's request at a boundary) writes byte 19 only when its listener was opened in the current epoch; otherwise 0.
4. **Addressed: the fallback is narrowed.** The direct path is tried only from a sighting of the current epoch. It falls back once to today's path only on a transport failure before the first handshake byte (connect refused, a 4 s connect timeout, the channel closed before any byte). Any handshake outcome (an authentication failure, a tarpit delay, a `BDO1` or opening mismatch) is final, as on today's path, so a failed peer gets no second attempt and the stranger tarpit counts it once.
5. **Addressed: HIGH priority at once.** The background GATT client requests HIGH as soon as it is connected, before its discovery completes (the stack applies it when its discovery lock releases), and keeps it for the life of the link, as today's control client does.
6. **Addressed: exact scope.** Byte 19 is written only in version 5 announcements: a call offer at route cost 0 that is not a relay offer (no relay flag, not a relay-helper offer), and a viewer request without a recovery hint. Never in version 2 (fixed prefix: Classic, Visible-by-handle windows, a downgrade to a version 2 source), never in version 8 window offers, never in stream offers, never in the compact (iPhone) form, never in title or reach pages. V1 now covers every released decoder: Android builds, the iOS app and the Windows app (each must ignore a non-zero `streamFps` in a call offer or viewer request); the design stays off until all three are checked.
7. **Addressed: the listener type, not the SDK level.** Byte 19 is written only when the CoC listener registry reports this role's listener as a per-session listener opened in the current epoch (`CocListeners`/`CocListenerHub` knows whether a role holds the long-lived shared listener of the AOSP-leak workaround). Any phone that holds a long-lived listener, whatever its SDK, writes 0.
- **Test gaps added to the test plan:** JVM: the relay mirror writes 0; a waiting viewer's re-announcement across a boundary writes 0 unless reopened; a stale PSM (connect refused) falls back once; an authentication failure does not fall back and counts once in the tarpit; byte 19 never appears in versions 2 and 8, stream offers or recovery requests. Phone: the interval timeline of the background client; privacy over 3 boundaries per required phone (raw observer plus rotid_tracker P5).

## Review 2 (2026-10-26/27: reviewer and reviewer Opus, independent) and Revision 2 (2026-10-27)

Both reviews returned CD for revision, as second priority after GD.

| 1 | The 0-15 throwaway-listener step is still linkable. The next PSM is one of about 16 successors in a 128-value range (reviewer). Opus estimates about 1/512 per chance alignment over 3 boundaries. Freeing a PSM never rewinds the AOSP cursor. | reviewer, Opus | High | The unlinkability claim is **withdrawn**. Byte 19 is written **only for verified contacts**, masked: `byte19 = 0x80 or ((psm and 0x7F) xor (HMAC-SHA256(presenceKey, "BluetoothVideoMesh/Discovery/Psm/1" ‖ epoch)[0] and 0x7F))`. The presence key is the one rotating-ID recognition already shares with contacts; the epoch is in the input, so the mask changes every epoch. **Status: revision 2 for the coordinator and the user; no code.** After the walk split (Design GD, revision 2, "Decision input"), CD is the only design that removes the 0.5-1.4 s walk for pairs with an Android 10-12 phone or a BT 5.0 controller, on the CoC transport. That makes it the latency priority ahead of GD. Its gate is the masked contact-only PSM (item 1).
