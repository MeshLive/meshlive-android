# Release, licence and later direction (2026-10-10)

- Licence: GPL-3.0-or-later. Chosen over Apache/MIT to prevent closed clones of a security app. AGPL adds nothing for a serverless peer-to-peer app. Dual licensing stays possible while the project holds the copyright (a CLA for outside contributors). The test-video generator in `tools/video-stress-generator/` is MIT.
- Distribution: open source; an unofficial signed APK on GitHub Releases, plus F-Droid and IzzyOnDroid; separate arm64-v8a and armeabi-v7a APKs. No Play Store or App Store for now. iOS is published as source only.
- INTERNET permission accepted, for the local-only "Share app nearby" Wi-Fi Direct server. The app never contacts the internet.
- Name: MeshLive. The app name and organisation are the same: GitHub org github.com/MeshLive. HexLive was found taken; NodeLive was rejected because an IoT dashboard project uses it; meshlive.de is a German clothing brand (a different class). The application ID is `io.github.meshlive.app` (no domain is bought for now; the iOS bundle ID will be `io.github.meshlive.ios`); the Kotlin package stays `com.example.bluetoothtest`, and the host tools follow the ID (`MESHLIVE_APP_ID` overrides it). Web checks only; not legal clearance.
- Unreadable secure store: fail open with a banner and retry. Names are shown when the device is unlocked and hidden on the lock screen.
- Started as default-off experiments that do not block launch: rotating discovery IDs (design first), native libopus (FEC/PLC), a call resolution ladder, iPhone relaying, automatic store-and-forward sync. Translations dropped for now. The Wi-Fi bearer comes later (see [roadmap.md](../roadmap.md)). Experimental switches are tracked in the "Experimental, alternative and optional behaviour" register in [architecture.md](../architecture.md).
- UI: push-to-talk is not a mode (hold Mute to talk inside calls). No relay toggle on the Watch screen (automatic, one Settings switch). No security, heat or battery text unless actionable. iOS uses native HIG while keeping Android's screens, flow, wording and brand colours.


- **Q23, cloud backup: off.** `allowBackup="false"`; the sample backup and data-extraction rules files were empty and were removed with their manifest attributes. Since 2026-10-21 (Platform behaviour audit, B2) explicit exclude-all `dataExtractionRules` exist again, because Android 12+ device-to-device transfer tools are not required to honour `allowBackup="false"`. The keys are Keystore-bound, so a restored copy would be unreadable, and call history by peer prefix must not reach Google backup. Briar, Meshtastic, qaul and Gilgamesh do the same.
- **Q16, notification names: shown unlocked, hidden on the lock screen.** The incoming-call alert already followed this; ongoing call and stream-viewer notifications now carry the peer's name in their full version and stay name-free on a locked screen. The opt-in for names on the lock screen stays. Audio-only live notifications never carry a name.
- **Q-SKIP1: the PHY-move backlog skip is on by default for live streams with a fixed (manual) bitrate.** Off with Auto quality (Auto alone gave no benefit), for calls and for audio. The launch extra `test_phy_move_skip_backlog=false` is the control arm; `=true` forces it on. Evidence: frozen share 64.5 / 59.8 / 25.8 percent without the skip against 9.6 / 9.1 / 8.8 percent with it on a fixed 300 kbps stream; under Auto 7.3 / 8.6 / 5.8 against 5.2 / 7.2 / 7.4.
- **Q15, unreadable verified-contact store: fail open with a warning and a retry (option A).** Calls still work. The home screen shows "Verified contacts couldn't be loaded". A temporary Keystore or I/O error is retried with backoff (2 s doubling to 60 s) and the banner clears by itself. A corrupt file is kept and never overwritten; the banner offers "Reset verified contacts".
- **Q22, old builds: no special handling.** The user expects very few old installs ("they'll just get to know to update"), so there is no notice and no wire change.
- **Kept as built:** Q5 speaker for video calls and earpiece for audio calls, with a toggle; Q24 "Share app nearby" hidden until T9; Q35 the version tag in link hellos stays on; Q34 the "Phone" rename notice with its Restore button; Q25 CoC to GATT counting only on Android 10.
- **Q8:** no-loss stays the default; bounded age stays Experimental.
- **Q-PHY1:** keep remembering a 2M failure; the 2M-after-authentication option stays Experimental and off.
- **Q-P1 to Q-P5:** the recommended options. **Q-B1 to Q-B3:** confirmed.
- **Third batch.** Q26 and Classic: the root cause is the address (Classic pages a fixed BR/EDR address that LE advertising never carries and Android hides from apps), not timeouts. Direction: discover and authenticate over GATT, exchange the Classic address over that authenticated link (a phone learns its own address when a peer echoes the address of an incoming Classic connection), then move media to Classic make-before-break; bounded connect becomes the fallback. Design record and review before coding. Q31: relay queues and viewer buffers sized in milliseconds from the measured drain rate and jitter, as an A/B arm; per-child temporal-layer selection at relays (relay child thinning, under test) and three-layer (L1T3) streams are a later, larger A/B, not dropped. Q3: encoder work is per chip-family tuning (hardware intra refresh and rate-control mode, libaom realtime speed and threads, SVT-AV1 comparison, hardware AV1 encoders where present), ranked per phone by measurement; no GPU encoder and no custom codec (dedicated video blocks already beat GPU and CPU, and a custom bitstream needs its own decoder everywhere).
- **Design CX questions.** Classic cannot be made private: BR/EDR has no rotating address, the fixed address is visible over the air in every Classic connection (part of it in each packet's access code), and anyone who learns it can page the phone later while Bluetooth is on. So the Classic upgrade runs only between mutual verified contacts, in both directions and in every mode; strangers, unverified phones and relays through strangers stay on LE. With rotating IDs on it is off by default, behind a setting that says contacts can recognise this phone. The address is sent only to that verified contact inside the encrypted link, never stored for or sent to anyone else (this replaces the two-peer confidence rule of Q-CX4 for strangers). Q-CX2 reuse the one-time visibility prompt only while the phone has no self-address, never mid-call; Q-CX3 keep the LE link as a low-priority standby and measure its cost; Q-CX5 upgrade only with Connect without pairing and its child setting on; Q-CX6 two Classic media children per sender or forwarder until measured.
- **Design CX, default and follow-ups.** The Classic upgrade is off by default for everyone, not only with rotating IDs: it is an opt-in setting for users who understand that contacts can recognise the phone and who need the extra speed; ordinary users stay on LE. Q-CX7 identify the host by the per-attempt UUID in the inquiry response where the stack publishes it, else by the exact Bluetooth name sent over the encrypted link with at most two candidates paged, else no first-contact search on that stack. Q-CX8 the setting says plainly that a contact learns this phone's fixed Bluetooth address and keeps it after removal. Q-CX9 the link-hello capability bit is accepted and disclosed in PRIVACY.
- **Design CX, review 2 follow-ups.** Q-CX2/Q-CX7 revised: Android discovery pages candidates before any authentication, so there is no inquiry and no visibility prompt; the user types their own Bluetooth address (Settings > About phone > Status), confirmed by the first ticket-bound connection. Q-CX10 the upgrade also needs a per-contact opt-in on both phones, which creates a shared key for this feature only (removing the contact deletes it). Q-CX11 the typed address is the only seed (plus a DEBUG seed).
- **Q-CX12, a mistyped address.** The address is typed twice, must match and pass the format check, and the setting shows its last four characters to compare with Android Settings. The residual is accepted and disclosed in PRIVACY: a typo that happens to name a responsive nearby device lets that device see the dialing contact's address during paging. The phone test includes a wrong address that belongs to a responsive device.
- **Q36, relays on a dual-role-limited controller.** When a relay's Bluetooth controller cannot schedule a 15 ms child link beside a 15 ms parent link (seen on the Exynos 9611 in the M31), relay upstream DCK becomes the default where the parent is Android 14+, once the S24 video A/B passes; the next experiment is a parent re-anchor (the parent cycles connection priority inside a dead stretch). A dual-central relay and excluding such controllers from relay duty stay alternatives.
- **Q37, background scanning on Android 10-11.** Those versions return no background BLE scan results without working location access or with the Location switch off. Sessions there declare a `location` foreground-service type (Android 10-11 only, as Meshtastic does) and the app tells the user the Location switch must be on; no background-location permission is requested.
- **Q38, battery-optimisation exemption (revised by the user).** Onboarding explains why a mesh phone must keep running in the background, what it costs in battery, and the warning, then offers the system one-tap exemption prompt there; it can be skipped and is offered again from Settings and when an always-on role is turned on. (If a Play build is published, its review risk is checked first; the sideload build ships it.)
- **Q39, hardware codecs on phones without AV1/VP9 encoders (revised by the user).** Efficiency first: the encoder ladder prefers the best codec both phones handle in hardware, AV1, then VP9, then HEVC (H.265), and uses AVC (H.264) only as the last, universal fallback. HEVC is roughly VP9-class per bit and AVC wastes the most bandwidth. Both are default-off switches until an A/B of quality per bit, battery and heat against software AV1 on a cheap phone; CBR is always set explicitly. Revised on 2026-10-27 (Design HC): HEVC ranks above VP9 (hardware AV1, HEVC, VP9, then H.264, all hardware, before any software encoder), and a smoke test plus one thermal comparison replace the long A/B.
- **Q40-Q50, device-family and test follow-ups (2026-10-15).** The user accepted the recommended option for each, with two standing conditions: never compromise privacy or security, and never degrade the experience on working phones to accommodate a few that cannot connect (fallbacks act only on the failing phone or link). Q40: stuck Bluetooth on Android 10-12 gets a notice with a button to Bluetooth settings (apps cannot toggle Bluetooth at targetSdk 33+). Q41: resume relaying after reboot or update is opt-in and off by default. Q42: no companion-device association for now (it conflicts with rotating IDs). Q43: software echo cancellation only after measurement. Q44: the session wake lock stays Experimental, then defaults on in the sideload build only. Q45: a cheaper codec on low battery waits for the Q39 ladder data. Q46: Telecom self-managed calls get a design record only. Q47: publish the 32-bit (armeabi-v7a) split. Q48: DCK becomes the default for Android 14+ parents with a relay-capable child (the S24 video A/B passed). Q49: the CoC MTU prime becomes the default on fresh-ACL stacks (Android 12-13 centrals) after the lane 11 breadth runs; other stacks skip it. Q50: streams get the staged GATT fallback of Design SG (receiver notice, receiver restart on GATT, then a separate GATT child pool at the source), behind coc_auto_gatt; healthy viewers keep their transport and authentication is unchanged.
- **Q48 held (2026-10-15, afternoon).** The DCK default was reverted to off the same day it was promoted: the first full-chain A/B with a child (S24->M31->A15s, raw 440 kbps, lane 11 block E) gave parent 274 vs 389 kbps and child frozen 83% vs 67% with DCK on (n=3 per arm, S24 at 15-17% battery, weak hops in both arms). That contradicts the parent-only evidence, so DCK stays Experimental until a clean full-chain retest (charged S24, n>=6 per arm) settles it; under the user's standing condition a change must not degrade working phones.
- **Q-QL1 (2026-10-19), expiring verification codes on by default.** Answered by the user's priority call to fix calling saved contacts: `bvmid2` is ON by default (option A). The static BVMID1 code opens no Bluetooth session, so it moves no presence lease, and a contact added with it could not be called from Contacts (with rotating IDs a contact is found only by the rotating ID its lease lets this phone compute). N5 and the Design QL phone test passed on two Android pairs. An explicit stored choice still wins; "Accept older verification codes" (`bvmid1_compat`, off) stays the compat switch for 0.2.0-beta phones, which cannot read BVMID2 codes. Consequence kept from review F18: with `bvmid2` on, a contact only checked by safety code gets no new presence lease until both phones scanned each other, so Contacts tells the user "Ask <name> to scan your code too". iOS must read BVMID2 before its next release.
