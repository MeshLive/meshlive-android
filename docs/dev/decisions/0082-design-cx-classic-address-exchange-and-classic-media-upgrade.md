# Design CX: Classic address exchange and Classic media upgrade (verified contacts only, opt-in)



**Problem.** Classic RFCOMM carries about 1,500 kbps, several times what LE GATT or CoC sustain here, but it pages a fixed 48-bit BD_ADDR. Discovery is LE and uses resolvable private addresses, so the scanner never sees the BD_ADDR, and Android hides a phone's own address from apps (`BluetoothAdapter.getAddress()` returns `02:00:00:00:00:00`). Today ("Connect without pairing", `ClassicBondFree.kt`) a phone learns a peer's address only after a Classic contact, and the first contact needs a Classic inquiry with the other phone made visible (the system prompt).

**What Android lets an app know (checked against the AOSP Bluetooth module sources at commit 745ee92b87ed, the Android 6.0 behavior page and the API documentation).**

The accepted-socket row and the user typing their own address are the only legal sources used.

**Design.**

1. **Contacts only, both ways, with a key both sides already hold.** Being verified is one-sided by nature (a QR scanned from a poster), and any message that says "I verified you" tells the peer so. The gate is a **Classic pairing key `K_cx`** per contact, established with an explicit per-contact opt-in on both phones ("Allow Classic Bluetooth with this contact", default off). In an answered session each phone whose switch is on and whose peer is verified sends `PAIR(epoch)`; a phone that already holds a key **also answers** a received `PAIR`; when both sent and received, both derive a candidate key from that session's exporter and the epoch and stage it as `PENDING`. A `PENDING` key is promoted to `CONFIRMED` only when the peer's `CONTACT` tag verifies under it, so a crash on one side, a reset or a re-enable recovers by the next `PAIR` without ever sending `CONTACT` into a void. Epochs are 64-bit, monotonic and never reused; a peer epoch more than 1,000 above the phone's own is ignored. If a `CONTACT` tag verifies under none of the keys held, the verifier sends `PAIR` **even when it holds a confirmed key** (one phone confirmed the new key while the other let its pending key expire and both held different confirmed keys), at most once per session and three times per contact per 24 h. `K_cx` proves that **the peer opted in to Classic with this phone**, not that it still verifies this phone (each phone checks its own store and switch at every use). A phone holding a key the peer deleted still sends `CONTACT`; the stale-`CONTACT` disclosure (the peer learns this phone still holds a key for it) is accepted and stated, and **no `HOST` and no dial happen unless both sides sent and received a valid `CONTACT` in this very session.** Revocation, reset (a new epoch) and expiry of `PENDING` are specified in PROTOCOL.
2. **Address echo.** A phone that accepts an incoming Classic connection from a key-holding contact (and not on a relay leg) reads `getRemoteDevice().getAddress()` and tells the dialer, inside the encrypted link and authenticated by a key tag, the address it saw (`ECHO`). The dialer learns **its own** BD_ADDR from its first Classic connection to a contact.
3. **Self-address record (a fallible routing observation) and what may be offered.** Sources: the address the user typed (twice, format-checked, last four digits shown for comparison) and echo votes, one per stable verified contact. **To any contact a `HOST` carries only the typed address** (user-verified). To a contact `C` it may also carry an address that `C` itself voted for or that is `provenFor(C)` (a ticket-bound bind on this phone's listener proves only that `C` reached this phone; the accepted socket does not show which address `C` dialed, so a contact could echo a false address X and then dial the real address Y, and the proof must not make X offerable to others). A malicious contact is thus sent back only what it supplied. Corroboration by several contacts is not accepted instead, because colluding contacts corroborate each other; without a typed address a phone serves only the contacts whose votes or proofs it holds. A newer vote never replaces the typed address; an incumbent for `C` changes only by `C`'s own newer vote or a bound connection by `C`; the previous selection stays offerable for 7 days; `disputed` only when two or more distinct contacts disagree with every candidate. No promotion by elapsed time; routing confidence, not hardware proof. No-backup storage; removed by the emergency wipe, when the feature is turned off and per contact on revocation.
4. **Address advertisement over the authenticated link.** After fresh mutual `CONTACT`, the hosting phone sends `HOST` (address, one-time ticket, validity) inside the encrypted session, never in an advertisement, never in the end-to-end session, never forwarded. Received addresses are claims in a separate store; they never enter or evict anything in the existing address book until a connection at that address authenticated as the expected identity.
5. **Media upgrade, make-before-break.** After the call is answered (or the viewer admitted) and 3 s of media:
   - **Roles and dial.** The side that accepted the session hosts when it holds an offerable address; otherwise the initiator. The host opens an insecure RFCOMM listener on a per-attempt random UUID and sends `HOST`. The guest pages (12 s, at most once per 30 s per contact), reads a fresh 16-byte host challenge and sends a pre-proof that binds the challenge and the exact first handshake message (built once, hashed, the same bytes written); the host verifies it before sending any handshake byte. The ticket is consumed atomically on a valid proof; a retry uses a new ticket and UUID. A failed or timed-out dial is reported to the host with `DECLINE` reason 6 so it can count failures (3 per address per hour stops it).
   - **Handshake options (stage 1).** Same protocol version as the old link, fixed; expected peer pinned to the old link's node ID and fingerprint; no build tag, no pseudonym, no advertisement-bound contact tag, no `BDO1`. `BIND` MACs (ticket, challenge, new transcript) under a key exported from the old link's key schedule.
   - **Simplification principle (design decision, round 6).** The earlier cutover sprouted interleaving holes because it aimed for a perfectly lossless switch. The invariant now is: **no cutover race may ever end the session while a carrier is alive; races may only lose records.** At the consumer any record that is stale, from a fenced carrier or out of order is dropped, never thrown; indispensable state survives by the existing state-only re-assertion; video recovers with a keyframe request after any gap; session failure happens only on an authentication or protocol violation or when no carrier is alive. Wherever a state or row existed only to keep the switch lossless, it was replaced by "drop, re-assert, keyframe" and deleted.
   - **The cutover in one paragraph.** Two carriers, `O` (LE) and `N` (Classic); one `SEND_ON` per sender and one `ACCEPT_FROM` per receiver direction. To move, the sender picks the next frame boundary, writes one in-band `SWITCH(gen, boundary)` on `O` after the last pre-boundary record, sends everything from the boundary on `N` and re-asserts state once. Nothing waits: no acknowledgement, no latency probe, no sender hold. The receiver opens the new-link gate when the `SWITCH` marker is dequeued in order; `N` records that arrive earlier are held for at most 1 s and 5 MiB (a fixed ceiling; on expiry they are dropped and `N` is closed). If `O` dies, the sender writes the same `SWITCH` on `N` (the old tail is lost) and the receiver, which sees `O` die itself, accepts `N` at once. If `N` fails or is closed, both ends fall back to `O` (`RESUME` on `O`, partial fragment assembly dropped, keyframe requested, 30 s cooldown, at most 2 fallbacks per session). Closing `N` is the only fate sharing needed.
   - **One inbound consumer.** Reader threads only parse and stamp records with a carrier instance id (a new socket per attempt, so ids never recur). Content-order-relevant items (media, `SWITCH`, `RESUME`) go through one ordered content queue and a single non-blocking consumer that applies the receiver rows at dequeue before the existing endpoint dispatch (so a blocking `awaitTerminalAck` in `AndroidVideoReceiver` cannot delay a marker). There is no epoch stamp, so a valid record that follows a marker is never discarded. Everything else (`ECHO`, `PAIR`, `CONTACT`, `HOST`, `DECLINE`, `BIND`, `READY`, `CLOSE`) is handled directly from the reader thread. A defensive rule peeks the cleartext `BME1` and mesh sequences and drops any record not above the last opened one, so the opener can never throw at a cutover.
   - **Per-carrier liveness.** A socket error, a write stalled 2 s or no inbound byte for 2 s closes that carrier only; each carrier has its own timeout, so the standby cannot mask a dead Classic link. After `O` is lost there is no standby: a stall on `N` is a session failure through the existing path.
   - **Fragmented call video.** At a normal switch no frame is split. After a `RESUME` or a switch seen over `N` the consumer drops the partial assembly and skips fragments until offset 0 arrives with an empty buffer (the only resync point); while suppressing, `requireIdleFor` must not fire for lifecycle records or signals; strict checks are unchanged elsewhere.
   - **Controls and termination, with no acknowledgements.** After every carrier event the sender re-asserts once, under fresh sequences, the current stream lifecycle state, the microphone and camera state and a pending `ENDED` (inside the existing 2 s `STREAM_END_ACK_TIMEOUT_MS` wait); never a superseded value, never old ciphertext; a late re-assertion cannot revert a newer one because a direction's records are strictly ordered and only one carrier delivers it. Pre-`ACTIVE` signals are never re-sent and no cutover starts before the call has been `ACTIVE` for 3 s. **`HANG_UP` has no ack and no retry**: it is sealed on the current carrier, `CLOSE` goes to every live carrier that finished `BIND` and `READY`, the microphone, camera and screen are released at once, writers drain in the background and the session waits for all readers or 3 s (as today). The content and `CLOSE` may arrive in either order; the first wins. One closing coordinator and one finalizer own shutdown; a second hang-up while ending is benign; a carrier ending is a bearer event, not the end of the call.
   - **Limits.** `READY` exchanges each side's receive ceiling, device-family cap and transport budget, independent of media. Send limit = min(requested, peer's receive ceiling, family caps, transport budgets); a requested bitrate is never raised; LE limits and transport-keyed state (close wait, pacer seed, flush interval, playback delay profile, audio headroom) return on fallback.
   - **Never costs the existing link.** The upgrade attempt (paging and handshake) is cancelled if the old link's oldest queued record passes 2 s while it runs.
6. **Scope in stages.** Phase 1: direct calls and direct stream links with real identities on both sides. Phase 2: stream forwarder hops (hop-local; only between contacts with keys). Phase 3: call relay hops, which first needs Design C's "one bearer end to end" rule amended; not in this design. iPhones cannot open RFCOMM and never set the bit. On a Classic link where a relay `SETUP` applies, `ECHO` is omitted, so the `BDO1` and `SETUP` first-record rules win.
7. **Bootstrap: authenticated out-of-band seeding; no inquiry, no visibility prompt.** The first Classic contact needs the host's address, and a phone learns its own only from an echo. Searching for the host by Classic inquiry is **disabled**: Android discovery can page found devices for their names, which sends the initiator's BD_ADDR before the app has authenticated anyone, names are spoofable, and an advertised per-attempt UUID can be copied to another address.

| Tier | How | Prompts | Status |
| --- | --- | --- | --- |
| 0 | A phone with an offerable address and a confirmed key for the contact hosts over the LE session; the guest dials; the echo gives the guest its own address | none | Normal operation |
| 1 | The user types the phone's Bluetooth address **twice** (shown by Android in Settings > About phone > Status; the app validates the format and never reads it itself; the setting shows the last four digits for comparison).    **Mistyped address (Q-CX12, decided by the user 2026-10-14).** The address is typed twice, must match and pass the format check, and the setting shows its last four characters to compare with Android Settings. The residual is accepted and disclosed in PRIVACY: a typo that happens to name a responsive nearby device lets that device see the dialing contact's address during paging, before any UUID lookup or `BIND` can reject it (a random 48-bit typo hitting a nearby device is negligible, and a malicious contact already learns the guest's address in this design). The phone test includes a wrong address that belongs to a responsive device.

   Whether insecure RFCOMM raises a pairing dialog or stores a bond is **not** a given: AOSP `btif_dm.cc` (`btif_dm_ssp_cfm_req_evt`, `btif_dm_get_pairing_type`) auto-accepts a Just Works pairing only when neither side set the dedicated-bonding bit, the bonding was not API-initiated and the peer is not a HID pointing device (the temporary-pairing path); otherwise it raises the consent request and the bond is persistent. Absence of dialogs and bonds is a measured compatibility gate per stack (T-CX1); a stack that shows a dialog or stores a bond keeps the feature off (a DeviceFamilyPolicy entry with the evidence) and stays on LE. The "zero prompts" claim is limited to contacts with a key and a seeded address on a validated stack.

**Failure handling.**

| Failure | Result |
| --- | --- |
| Peer lacks the bit or a key, switch off on either side, iPhone, permission missing, a pseudonym or relay leg | No record is sent; nothing changes |
| One side lost its key (crash, reset) | The next session's `PAIR` repairs it (the other side answers even though it holds a key); a `PENDING` key expires in 7 days or 3 failed sessions |
| `HOST` address wrong (stale, lying contact, typo, third phone) | The dial authenticates as someone else or times out; the claim is dropped; the guest sends `DECLINE` reason 6; 3 failures per address per hour stop it; media unaffected |
| Host listener cannot be opened, guest radio busy | `DECLINE` with a reason; no retry for 30 s |
| Proof, `BIND` or identity mismatch | Silent close of the Classic socket; `bind_fail`; the ticket is not reusable |
| `N` fails, stalls or is closed after the switch (either end, either direction) | `N` is closed; both directions use `O` again; `RESUME` on `O`; partial fragment assembly dropped; keyframe requested; state re-asserted; 30 s cooldown, at most 2 per session. The session continues |
| `O` dies while `N` lives (before, during or after the switch, seen by one end or both) | `SWITCH` on `N` (or its repeat); `N` is the only carrier; the old tail is lost; keyframe requested; state re-asserted; a later `N` stall is a session failure |
| Early `N` records and the `SWITCH` marker never arrives | Held at most 1 s and 5 MiB, then dropped and `N` closed; fallback as above |
| A stale, duplicate or out-of-order record at a cutover | Dropped at the consumer; never an error |
| Both carriers gone | The existing failure path of the session |
| Echo disagrees with the selected address | One vote, not a replacement |
| Radio contention starts a freeze on the old link | Cancel the attempt, `abort reason=old_link_degraded` |
| `HANG_UP` | Sealed on the current carrier, `CLOSE` on every live carrier, resources released at once, 3 s reader wait |

**Threat model.**

| Threat | Answer |
| --- | --- |
| A one-sided verifier learns or reveals verification | Only `PAIR` (opt-in, per contact) discloses; a stale `CONTACT` tells the peer only that a key is still held, accepted and stated; everything else is gated on a key both sides established and a fresh mutual `CONTACT` |
| A stranger offers its own address to learn a rotating phone's | No `HOST` is acted on before fresh mutual `CONTACT`, which needs the key |
| A malicious contact poisons the address other contacts are sent to (including echoing a false address and then dialing the real one to "prove" it) | Other contacts are sent only the typed address; a contact is sent back only what it voted for or reached; proofs are scoped to the contact |
| Hijack of the media link | Pre-proof (fresh challenge, exact first message), pinned identity, `BIND` over the new transcript with opposite roles; media stays sealed by the unchanged `BME1` keys; a link-layer attacker can only drop or delay |
| Address spoofing | The address is only a hint; the handshake decides who answers; claims never evict address-book entries |
| A contact lies about **its own** address (`HOST`) | Points the guest at a third device for about one bounded page per 30 s; separate claim store; the guest verifies the node ID; an RFCOMM connect, not a pairing |
| A mistyped address names a responsive device | Accepted and disclosed (Q-CX12); format check and double entry make it improbable |
| Tracking through the stable address | Never in an advertisement, never to a non-key peer; a contact keeps what it learned even after removal, and no revocation can revoke a BD_ADDR (stated in Settings and the user guide); a Classic session exposes the LAP to any radio in range and the phone stays pageable while Bluetooth is on |
| Pairing before authentication by a search | No search is made by this feature (Tier 2 disabled) |
| Capability bit 5 | One more stable capability bit visible to strangers who connect and to a sniffer of a cleartext BMH2 hello; hidden in BMH3 from sniffers; disclosed in PRIVACY |
| Replay of `HOST`, pre-proof or cutover records | `BMS1` ordering; challenge and message commitment; single-use ticket; `SWITCH` generations (a repeat is ignored, a different boundary for an old generation is dropped and logged) |
| Denial of service on the listener | Phone-wide budgets (2 concurrent upgrade sockets, 6 accepts per 30 s), absolute 2 s and 5 s watchdogs, at most 2,081 pre-authentication bytes, one HMAC and one hash, no signing; the ticket survives unrelated invalid connections; suppression by a radio attacker is an accepted residual because LE continues |
| Oversized records | `BCX1` limit (64 bytes, 128 before BIND) enforced from the header's length before allocation; receiver hold limits in frames, records and bytes |
| Downgrade by stripping the bit | Link hellos are signed; blocking Classic keeps LE |

- DEBUG `test_classic_address_exchange=true`: sign bit 5, `PAIR`, `CONTACT`, `ECHO`, `HOST`, the self-address record (needs bond-free Classic).
- DEBUG `test_classic_upgrade=true`: also host/dial/cutover (implies the exchange). The text says plainly that a contact learns this phone's fixed Bluetooth address and keeps it after removal, and that anyone who learns it can look for the phone later. **Alternatives not taken.**

| Alternative | Why not |
| --- | --- |
| Address in the LE advertisement; public-address advertising; LE bonding with cross-transport key derivation | Stable identifier; privileged API; pairing dialogs and a stored bond |
| Inquiry plus UUID or name identification of the host (Tier 2) | Discovery can page candidates before authentication; names and copied UUIDs are spoofable; disabled |
| A "both verified" hello flag or a `CONTACT` that states verification | Leaks one-sided verification; replaced by the key |
| Commit-reveal or private set intersection per session | Heavier than a once-established shared key for the same property |
| Reuse presence leases as the mutual proof | Leases exist only with rotating IDs on and expire in four weeks |
| A fixed upgrade UUID | A scanner could look for it; the UUID is per attempt |
| A sender-side lookahead boundary and hold (the first cutover draft) | An idle sender never reaches the boundary and an ack round trip on a congested LE link cancels the cutover; replaced by the two-phase cutover |
| A lossless cutover with acknowledgements, epochs, commit requests and a measured latency | Each guarantee added states and rows and each review found a new interleaving hole; replaced by the lossy, never-fatal design and a model test (round 6) |
| Per-direction fallback | Doubles the state matrix; closing `N` returns both directions to LE |
| Acknowledged and retried controls (`CTRL_ACK`) | No message IDs in the call signals: a duplicate ends the call or a late retry reverts a newer state; replaced by `CLOSE` on every carrier and state-only re-assertion after each carrier event |
| Move media at the endpoint layer | Would re-key and re-bind to relays; the carrier switch keeps `BME1` untouched |

**Review 2026-10-14 (first independent read-only review, NO-GO as drafted at 24f1218; resolved in 0108e88).** CR1 contacts only in both roles; CR2 boundary and generation for every content type, single carrier owner; CR3 `RESUME` on the surviving link, bearer failure distinct from session failure; CR4 pre-proof with fresh challenge and exact first-message hash, atomic single consume, fresh ticket per retry (judged sound by the later reviews; the complete framed BMH2 hello is built once); CR5 votes of stable verified identities, no time promotion; CR6 separate claim store, provenance across all entries sharing an address; CR7 phone-wide budgets, watchdogs, length check before allocation; CR8 upgrade-specific handshake options; CR9 explicit record order; CR10 `READY` ceilings; CR11 zero-prompt claim limited, pairing dialog and bond are measured gates; CR12 bit 5 and type 14 free, mask fix at `BluetoothPrivateCallRelay.kt` lines 693 and 723; CR13 exporter derived before key erasure in canonical order, wiped at teardown, `UP` held for the whole old session (no re-derivation after the keys are gone).

**Review 2 2026-10-14 (second review of 0108e88, NO-GO; resolved in 534bc19).** R2-1 leak of one-sided verification: the pairing key `K_cx` (now refined by R3-4); R2-2 inquiry pages before authentication: Tier 1 inquiry disabled, typed address, no visibility prompt; R2-3 reliable controls: semantic retry under fresh sequences (now narrowed by R3-3); R2-4 explicit state machines with fenced generations and independent watchdogs (now simplified by R3-2, R3-8); R2-5 bounded hold (now replaced by the two-phase cutover, R3-2); R2-6 a lone conflicting vote (now strengthened by R3-1); R2-7 EIR visibility is not `device.uuids`: moot while Tier 2 is disabled, recorded as a reopen condition.

**Review 6 changes that are not defects.** The upgrade attempt ceiling is 5 s everywhere (code, PROTOCOL liveness paragraph, S0-2), matching the deadline table. The old `RequestKeyframe` is split: `ForceLocalKeyframe` (this phone's own encoder, sender rows) and `RequestPeerKeyframe` (the receiver rows), with a new `ResetSendFragments` output for the unsent fragments of the frame being sent. Carrier-up and carrier-died events pass through the single consumer, in reader order relative to that carrier's content (PROTOCOL "One inbound consumer"); the model now enqueues them with the records. Two half-open reductions, both measured below: (a) a `SWITCH` that arrives on `N` while `O` is still alive here proves the sender closed `O`, so this phone closes `O` too, before the repeat check; (b) an `N` that dies while `O` lives always sends `RESUME(ticket)`, and the receiver closes the named `N` even when it is not (yet) accepting it. The round 6 behaviours of all of these stay switchable in `CarrierCutover.Config` (`asFirstDraft()` turns every correction back).

**What passed (corrected rules).** Twelve bounded exhaustive searches (state-hashed depth-first over 1 s ticks, the PROTOCOL ratios of hold 1 s to detection up to 2 s, a record delayed up to two ticks, a hold ceiling of three records) finished with no violation and 13.0 million distinct states in total: switch, hold and fallback with one fault (0.63 M states), the same with the reader threads separated from the consumer and carrier events in the queue (2.13 M), two faults in either order on both carriers (1.85 M), the handshake still pending with `READY` at any time (0.77 M), a second attempt after the first died (2.07 M), indispensable-state changes at any time (2.99 M), duplicated records (0.89 M) and dropped records (1.61 M; safety invariants only, because a stream carrier does not drop records and convergence is not claimed after one), and four fault-free searches of the normal switch with a writer backlog on the old link (invariant 8: frames of one and of two records, FIFO without the gate, and the reader queue; 40 thousand states, hold 2 s and records delayed at most one tick). **Half-open loss, measured (the review question, restated after review 6).** One media record per 50 ms in each direction, one carrier dies, and the two phones notice it at once or after the 2 s maximum (every combination of: the old link or the new one dying, before or after the switch, the peer's own direction switched or left on the old link; no network delay, so the numbers are the cutover's own). **Round 6 text:** the longest gap the receiver sees is the sender's own detection delay plus one 50 ms record, **2,050 ms (40 of 600 records lost in that direction at 20 per second, about 40 audio records or 60 frames at 30 fps)**, whenever the sender notices late, whether or not the peer noticed at once. That is the figure for a dead carrier with an empty writer queue; the honest statement is **2,050 ms plus the dead carrier's queued backlog** (measured with 250 ms still queued when the carrier dies: 2,350 ms). **Corrected text, with reductions (a) and (b):** both phones notice at once 50 ms (0 records lost); one phone notices at once 100 ms (1 record lost); neither notices before 2 s 2,050 ms (40 lost, plus the backlog). Neither reduction alone lowers the worst case of the middle row (round 6 text, (a) alone, (b) alone: 2,050 ms each): (a) acts when `O` dies and (b) when `N` dies, and the worst case runs over both. What remains is the 2 s liveness timeout when neither phone notices early.

**Reduction (a) withdrawn (review F-6, 2026-11-04).** A `SWITCH` that arrives on `N` no longer closes `O`: it names no instance of `O`, so a delayed marker could close the healthy standby an in-call renewal had just installed and end the call when Wi-Fi then died. It is logged (`old_dead_hint`) and ignored; `O` closes only by this phone's own liveness rule or the session end. Cost: when only the sender notices the old link's death at once, the other phone's own direction keeps writing into the dead link until its own detection (at most 2 s); `halfOpenMediaLossIsBoundedByTheSendersOwnDetectionDelay` prints the new numbers (A1 step 1b report).

Model checking found two renewal races before any wiring: an old-instance death queued before a renewal ended the call (the owner now holds a carrier-0 death while a renewal runs and drops it when the renewal binds), and a state record in flight on the replaced link was lost (every standby replacement now re-seals indispensable state). Review A1F2 closed the remaining two: a failed in-call renewal blocks any replacement for that fault, so a queued old-instance death is delivered and the session ends only when no carrier is left, and a `RESUME` naming the carrier this side still reads from is honoured; the reader-queue and 10,000-seed renewal searches pass with these rules.

**What the model does not show.** Records are opaque (no media, no fragments: only the existence of the suppress and reset outputs is checked); the writer is a FIFO per carrier whose only reordering is the first draft's priority `SWITCH`, and a record the writer never sent when its carrier dies is modelled as a write into a dead socket or, in the backlog measurement, as discarded in flight; the machine never looks at record kinds; time is coarse (1 s ticks in the exhaustive searches, 100 ms in the random runs, 50 ms in the half-open measurement; the real 3 s, 30 s and 5 s constants run in the random searches only, with the cooldown shortened as stated); the owner is assumed to call `onCarrierPending` when the new socket connects, never to start an attempt while another is alive, to map the 8-byte ticket to a per-session attempt counter, and to call the machine only from the consumer, with carrier events in reader order; the two phones run the same machine. Invariant 8 holds only while no record is delayed beyond the hold and is checked in fault-free runs; with longer delays the hold promotes by design and the old link's tail is dropped (the gate makes that rare, T-CX4 measures it). S0-3 and the stale-record drop depend on timing the model does not enforce: with a 2 s write watchdog and 30 s dial spacing a marker cannot outlive an attempt, so the ticket is defence in depth for `RESUME` and a real guard only if that timing ever changes.
